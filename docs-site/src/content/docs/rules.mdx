A rule is a markdown file under `.claude/rules/`. Claude Code loads it into every session in the
project, unless the rule is [path-scoped](#resident-and-path-scoped-rules): then it loads only when
a matching file is read. `cckit init` copies the rules from the kit's `templates/rules/`, picks the
set your profile lists, and fills in your project's values (the base branch, the owner, the
language).

To see the exact list for your project before anything is written:

```bash
cckit init --dry-run
```

| Rule | Governs | Profiles | Loads |

| `branch-naming` | branch name format, merge order, the lockfile rule, one worktree per agent | all six | every session |
| `communication-style` | how the agent writes to you, and the `concrete` pass on durable prose | all six | every session |
| `task-management` | GitHub issues as the source of truth, and the task loop | all six | every session |
| [`issue-lifecycle`](#issue-lifecycle) | deliverables as native sub-issues, approved-plan autonomy, explicit closes | all six | every session |
| [`merge-safety`](#merge-safety) | rebase onto the current base before merging, a coupled chain as one PR, the gate re-run on the integration branch | all six | every session |
| [`gate-and-review`](#gate-and-review) | the gate blocks the push and its output goes on the PR; every AI-reviewer finding is fixed or rebutted before the merge | all six | every session |
| [`authoring`](#authoring) | docs and README updated in the same change, no issue numbers in pasted prompts, summaries that name the work without machine flags | all six | every session |

The six profiles are `software`, `content`, `marketing`, `research`, `automation` and `minimal`; each lists its
rules under `rules` in `profiles/<name>.json`.

<Aside type="note" title="They are yours once written">
`cckit init --upgrade` preserves every rule file that already exists and adds only the missing
ones, so an edit you make survives an upgrade.
</Aside>

## Resident and path-scoped rules

A rule with no `paths:` frontmatter is **resident**: Claude Code loads it into every session,
whatever the task. A rule that declares `paths:` is **path-scoped**: it loads only once the session
reads a file matching one of its globs.

```markdown
---
paths:
  - "src/components/**/*.tsx"
---
```

Of the rules cckit ships, one is path-scoped:

| Rule | `paths:` | Written by |
| --- | --- | --- |
| `react-annotate` | `**/*.tsx`, `**/*.jsx` | `/kit-annotate`, the annotation setup |

Every other rule in the table above is resident, including all the rules a profile installs. They
are cross-cutting — branch names, merges, issue state — and have no file pattern to wait for.

To scope a rule of your own, add a `paths:` list to its frontmatter:

- **Scope a rule about one surface** — a component directory, a migrations folder. Globs resolve
  from the directory that holds the rule's `.claude/`, so a session started in the main checkout
  that edits inside `.claude/worktrees/<wt>/` needs the `.claude/worktrees/*/apps/**` form next to
  `apps/**`.
- **Do not scope a behavioural routing rule** ("send every design question to the designer agent"):
  it would not load until a matching file had already been read.

Resident rules count against the 150k characters of instruction files Claude Code loads per
session. [`instruction-budget-lint`](/review/gates/#instruction-budget-lint--what-every-session-loads)
is the gate on that total; its `--report` lists the resident and the path-scoped files separately.

## plain-language

`templates/rules/plain-language.md` — for a project whose people do not use git. cckit still runs
the work on worktrees, branches and pull requests; the rule decides what the agent **says**.

| cckit does | The agent says |
| --- | --- |
| records a task | "I added it to the task list." |
| creates a worktree and a branch | "I started the draft." |
| commits and pushes | "I saved the draft." |
| opens a pull request | "The draft is ready for review." Then the link. |
| the pull request merges | "It is approved and part of the shared version." |
| task states `todo` · `doing` · `review` · `done` | "not started" · "in progress" · "waiting for review" · "done" |
| task state `draft` (only on this computer) · `shared` · `dropped` | "not started, and only on this computer so far" · "waiting to be added to the shared list" · "dropped" |

The rule has a wording for every state `cckit task list` prints. `draft` in that list describes the
task record (nobody has started it and it is not on the shared list), so the agent says "not
started" for it and keeps "the draft" for the piece being written.

It names the mechanics when the person uses one of those words or asks how it works, reports a
failure as a failure with the command and its error on one line, and changes no command, no commit
message, no pull request title or body, and no text a program reads.

The rule follows a config switch, not a profile list:

```bash
cckit init --profile content --plain-language on --no-github
```

writes `"plainLanguage": {"enabled": true}` and the rule. `--plain-language off` leaves both out,
also on the `marketing` profile, whose default is on.
On `cckit init --upgrade` the stored switch wins: a project that set it to `false` and deleted the
rule does not get the rule back, and one whose switch is on gets a missing rule file restored. The
same switch rewords the progress lines of [`cckit task`](/project-management/light-tasks/#plain-language).

## Rules that came from a correction

Some rules restate nothing the kit already did by default: each records a correction that had to
be repeated across projects before it was written down. Those rules name their origin, the rule
they complement, and which one wins when two disagree.

### issue-lifecycle

`templates/rules/issue-lifecycle.md` — three conventions about when an issue is open, who merges,
and what closes it.

| Convention | Where it came from | Wins against |
| --- | --- | --- |
| A deliverable is a native sub-issue, never a body checkbox | issues closed with boxes still unchecked took the unfinished work out of every open-issue view | `plan-output-format` — the Deliverables table is an index; the issue state wins |
| An approved plan is executed, not re-confirmed: the captain merges each wave and pings only on a genuine blocker | an approved plan stalled on "merge or review?" for a routine planned merge | `risk-tiered-review` for a merge the plan covers; that rule's always-human list still wins for a change the plan did not imply |
| `Closes #N` links the PR; a close op closes the issue | GitHub auto-closes only on a merge into the default branch, so projects integrating elsewhere kept finished issues open | `task-management` — keep writing `Closes #N`, but the close is an explicit op |

The third one depends on your setup. `cckit merge` and `cckit effort close` close the linked issues
themselves, so it bites only on a merge the kit did not perform — the GitHub UI, or a raw
`gh pr merge`. `cckit doctor` warns when `github.baseBranch` differs from the GitHub default
branch; after such a merge, run `cckit close <N> "<summary>"`.

### merge-safety

`templates/rules/merge-safety.md` — three conventions about what a branch must pass before it lands.

| Convention | Where it came from | Wins against |
| --- | --- | --- |
| `MERGEABLE` is not safe: bring the branch onto the current base and pass the gate there before merging | a PR cut from a base that had since moved merged clean and reverted a sibling — 7,285 lines removed, no conflict, no failing check | `branch-naming` § *Merge order* decides the order and this rule decides what each PR passes first; it extends that section's lockfile "rebase the others" to every PR |
| A coupled chain ships as ONE PR | the PRs of a chain are siblings cut from one base, each stale once the one before it lands; a single PR has no sibling to revert | `task-management`'s one-PR-per-issue line — its migration/DDL exception becomes any coupled chain — and `branch-naming`'s size guidance, for a chain only |
| Re-run the gate on the integration branch after the subs merge | the gate had been run on each sub and not again on the branch they merged into | `effort-model` § *Lifecycle*, which lists no gate step between merging the subs and opening the PR |

The first one is a rule for whoever merges, because neither merge op makes a stale, conflict-free
branch current:

| Op | What it merges | What it rebases |
| --- | --- | --- |
| `cckit watch --merge` | a PR classified `CLEAN`: `MERGEABLE` with a merge state of `CLEAN`, `UNSTABLE` or `HAS_HOOKS`, no failing or pending check, no failing review, no policy floor | nothing — a `BEHIND` PR is classified `BLOCKED` and skipped |
| `cckit merge` | the PR as GitHub has it | only a `CONFLICTING` PR, from its own head branch, then `git push --force-with-lease` |

GitHub reports `BEHIND` only when the base branch's protection requires branches to be up to date
before merging. Turn that setting on for your base branch and the captain stops merging stale PRs;
with it off, a stale branch reads `CLEAN`. To bring a branch current by hand:

```bash
git fetch origin <base>
git rebase origin/<base>
git diff --stat origin/<base>...HEAD   # a deletion the issue never asked for is the revert
```

Then run your gate and push.

### gate-and-review

`templates/rules/gate-and-review.md` — two conventions about what stands between a commit and a
merge.

| Convention | Where it came from | Wins against |
| --- | --- | --- |
| The gate runs before `git push` and blocks it; the PR carries the run's output and exit code. CI running the same command is the second observation | a stated preference repeated across projects: a blocking pre-push hook plus exit evidence on the PR, not a CI lint job | `risk-tiered-review` § *The gates* on when and how the gate runs; that rule still decides who reads the PR |
| Every AI-reviewer finding is fixed, or rebutted with a reason on its own thread, before the merge — silence is never an outcome | measured: five review rounds collapsed to one when the reviewer's pass ran locally before the push | `risk-tiered-review`'s `risk:low` auto-pass and its approved-plan exemption, for a PR that carries findings |

The rule states the conventions; these are the switches that enforce them. All are off until you
turn them on:

| Switch | Effect | Turn it on |
| --- | --- | --- |
| `prePush.enabled` + `prePush.command` | a Claude Code `PreToolUse` hook (`.claude/hooks/prepush_gate.sh`) runs the command before an agent's `git push` and stops the push on a non-zero exit | `cckit init --prepush "<command>"` |
| `captain.mergePolicy.requireChecks` | `cckit watch --merge` reads a PR with no checks as `CHECKS_MISSING` and does not merge it | set it `true` in the config, or `KIT_CAPTAIN_REQUIRE_CHECKS=1` |
| `review.command` | the captain sends each PR it would merge to your reviewer; a recorded `gate: fail` blocks the merge | name the command in the config |
| `captain.mergePolicy.requireReview` | a PR with no verdict recorded reads `REVIEW_MISSING` and is not merged | implied by `review.command`; or set it `true`, or `KIT_CAPTAIN_REQUIRE_REVIEW=1` |

Two things no switch covers. The hook is a Claude Code hook, not a git hook, so a `git push` typed
in a terminal outside the agent session is not checked. And the captain reads one verdict per PR,
not one answer per finding: to make an unanswered thread block a merge, turn on *Require
conversation resolution before merging* in the base branch's protection on GitHub.
`cckit status` lists each open PR's unresolved review threads.

To put the gate's output on the PR, `scripts/lib/pr-evidence.sh` posts a log as a comment and edits
that comment in place on a re-run. `cckit init` copies it into the project (`cckit init --upgrade`
adds it to a project scaffolded before it shipped). No verb calls it for you; from the project root:

```bash
<your gate command> > gate.log 2>&1; echo "exit $?" >> gate.log
source scripts/lib/pr-evidence.sh
pr_attach_evidence <pr-number> gate.log "gate"
```

See [Captain merge policy](/config-and-permissions/#captain-merge-policy),
[the agent review stage](/config-and-permissions/#the-agent-review-stage) and
[Codified review gates](/review/gates/) for the lint that turns a recurring finding into a gate.

### authoring

`templates/rules/authoring.md` — three conventions about what gets written alongside the work: the
docs, the prompts in those docs, and the summary handed back to a person.

| Convention | Where it came from | Wins against |
| --- | --- | --- |
| Docs and README are acceptance criteria of every unit of work, updated in the same change, never a follow-up | a stated rule: the maintainer made the docs and README update mandatory for every unit, small changes included. It was written down only for `plan-next` output, a rule no profile ships | `plan-next` on where a sub-issue's own docs go — in that sub's commit, not deferred to the plan's docs sub-issue, which stays for what no single sub owns |
| A prompt meant to be pasted carries no issue number: it tells the agent to read the board and lets you pick | tutorial prompts shipped with literal numbers (`cckit orchestrate 46 47 48`) that were the author's issues, not the reader's | `naming-and-ids`, for a prompt only: that rule says how to write a reference, this one says a prompt has none |
| A summary for a person names the work as `slug #N` and attaches no output-mode flag to a verb it only mentions | recaps carried `cckit … --llm` beside each verb; the maintainer's response was that the tags said nothing | `naming-and-ids` wins on the identifier where it is installed (`E241`, `PR 268`); this rule wins on the name always accompanying it |

What each one asks for in practice:

- **Docs.** Search for the verb, flag, config key or path your change touches. Every match the diff
  leaves stale is unfinished work. A change with no visible behaviour owes no doc edit; say so in
  the PR body in one line.
- **Prompts.** Write *sync the board, show me what is ready, and I will pick*. In a command line use
  a placeholder (`cckit start <issue>`) or a form that selects for itself (`cckit next`). A commit,
  a PR body or a changelog still cites the real number: those describe one repository's history.
- **Summaries.** A command belongs in a summary when you are going to run it next, written exactly
  as typed. A flag that is evidence in a PR body — the command that ran and its exit code — stays.

### review-pages

`templates/rules/review-pages.md` — which output goes to a [review page](/project-management/plan-pages/) and how.

| Part | What it says |
| --- | --- |
| Three kinds | `plan` (before implementation), `decision` (two or more options), `grill` (a grilling round). Everything else stays in the terminal |
| Ask first | `cckit page mode` prints `page` or `terminal: <reason>`; on `terminal` the agent writes no HTML and prints instead |
| Write back | `cckit page answer` records every answer, on both paths: a comment on the issue, or a file under `docs/answers/` to commit with the change |
| Limits | never in an unattended run; a page before `cckit effort start` is recommended and checked by nothing; `reviewPages.enabled: false` turns pages off |

### shared-checkout

`templates/rules/shared-checkout.md` — three conventions about the one directory every session on a
machine has in common: the primary checkout, the first entry of `git worktree list`.

| Convention | Where it came from | Wins against |
| --- | --- | --- |
| Never move the primary checkout by hand — no `checkout`, `switch`, `pull`, `merge`, `rebase`, `reset` or `stash` there; it stays on the base branch, clean | observed 2026-07-03 with several sessions live: the primary checkout was found parked on a feature branch, then on the base, without the session reading it having moved it | `branch-naming` § *Branch lifecycle*, whose "switches to the base branch and pulls" describes the close op and stands for it only; `delegation-brief`'s `git reset --hard origin/<base>`, which is for an isolation worktree and never the primary checkout |
| Work in a worktree, always, a one-line fix included | the same incident: the close ops only check out the base, so a primary checkout on a feature branch means a session checked it out there | `branch-naming` § *Parallel work* — its one-agent-one-worktree line is extended to a session working alone |
| Call a freshly merged verb from a current worktree's `bin/`, not from PATH, when PATH resolves into the primary checkout | two incidents the same day: a verb merged minutes earlier answered "unknown command", and the version check read "ahead of plugin 0.3.0" from the stale branch's files | nothing — no shipped rule says which copy of a tool to run |

The rule forbids hand-run git, not the verbs. `cckit merge` (`scripts/lib/kit-task-ops.sh:424-425`)
and `cckit effort close` (`scripts/lib/effort-ops.sh:1025-1026`) check out and pull the base in the
primary checkout as their last step. With the checkout already on the base and clean, that switches
nothing and fast-forwards; both lines end in `|| true`, so a dirty or re-parked checkout is left
stale without a message.

[Multi-session safety](/development/many-sessions/) lists what sessions share and what cckit already isolates;
the [install & update matrix](/install-matrix/) says which install routes put PATH inside a clone.
