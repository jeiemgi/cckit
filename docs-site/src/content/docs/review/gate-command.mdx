An agent says a change works. The cheapest way to check that claim is to run something: the tests,
the type check, the linters. If each person and each agent runs a different subset, "it passed"
means a different thing every time.

So a team picks **one command** and calls it the gate. A change is ready for review when that
command exits 0, and not before. cckit does not choose the command for you. It gives you a place to
name it and makes the agent run it.

## Steps

### 1. Write the command down

<Chat
  title="naming the check that proves a change to the Bakery site is sound"
  say="Run the build and the linter together, as one command that fails when either fails, and tell me if they pass."
  ran="pnpm build && pnpm lint"
  means="This is the gate. A change is ready for review when it exits 0, and not before."
>
  Both passed. For this site the build and the linter are the check, joined into one line that
  exits non-zero on any failure. That line is the gate.
</Chat>

<Outcomes of="a gate command" title="Other examples of a gate command">

Whatever proves your project is sound, joined into one line that exits non-zero on any failure. For
a JavaScript project that is often the test, type-check and lint scripts:

```bash
pnpm test && pnpm typecheck && pnpm lint
```

Many projects put it in a script, so the gate has one name. cckit's own gate is
`bash scripts/check.sh`.

</Outcomes>

### 2. Tell cckit at setup

<Chat
  title="making the Bakery site run its check before every push"
  say="Set up the Bakery site so every push runs the check first and stops if it fails."
  ran='cckit init --prepush "pnpm build && pnpm lint"'
  means="This is for the first cckit init of a project. In your own project, pass your gate command in place of the Bakery one."
>
  Done. The check is saved in the project config and the push hook is installed. From now on a
  `git push` runs the check first and stops if it fails.
</Chat>

<Outcomes of="cckit init --prepush" title="What the flag writes">

`cckit init --prepush "<your gate command>"` writes `prePush.enabled` and `prePush.command` to the
project config and installs the hook `.claude/hooks/prepush_gate.sh`. From then on, when the agent
types `git push`, the hook runs the command first and stops the push if it fails.

</Outcomes>

The Bakery site was already set up, without the flag. For a project like that there is no cckit
command that adds the hook yet: `cckit init --upgrade` does not install it (see
[Limits](#limits)). Run the gate in CI (step 3), which covers every pull request, and see
[Hooks](/hooks/) for what the hook is and where it is registered.

### 3. Run it in CI too

The hook covers the agent's machine. A CI workflow that runs the same command on every pull request
covers everyone else, and gives the captain a check status to read.

### 4. Add cckit's lint scripts to it

Add them when you want a reviewer's repeated findings to fail the gate: [Turn repeated review
findings into checks](/review/gates/).

  ran="git push"
  means="If the push goes through, the hook is not installed. See Limits below."
>
  The push was stopped. The check failed, so the hook refused to send the branch. Here is the
  command's output.
</Chat>
## Limits

- **The hook is installed by a first `cckit init`.** `cckit init --upgrade` keeps an existing
  `prePush.command` and does not add the hook to a project that was set up without the flag.
- **The hook sees a `git push` the agent types.** A push made by `cckit pr` or `cckit hotfix`
  reaches only a real git hook (`.git/hooks/pre-push`). Both verbs export the target branch to it
  as `KIT_PR_BASE`: [Hooks](/hooks/#kit_pr_base-in-a-git-pre-push-hook).
- **No cckit verb runs the gate before a merge.** `cckit merge` and `cckit effort close` merge what
  GitHub has. Whoever merges runs the gate on the current tree first:
  [Merge, close and clean up](/ship/merge-and-close/).

The [`gate-and-review`](/rules/#gate-and-review) rule, installed by every profile, states the
team's side of this: the gate blocks the push, and every reviewer finding is fixed or answered
before the merge.
