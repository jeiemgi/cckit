A key committed by accident is public the moment it is pushed, and removing it afterwards does not
make it private again. An agent raises the odds: it stages files quickly, and it does not know
that a client's name or an internal hostname is private to you.

The answer is a check that runs at the last moment the mistake is still local: when the commit is
made. The secret guard scans what is being committed and blocks the commit when it finds a key, an
env file, or a term from a list you wrote. Review never sees the secret because the commit never
existed.

<Aside type="note" title="New here? What a pre-commit hook is">
A pre-commit hook is a script git runs the moment you try to commit. If the script fails, the commit is blocked. cckit uses one so a secret is caught at commit time, before it ever reaches a remote.
</Aside>

## Who runs it

Nobody runs it by hand. Git runs the hook on every commit, whoever made it: you, Claude Code,
Codex. In cckit's own repository the same scan also runs inside the gate, over every tracked file,
including docs, the cookbook, examples and templates.

## What it blocks

- **Forbidden files** — `.env*` (including `.env.example`), `*.pem` / `*.key` / keystores, `id_rsa`, `.netrc`, `*.tfvars`, project id dumps.
- **Secret content** — provider key prefixes, private-key blocks, JWTs, and secret-looking assignments. Placeholders like `<...>`, `${...}`, and `YOUR_…` are allowed.
- **Your private terms** — a denylist you control (below).

## Where the guard lives

The guard is three files in the cckit repository:

| File | What it is |
| --- | --- |
| `scripts/lib/secret-guard.sh` | The scan |
| `githooks/pre-commit` | The git hook that runs the scan on the staged files |
| `privacy-denylist.example` | The empty starting point for your private list |

<Aside type="caution" title="cckit init does not copy these into your project">
`cckit init` writes none of the three. In a clone of cckit they are already in place. In your own
project, copy them in first:
[Stop agents committing secrets](/review/stop-committing-secrets/) has the commands.
</Aside>

## Where it runs

| Where | What it scans | How to enable |
| --- | --- | --- |
| Pre-commit hook, `githooks/pre-commit` | The files staged for that commit | `git config core.hooksPath githooks` |
| The gate of cckit's own repository, `scripts/check.sh` | Every tracked file | Runs as part of the check suite |

A finding blocks the commit. The guard is not bypassed by the permission consent described in
[Config and permissions](/config-and-permissions/#the-permission-gate-ask-before-operating). The
hook itself can be skipped by whoever commits: `git commit --no-verify` does it, and the hook's own
message names that flag. `core.hooksPath` is a setting of one clone, so each person on the team
turns the hook on once.

## Your private denylist

Nothing project-specific is hardcoded in cckit. You declare what is private to you, and cckit
ships the list **empty**: it never guesses what is yours.

<Steps>

1. **Copy the example** into the state directory (the target is gitignored). `secret-guard.sh` reads
   the **one shared** `.cckit/` for the whole repository, so a plain relative `cp` run from a
   worktree writes a file the scan never reads — and it would ignore `KIT_STATE_DIR`. Let the
   resolver name the destination:

   ```shell
   # works from the primary checkout and from any worktree, and honors KIT_STATE_DIR
   d="$(git rev-parse --git-common-dir)"; case "$d" in /*) ;; *) d="$PWD/$d" ;; esac
   d="${KIT_STATE_DIR:-$(cd "$d/.." && pwd)/.cckit}"
   mkdir -p "$d" && cp privacy-denylist.example "$d/privacy-denylist"
   ```

   From the primary checkout with no override, that is just `.cckit/privacy-denylist`.

2. **List your terms** — org names, hosts, emails, anything private to you, one per line.

3. **Commit something** — the guard fails if any term appears in a file being committed.

</Steps>

The shared `.cckit/` lookup needs `scripts/lib/kit-state.sh` beside the guard. Without that file
the guard reads `.cckit/privacy-denylist` relative to the directory the commit runs in.

## Reporting a vulnerability

Open a private security advisory on the repository (Security → Advisories), or a regular issue if it is low-risk. Do not include secrets or exploit details in a public issue.
