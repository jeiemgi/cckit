The agent that wrote a change reads it with the same assumptions it wrote it with. A second
reader with no stake in the change catches what the first one cannot. On a human team that is code
review. When the captain merges on its own, nobody is doing it unless you give that job to a second
agent.

**What you will have at the end:** a reviewer agent that reads each pull request before
`cckit watch --merge` lands it. The captain pipes a brief to the reviewer, the reviewer answers
with a short report, and that report is stored as a receipt tied to the commit it read. A
`gate: fail` blocks the merge until a new commit is pushed and reviewed.

**Who does it:** the reviewer is an agent profile that lists the `review` stage and may not write
to a branch. It runs on the `claude` or `codex` CLI you already have, or on any command you name.
The stage is off until you configure it.

## Steps

### 1. Declare a reviewer and turn the stage on

<Chat
  title="adding a read-only reviewer to the Bakery site"
  say="Add a reviewer to the Bakery site: a read-only agent that reads each pull request before the captain merges it."
  ran="jq '{review, agents}' .claude/kit.config.json"
  means="The reviewer is a profile that lists the review stage and does not set write, so it may not write to a branch."
>
  I added the reviewer profile and turned the review stage on in the project config, then read both
  blocks back. Nothing is reviewed yet: that starts when a pull request is open.
</Chat>

Add both blocks to the project config (`.claude/kit.config.json`, or `cckit.config.json` at the
root):

```json
{
  "review": { "headless": true, "timeoutSeconds": 900 },
  "agents": {
    "profiles": {
      "reviewer": { "kind": "claude", "tier": "low", "stages": ["review"] }
    }
  }
}
```

<Outcomes of="the reviewer config" title="What these two blocks do">

`headless: true` has cckit build the reviewer's command from the profile: `claude -p` for
`kind: claude`, `codex exec -` for `kind: codex`. The profile lists the `review` stage and does
not set `write`, so it may not write to a branch. A profile with `write: true` is refused as a
reviewer.

</Outcomes>

## How to check it worked

- `cckit receipt show <issue> review` prints a receipt whose `gate` line is `pass` or `fail`.
- The same report is a comment on the issue.
- `cckit watch --merge` merges a pull request with a pass on its current head and reports
  `REVIEW_FAILING` or `REVIEW_MISSING` for one without.

## How it works

The reviewer gets a brief on stdin: the PR and issue, an instruction to report only defects it can
point at in the diff, and a READ ONLY rule. It must end its reply with five lines, which is the
format the receipt is parsed from:

```text
outcome: <pr-open|blocked>
url: <the PR URL>
gate: <pass|fail> — <what was read>
blocker: <the defect that stops this merging, or none>
next stage: <none if it may merge, build if it goes back to the author>
```

Configuring the stage also requires its result: with `review.headless` or `review.command` set, a
PR with no verdict reads `REVIEW_MISSING` and the captain does not merge it. Every `cckit watch`
pass dispatches, with or without `--merge`.

**To run your own reviewer,** set `review.command` to a command line that reads the brief on stdin
and prints that report on stdout. It wins over `headless`, and it receives the resolved profile in
`CCKIT_REVIEW_PROFILE`, `CCKIT_REVIEW_KIND` and `CCKIT_REVIEW_ARGS`.

**Which profile reviews.** With no `agent:<profile>` label on the issue or its parent effort, the
reviewer is `agents.default`, or the lowest-`tier` profile when that is unset. That choice is not
made per stage. If it lands on a profile that does not list `review`, the dispatch is refused:

```text
agent-profile: profile 'builder' is not allowed at stage 'review' (it lists: build )
agent-resolve: rejected 'builder' (from agents.default)
```

The config in step 1 declares one profile so the default is the reviewer. With that config,
launch build workers by naming the CLI (`cckit orchestrate --agent claude <issues…>`), which skips
profiles; an unflagged launch would resolve the reviewer for the build stage and be refused.

- Every key, the environment the command receives and the timeout rule:
  [The agent review stage](/config-and-permissions/#the-agent-review-stage).
- Profiles, tiers and the label that selects one:
  [Agent profiles](/config-and-permissions/#agent-profiles).
- Receipts, attempts and the issue comment:
  [Stage receipts](/config-and-permissions/#stage-receipts).

<Aside type="caution" title="What is and is not verified">
cckit refuses a `write: true` reviewer, but it does not verify that the reviewer's process is
read-only: what the agent may do is set by its CLI's defaults, your agent settings and the
profile's `args`. The stage is tested with stub binaries; the reference states that no live
reviewer has been run through `headless`. Run it first on a repository where a wrong verdict
costs nothing.
</Aside>

## Troubleshooting

**The row never reads `-> reviewed`.** The PR is not one the captain would merge: it conflicts, a
check is failing or pending, it is a draft, or a policy floor holds it. Those are not sent to a
reviewer.

**`PR #<n> has no linked issue`.** The branch name carries no issue number, so there is nothing to
record a receipt against. Open PRs from `cckit start <issue>` worktrees.

**The PR stays `REVIEW_MISSING` on every pass.** The reviewer ran and left no receipt: it timed
out, exited non-zero, or its reply had no `outcome:` line. Run the reviewer command by hand with a
short prompt and check that its reply ends with the five lines above.

**`review.headless is on but profile '<name>' is kind '<kind>'`.** `headless` builds a command for
`claude` and `codex` only. Set `review.command` for any other reviewer.

**You disagree with a `REVIEW_FAILING` verdict.** No setting turns a recorded fail off. Push a
commit: that makes the verdict stale and the next pass reviews the new head.
