An agent finishes a change and reports that it works. That report is a claim. The agent that wrote
the code is the one least able to see what is wrong with it, and it writes changes faster than a
person can read them.

A software team answers this with layers. Cheap checks run first and catch what a machine can
catch. A second reader looks at what is left. A person opens the running result. Only then does
somebody decide to merge. Each layer leaves a record tied to the commit it looked at, so "it
passed" always means "this exact commit passed".

The layers are opt-in. A new project has almost none of them switched on, and you add each one
when the team needs it.

## The layers, in order

1. **The gate.** One command that proves a change is sound: the project's tests, its type check,
   its linters. The builder runs it before pushing, and the output goes on the pull request as
   evidence. cckit ships three lint scripts you can add to that command, so a defect a reviewer
   found once fails the gate the next time.
2. **The secret guard.** A scan of what is about to be committed for keys, env files and the
   private terms you list. It runs at commit time, before anything leaves the machine.
3. **A second agent's read.** A read-only reviewer agent reads the pull request and answers
   `gate: pass` or `gate: fail`. A fail blocks the merge until a new commit is pushed and reviewed.
4. **A person trying it.** The QA lane starts the project on its own ports, opens the screen the
   change touched, and records a pass or a fail with notes.
5. **The decision to merge.** A person, or the captain on a plan the owner approved. The captain
   is whoever drives an approved plan: see [Roles](/project-management/roles/#the-captain). That
   step is the [Ship](/ship/) area.

## What to do first

1. **Name your gate command** and have the agent run it before every push:
   [Choose your gate command](/review/gate-command/).
2. **Install the secret guard**, so a key cannot reach a commit:
   [Stop agents committing secrets](/review/stop-committing-secrets/).
3. **Turn on agent review or QA later**, when more than one person merges or when changes need a
   person to look at a running screen.

## Who does each one

| Layer | Who does it | Where the result is kept |
| --- | --- | --- |
| Gate | The agent that built the change, then CI | The gate's log on the pull request, and the check status |
| Secret guard | A git hook, on every commit | The commit is blocked; there is nothing to keep |
| Agent review | A second agent that may not write to the branch. It runs under an agent profile: a named agent setup in the config, not the team profile you picked at setup | A `review` receipt (a small saved record of a verdict, tied to the commit it was given for) and a comment on the issue |
| QA | A person. The `qa` agent of the software profile writes the tests; it does not record this verdict for you | A `qa` receipt and one comment on the pull request |
| Merge | The owner, or the captain on an approved plan | The merged pull request and the closed issue |

The `security` agent of the software profile is a specialist you call for an audit. The
`/kit-security-sweep` skill sends it through the project and files what it finds as issues. It is
not a step every pull request passes.

The roles are described in [The team](/philosophy/the-team/).

## What is on, and what you turn on

Most of these layers are off in a new project. This is deliberate: a repository with no CI, read
by one person, is a legitimate setup, and a check that holds every merge without saying why is
worse than no check. Turn each one on when you want it.

| Layer | In a new project | How to turn it on |
| --- | --- | --- |
| Lint scripts | The three scripts are copied in by `cckit init`, each with a record of the defects the project already has | Add them to your gate command: [Turn repeated review findings into checks](/review/gates/) |
| Gate before the push | Off | `cckit init --prepush "<command>"`: [Choose your gate command](/review/gate-command/) |
| Secret guard | Not copied into your project | [The secret guard](/review/secret-guard/) |
| Agent review | Off | Set `review.headless` or `review.command`: [Agent review before a merge](/review/agent-review/) |
| QA required to merge | Off | `captain.mergePolicy.requireQa`: [QA on a running stack](/review/qa-lane/) |
| Holding risky files for a person | On | See below |

## What always needs a person

`cckit watch --merge` is the one place cckit merges without a person watching. It has **floors**:
kinds of change it never merges alone. A pull request that touches a workflow file, a dependency
or lockfile, or a security-sensitive path, or that carries the `hold` label, is reported as `HELD`
and left for a person. A draft is reported as `DRAFT` and waited on.

The floors are on by default and can be switched off or extended. The exact paths and the config
keys are in [Captain merge policy](/config-and-permissions/#captain-merge-policy). The four cases in
which a captain stops and asks, whatever the files, are under
[the captain](/project-management/roles/#the-captain).

<Aside type="note" title="Review tiers by risk are optional">
cckit ships a rule that sorts pull requests into `risk:low`, `risk:med` and `risk:high` and says
which tier a person must read. No profile installs it. Copy
`templates/rules/risk-tiered-review.md` into `.claude/rules/` to adopt it. The rule that every
profile does install is [`gate-and-review`](/rules/#gate-and-review): the gate blocks the push, and
every finding from an AI reviewer is fixed or answered before the merge.
</Aside>

## The tools that plug in

cckit does not build a reviewer, a test runner or a CI service. It connects the ones you have and
records what they said.

- **Your gate command.** Whatever proves your project is sound. cckit runs it before a push when
  you ask it to; it does not choose it for you.
- **GitHub checks.** The captain reads the check status GitHub reports. Branch protection on
  GitHub is where "a person must approve" and "every review thread must be resolved" are enforced.
- **Claude Code or Codex as the reviewer.** The review stage runs `claude -p` or `codex exec -`
  for you, or any command you name that reads a brief and prints a verdict.
- **Your project's own start command.** The QA lane launches the command you declare. It does not
  guess how your project boots.

## The verbs

| Verb | What it is for |
| --- | --- |
| `cckit qa up` · `open` · `verdict` · `stop` | Start the project for one change, open the changed screen, record pass or fail, free the ports |
| `cckit qa lanes` | List every change that has a running stack or a verdict |
| `cckit watch` | One captain pass: read every open pull request, send the ready ones to the reviewer |
| `cckit receipt list <issue>` · `cckit receipt show <issue> review` | Read back what a reviewer or a QA pass recorded |
| `cckit status` | Open pull requests waiting on a person, with their unresolved review threads |

Every flag is in the [CLI reference](/cli-reference/).
