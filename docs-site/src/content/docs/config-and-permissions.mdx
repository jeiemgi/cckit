How cckit finds its config, reads what kind of project it is pointed at, and asks before it changes anything — all without a single hardcoded org, repo, or path.

## Config resolution (nearest wins)

cckit runs in the directory you invoke it from. It finds the config for that project by walking upward from the current folder and taking the first match.

| Order | Source | What it is |
| --- | --- | --- |
| 1 | `$KIT_CONFIG` | An explicit path in the environment. Always wins. |
| 2 | `cckit.config.json` | The project config at (or above) the repo root. |
| 3 | `.claude/kit.config.json` | The config a kit-scaffolded project keeps under `.claude/`. |
| 4 | cckit's own config | The fallback when you run outside any project. |

No org, repo, or path is hardcoded — every value comes from this file. A repo with no config is invited to run `cckit init`.

`cckit init` writes source 3 when the Claude adapter is selected and source 2 for a Codex-only
project, which has no `.claude/` directory. The config's `adapters` array records the selection
(`["claude"]`, `["codex"]` or both); a config without the key means `["claude"]`. The ownership
manifest — the hashes `cckit remove` and `--upgrade` use to tell a kit-owned file from an edited one —
sits beside it: `.claude/kit.manifest.json`, or `.cckit/kit.manifest.json` in a project that started
Codex-only. Neither file moves when the second adapter is enabled later.

### Overriding the base branch for one command

`github.baseBranch` is the default, not the last word. A `KIT_BASE_BRANCH` already in the
environment wins over it:

```bash
KIT_BASE_BRANCH=effort/42-auth cckit orchestrate 44
```

```text
orchestrate: repo owner/repo (base effort/42-auth), cap 4, runtime 'tmux', agent 'claude'
orchestrate: base 'effort/42-auth' comes from KIT_BASE_BRANCH in the environment (the config says 'develop')
```

The second line appears only when the two differ. An empty `KIT_BASE_BRANCH` counts as unset.

| Variable | Holds |
| --- | --- |
| `KIT_BASE_BRANCH` | The base in effect: the environment value when one is set, otherwise the config's. |
| `KIT_BASE_BRANCH_CONFIG` | What the config says (`github.baseBranch` → `integrationBranch` → `flow` → `main`), whether or not it was overridden. |
| `KIT_BASE_BRANCH_DEFAULTED` | The value cckit exported when it fell back to the config; empty when the caller overrode it. Internal: do not set it. |

cckit exports the base it resolved, so a process it starts inherits `KIT_BASE_BRANCH`. That
inherited value is not an override: a later `cckit` in another project compares it with
`KIT_BASE_BRANCH_DEFAULTED`, finds them equal, and reads its own config. One limit follows: inside
an environment cckit already exported into, an override that names that same exported value is read
as the default.

`orchestrate` hands an override to each agent it starts, so `cckit pr` inside the pane targets the
same branch the worktree was cut from. On tmux the agent's command line becomes
`env KIT_BASE_BRANCH='<branch>' <agent> …`; on Herdr the workspace and each tab are created with
`--env KIT_BASE_BRANCH=<branch>`. A pane's environment comes from the tmux or Herdr server, not from
the `orchestrate` process, so the variable alone would reach the pane only when `orchestrate`
happened to start the server. `orchestrate` also starts a tmux server without `KIT_BASE_BRANCH` in
its environment and removes one an earlier run left there, so panes opened later on other projects
do not inherit it.

Two things to know before using it:

- **The branch must exist on origin.** `cckit start` and `orchestrate` fetch `origin/<base>` before
  cutting the worktree, and the fetch fails on a branch that was never pushed.
- **Every verb that loads the config reads it.** `cckit start` cuts from it, `cckit pr` opens the PR
  against it, `cckit gc` measures "landed" against it. Set it on the one command that needs it;
  a shell-wide `export` redirects all of them.

<Aside type="note" title="New here? Why 'nearest wins'">
"Nearest wins" means cckit uses the config closest to where you are standing in the folder tree. If you run a command three folders deep, cckit walks up until it finds the first config file and uses that one. This is the same idea many tools use so a sub-project can override its parent.
</Aside>

### Where these live on disk

Sources 2–4 are files; source 1 (`$KIT_CONFIG`) is an environment variable, so it isn't in the
tree. Everything cckit writes about *you* — install consent, identity — lands in `.cckit/`, which is
gitignored, so it never leaves your machine.

<FileTree>
- your-repo/
  - cckit.config.json    **source 2** · repo, owner, base branch — nothing hardcoded
  - .claude/
    - kit.config.json    **source 3** · a kit-scaffolded project's config
    - …    agents, hooks, rules, skills
  - .cckit/    gitignored — cckit's local state, never committed
    - consent    one `install:<id>` line per integration you approved installing
    - identity    your name, asked once on first run
    - privacy-denylist    extra paths the secret guard must block
  - … your existing files, untouched
</FileTree>

## Project scanning

cckit detects the project it is pointed at from the filesystem, not from baked-in knowledge. Run it yourself to see what cckit sees:

```bash
cckit scan --llm
```

It reads three things:

- **The repo root** — `git rev-parse --show-toplevel`.
- **Stack hints** — `package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`.
- **Kit state** — `cckit.config.json`, `.claude/`, `.cckit/`.

:::note[`.cckit/` is shared across worktrees]
There is **one** `.cckit/` per repository, at the primary checkout — not one per worktree. It is
resolved from git's shared common directory, so the captain's gate record, the resume-here handoff
and your private denylist are the same files whether you run cckit from the checkout or from a
worktree. Set `KIT_STATE_DIR` to override the location.

This matters because cckit tells you to work in worktrees. Resolving state against the *current*
worktree would give each one its own copy — a handoff saved in one place would read back as "no
resume-here handoff saved" everywhere else.
:::

## The permission gate (ask before operating)

cckit asks before it changes anything in a repo it has not worked in before.

- **A config or `.claude/` file is proposed before it is written.** `cckit add <module>` and `cckit migrate` go through one machine (`scripts/lib/kit-operate.sh`): show the change, ask, apply, record. `KIT_DRY_RUN=1` previews and writes nothing; `KIT_ASSUME_YES=1` skips the question, and still keeps a file you edited. `cckit init --dry-run` prints the scaffold plan and writes nothing.
- **A third-party tool installs only with recorded consent.** Your yes to `cckit doctor` (its prompt, or `--fix`) is written as one `install:<id>` line in `.cckit/consent` (gitignored). That file holds install consent and nothing else: no other verb reads or writes it. See [Integrations](/integrations/#what-your-yes-records).
- **The secret and privacy guard always runs** before anything is committed or published. It is not optional and no consent bypasses it — see [Security](/security/).
- **Destructive or irreversible operations** (force-push, repo create, history rewrite) always require a separate, explicit confirmation.

## Captain merge policy

`cckit watch --merge` is the one place cckit lands code without a human in the loop, so its policy is
config, not code. Everything below lives under `captain.mergePolicy` in the config file resolved
above, and every key has an environment override that **always wins** — so you can opt in or out for
a single invocation without editing the file.

| Key | Default | What it does | Env override |
| --- | --- | --- | --- |
| `floors` | `true` | Refuse to auto-merge a PR that touches `.github/workflows/**`, a lockfile or dependency-graph file, or a security-sensitive path — and always honour a `hold` label. Verdict becomes `HELD`. | `KIT_CAPTAIN_FLOORS=0` |
| `protectedGlobs` | `[]` | Extra path globs added to the floors above. | `KIT_CAPTAIN_EXTRA_GLOBS` |
| `requireChecks` | `false` | Treat a PR with **no checks at all** as unverified rather than green. Verdict becomes `CHECKS_MISSING`, action `verify`. | `KIT_CAPTAIN_REQUIRE_CHECKS=1` |
| `requireReview` | *(implied)* | Treat a PR with **no agent review recorded** as unverified. Verdict becomes `REVIEW_MISSING`, action `verify`. Defaults to on when `review.command` or `review.headless` is set and off when it is not — set it explicitly to break that link either way. | `KIT_CAPTAIN_REQUIRE_REVIEW=1` |
| `requireQa` | `false` | Hold a PR for a **human QA pass**. `true` covers every PR; a list of label names (`["flow:ui"]`) covers only PRs carrying one of them. A would-be merge with no `cckit qa verdict pass` recorded against its current head becomes `QA_MISSING`, action `verify`. | `KIT_CAPTAIN_REQUIRE_QA=1`, `KIT_CAPTAIN_QA_LABELS` |

### Holding merges for a QA pass

`requireQa` reads the verdict `cckit qa verdict` records for a lane. It is off by default, and
declaring a QA stack under `qa` does not turn it on.

| Verdict | Action | What happened |
| --- | --- | --- |
| `QA_FAILING` | `fix` | A QA fail is recorded against the PR's current head. Blocks whether or not `requireQa` is set. |
| `QA_MISSING` | `verify` | QA is required for this PR and no pass is recorded against its current head. |

- A pass belongs to one commit. Push again and it reads as absent, so the PR is `QA_MISSING` until
  the new head is reviewed. A fail recorded on an older head is absent too.
- The label list is matched against the **PR's** labels. A label whose name contains a space
  cannot be listed.
- `KIT_CAPTAIN_QA_LABELS` is space-separated. Setting either environment value means
  `requireQa` is not read, so `KIT_CAPTAIN_REQUIRE_QA=0` switches a configured list off for one run.
- A PR that is both unreviewed and un-QA'd reads `REVIEW_MISSING` first: the agent reviewer runs
  before the human one, and a PR held at `QA_MISSING` is still sent to the reviewer.
- With `qa.command` configured and `requireQa` unset, `cckit watch` names every PR it would merge
  with no QA pass on its head, and the key that holds them.

### Why `requireChecks` exists

The captain decides from three things GitHub reports about a PR: whether it merges cleanly, its merge
state, and its **check rollup**. When that rollup is *empty* there is nothing to read — and an empty
rollup is not a pass, it is the **absence of evidence**. Read as green, it means a repo with no CI is
auto-mergeable by construction: "the gates are green" was never observed, only assumed.

Turn `requireChecks` on and that case gets its own verdict, distinct from the two that already exist:

| Verdict | Action | What actually happened |
| --- | --- | --- |
| `CHECKS_FAILING` | `fix` | Something ran and went red. |
| `CHECKS_PENDING` | `wait` | Something is still running — come back. |
| `CHECKS_MISSING` | `verify` | Nothing ran. There is no evidence to wait for. |

It also closes a smaller race: a PR gated in the seconds before CI registers has an empty rollup too,
so with `requireChecks` on the captain waits for the checks to appear instead of merging into the gap.

<Aside type="caution" title="It is off by default — on purpose">
A repo with no CI, reviewed by a human, is a legitimate setup. Requiring evidence everywhere would
turn that into a captain that merges nothing and reports steady state with no explanation — a silent
stall, harder to debug than the thing it prevents. So the default keeps existing behaviour, and
instead `cckit watch` **says the assumption out loud**: any pass that would merge a PR with an empty
rollup prints that green was assumed, not proved, and names this key. If your repo has CI, set it to
`true` — cckit sets it on itself.
</Aside>

## The agent review stage

The captain can run an agent over a pull request before it merges, and refuse to merge on what that
agent finds. It is **off until you turn it on**, one of two ways:

```json
{ "review": { "command": "claude -p", "timeoutSeconds": 900 } }
```

```json
{ "review": { "headless": true, "timeoutSeconds": 900 } }
```

`command` is your own command line. `headless: true` has cckit build it from the resolved review
profile's `kind` and `args`: `claude -p <args>` or `codex exec <args> -`. `command` wins when both
are set. A profile whose `kind` is neither `claude` nor `codex` is refused under `headless` (no
receipt, the PR stays at `verify`) — give that one a `command`. Either setting turns
`requireReview` on.

cckit pipes a brief to that command's **stdin** and reads the reviewer's report off its **stdout**.
That report becomes a [stage receipt](#stage-receipts) at stage `review`, written locally and
mirrored onto the issue.

The command also receives the resolved profile in its environment, so it can dispatch the agent the
issue's `agent:` label actually asked for rather than a fixed one:

| Variable | What |
| --- | --- |
| `CCKIT_REVIEW_PROFILE` | the resolved profile name |
| `CCKIT_REVIEW_KIND` | its `kind` (the agent executable) |
| `CCKIT_REVIEW_ARGS` | its `args`, one per line |
| `CCKIT_REVIEW_PR` / `CCKIT_REVIEW_ISSUE` / `CCKIT_REVIEW_REPO` | what is being reviewed |

A command that ignores all of them still works.

`timeoutSeconds` (default `900`) bounds the run. The captain is unattended and single-threaded, so a
reviewer that never returns blocks the whole pass — every other PR in it included — with nobody
watching. On expiry the process is killed and **no receipt is written**: a killed reviewer is not a
verdict. A non-numeric or zero value falls back to the default rather than disabling the bound.

<Aside type="note" title="What headless builds, and what it does not">
`headless` uses the same launcher as [`cckit autopilot run`](/agent-compatibility/#unattended-run-limits)
(`scripts/lib/agent-launch.sh`). It adds no permission flag and names no model, so what the reviewer
may do is set by the CLI's defaults, your own agent settings and the profile's `args` — cckit
refuses a `write: true` profile but does not verify the process is read-only. Both command forms are
read from each CLI's `--help`; the tests drive stub binaries, so no live reviewer has been run this
way.

`command` remains for everything else: the reviewer can be anything that reads stdin and writes the
report format — a wrapper script, a hosted service, an agent CLI cckit has no headless form for.
</Aside>

### What gets reviewed, and when

A PR is dispatched to a reviewer only when the captain **would otherwise merge it**. One that
conflicts, fails a check or is still a draft is going to change before anyone should read it, and a
PR already stopped by a [policy floor](#captain-merge-policy) belongs to a human who does not need a
second opinion first.

After a dispatch the PR reads `verify` for the rest of that pass — **whether or not the reviewer
succeeded**. The verdict is gated on the next pass, once it is recorded. A review that is still
running is not a review that passed.

### The reviewer never writes

A review profile must not touch the branch it is reviewing. Three things hold that:

- `write` defaults to `false` on every profile, and a profile with `write: true` is **refused** at
  the review stage rather than trusted to behave.
- `orchestrate` leases each branch to one writer, so a second writer is refused anyway.
- The brief says READ ONLY in as many words.

The first is the one that matters — the other two are downstream of a profile you already declared
able to write.

### A verdict belongs to one commit

Each review receipt records the PR head it was produced from, and the gate compares it against the
current head. Push a new commit and the previous verdict reads as **absent**, not as a pass — the
reviewer read code that is no longer there. That applies to a `fail` too: a stale finding is not a
finding against the new revision.

That is also what makes the loop terminate. A PR with a `REVIEW_FAILING` verdict is not re-reviewed
on its own; the author acts on the finding and pushes, which moves the head, which makes the verdict
stale, which earns the next review.

### The two verdicts

| Verdict | Action | What happened |
| --- | --- | --- |
| `REVIEW_FAILING` | `fix` | The reviewer ran and said `gate: fail`. |
| `REVIEW_MISSING` | `verify` | No review recorded. |

`REVIEW_FAILING` always blocks. A recorded failure is **evidence**, so no configuration switch
turns it off — if you disagree with a verdict, record a new one.

`REVIEW_MISSING` is the same shape as `CHECKS_MISSING`: the **absence** of evidence, which is the
state of every repository that has not run a reviewer yet. Requiring it unconditionally would stop
every captain everywhere the moment you upgraded, so it blocks only when review is required.

<Aside type="caution" title="Absence is not failure — and not a pass either">
The distinction runs through both gates. Something that ran and went red is a fact you can act on.
Nothing having run is a hole where a fact should be. cckit reports them as different verdicts
because the fix is different: one is "go read the finding", the other is "go produce the evidence".

While review is **not** required, `cckit watch` says so out loud — any pass that would merge a PR
with no verdict prints that, names both keys that close it, and goes quiet once either is set.
</Aside>

<Aside type="tip" title="Not the same thing as review-lint">
[Codified review gates](/review-gates/) are static linters that run inside `scripts/check.sh` —
patterns earned from past review findings, enforced on every commit. This page's review stage is an
**agent** reading a diff. They are complementary and neither replaces the other.
</Aside>

## The QA lane

`cckit qa` reads one block, `qa`, written by the `qa` module interview (`/kit-add qa`, or
`scripts/kit-add.sh qa --answers <file>`). cckit records how the project's review stack boots; it
does not guess a boot command and does not write a boot script. The walkthrough is the
[QA lane guide](/qa-lane/).

```json
{
  "modules": ["qa"],
  "qa": {
    "command": "pnpm dev:stack",
    "ports": [{ "env": "WEB_PORT", "base": 3000 }, { "env": "API_PORT", "base": 4000 }],
    "readiness": [{ "env": "WEB_PORT", "path": "/" }, { "env": "API_PORT", "path": "/health" }],
    "route": "/dashboard",
    "credentialEnv": ["QA_EMAIL", "QA_PASSWORD"]
  }
}
```

| Key | Default | What it does |
| --- | --- | --- |
| `qa.command` | *(required)* | The command that boots the whole review stack, run from the worktree root. Without it `cckit qa up` refuses with exit `2`. |
| `qa.ports` | *(none)* | `{env, base}` per service: the port env var the command honours and its base port. A lane sets each `env` to `base + slot × worktree.devPortStride`. Empty refuses the launch. |
| `qa.ports[].env` | — | Env var name, matching `^[A-Za-z_][A-Za-z0-9_]*$`. |
| `qa.ports[].base` | `3000 + position` | Base port. The interview derives it when the answer names no port. |
| `qa.readiness` | *(none)* | `{env, path}` per service that must answer before the lane counts as usable. Empty refuses the launch: with no probe, launched cannot be told from usable. |
| `qa.readiness[].env` | — | Which service to probe, named by its port variable from `qa.ports`. |
| `qa.readiness[].path` | `/` | Path requested on that port. |
| `qa.route` | `/` | Route `cckit qa open` lands on when the PR body carries no `QA route:` line. Must start with `/` and hold no spaces. |
| `qa.credentialEnv` | `[]` | **Names** of the env vars holding the test account's credentials. A value is refused at interview time and never stored. Recorded only: no verb reads it yet. |

- Two `qa.ports` bases that differ by a multiple of the stride, fewer than 40 strides apart, are
  refused before anything launches — two lanes would share a port.
- A lane port that another process already listens on refuses `cckit qa up` with exit `2`. The
  first lane's ports are the bases themselves, so pick bases no dev server of yours uses.
  `cckit qa stop` leaves a listener the lane did not launch running unless it is given `--force`.
- `captain.mergePolicy.requireQa` is the one other key the lane uses; see
  [Holding merges for a QA pass](#holding-merges-for-a-qa-pass).
- `qa` is a receipt stage, not an agent stage: it is in the [stage receipt](#stage-receipts)
  vocabulary and not in `agents.stages`, because a person records it.

## Worktree bootstrap

`cckit start <issue>` and `cckit effort start <N>` make a fresh worktree runnable before you touch it:
they copy the gitignored `.env.local*` files and project ids a new checkout can't inherit, assign a
per-worktree dev `PORT` per app, and install dependencies — `node_modules` is per-worktree, never
shared. Every step is best-effort: a hiccup prints and moves on, it never fails the start.

### Where the install runs

The install step decides from **your project**, in this precedence — the first rule that applies wins,
and the ones below it are never consulted:

<Steps>

1. **`worktree.installPaths` is set** → install in exactly those directories, and only those. The
   root and workspace checks below are skipped entirely; `[]` means *install nothing*.

2. **Otherwise, the worktree root** — but only when its `package.json` declares at least one
   dependency (in `dependencies`, `devDependencies`, `optionalDependencies` or `peerDependencies`),
   **or** it is a workspace root **with at least one member** (`pnpm-workspace.yaml` whose
   `packages:` lists a pattern, or — in `package.json` — a non-empty `workspaces` array or a
   non-empty `workspaces.packages` array). A workspace root holds its members' deps, so the
   install there is real work. A `workspaces` object whose `packages` list is empty counts as
   memberless, however many other keys it carries.

3. **Otherwise nothing** — the start prints `no dependencies declared — skipping pnpm install`.

</Steps>

Rule 3 is the point. A root manifest with no dependencies has nothing to resolve, but pnpm would
still write an empty `pnpm-lock.yaml` (`importers: { .: {} }`) — a file that then trips the
[captain's own lockfile policy floor](#captain-merge-policy) and holds the PR for human review. cckit
itself is exactly this shape: a published bash CLI with zero dependencies whose only Node project is
`docs-site/`.

The "at least one member" clause in rule 2 matters for the same reason: `packages: []`,
`"workspaces": []` and `"workspaces": {"packages": []}` all *look* like workspace roots but declare
nothing, so installing at them lands right back on the empty lockfile.

### Installing somewhere other than the root

When your Node project lives in a subdirectory, name the directories under `worktree.installPaths` in
the config file resolved above:

```json
{
  "worktree": {
    "installPaths": ["docs-site"]
  }
}
```

| Key | Default | What it does | Env override |
| --- | --- | --- | --- |
| `worktree.installPaths` | *(unset — fall through to rule 2)* | Worktree-relative directories to run `pnpm install` in. Wins over rules 2–3; `[]` installs nothing. | — |
| `worktree.devPorts` | `[]` | `{path, base}` per app: the per-worktree dev `PORT` written into that app's `.env.local`. | — |
| `worktree.devPortStride` | `10` | Distance between one worktree's port block and the next. Every app's `base` must sit inside one stride-wide window. | — |
| — | install on | Skip the dependency install entirely for one invocation. | `KIT_WT_INSTALL=0` |
| — | `10` | Seconds `cckit start` waits for the port-slot ledger lock before allocating unserialized. | `_WT_LOCK_WAIT` |

<Aside type="caution" title="A written port is not always a used port">
cckit writes `PORT=` into each app's `.env.local`, but that only takes effect **if the app reads the
file**. A script like `next dev -p ${PORT:-3003}` is expanded by the npm-script shell, which never
reads `.env.local` — so the value is inert for it and each worktree falls back to the same default.

cckit doesn't depend on this: anything cckit launches itself gets its port passed explicitly. The
`.env.local` write is a convenience for apps that do read it. If you start a dev server **by hand**
in a worktree, check which port you actually got — and if you want the assignment to apply, read it
in the script yourself:

```json
"dev": "sh -c 'P=$(grep -m1 ^PORT= .env.local 2>/dev/null | cut -d= -f2); exec next dev -p ${P:-3003}'"
```

Extract just `PORT` — don't `source` the file. A dotenv file is not a shell script, and sourcing it
lets the shell reinterpret any secret containing `$`, a backtick or a quote.
</Aside>

<Aside type="note" title="Slots are allocated under a lock, not hashed">
A worktree's block is `base + slot * stride`, and the **slot** comes from a ledger at
`<git-common-dir>/kit-portslots.tsv` — one row per issue, reclaimed once its worktree is gone. The
offset used to be `issue % 40`, which hands two issues 40 apart byte-identical ports.

Choosing a slot reads the ledger and writes it back, so the whole transaction runs under an
exclusive lock: the directory `kit-portslots.tsv.lock`, since `flock(1)` is absent on a stock macOS.
Unserialized, eight concurrent `cckit start` runs produced as few as 3 distinct ports out of 24.

A lock held by a live process is waited out for `_WT_LOCK_WAIT` seconds; one untouched for a minute
is treated as abandoned and broken, so a process killed mid-allocation cannot wedge later starts.
When the lock cannot be taken at all, `cckit start` warns and allocates unserialized rather than
refusing to run.
</Aside>

<Aside type="caution" title="installPaths cannot leave the worktree">
Entries are worktree-**relative** and validated for containment: an absolute path, or one that climbs
out with `..`, or a symlink pointing outside the tree, is refused with a message and skipped. A
worktree sits three levels under the primary checkout, so an escaping entry would otherwise run pnpm
in a shared checkout — writing `node_modules` and a lockfile into another session's working tree.
</Aside>

<Aside type="tip" title="Nothing is hardcoded">
The kit carries no project's layout. Both keys are config, and the fallback is a question asked of
*your* `package.json` — so a repo with real root dependencies still gets its install, unchanged.
</Aside>

## PR conventions

`cckit pr` follows the repo's PR convention, set under `pr` in the config file:

```json
{
  "pr": {
    "titleStyle": "issue-title",
    "orchestratorSection": true
  }
}
```

| Key | Default | What it does |
| --- | --- | --- |
| `pr.titleStyle` | `conventional` | `conventional`: a Conventional Commits title derived from the issue's kind label, which release-please and a commitlint gate read. `issue-title`: the issue title, verbatim. `cckit effort pr` follows the same key: `conventional` gives `type(scope): name [#N]` and refuses a title that fails commitlint; `issue-title` gives `[Role] [#N] name`, unchecked. |
| `pr.orchestratorSection` | `false` | `true` opens the PR body with a two-line `## For the orchestrator` section: the issue number and what to review. |

## Light tasks

[`cckit task`](/light-tasks/) tracks work without GitHub issues. Two keys, both optional:

```json
{
  "tasks": {
    "source": "file",
    "dir": "tasks"
  }
}
```

| Key | Default | What it does |
| --- | --- | --- |
| `tasks.source` | `file` | Where task records live. `file` is the one source cckit ships: one tracked file per task. Another name `<name>` loads `scripts/lib/task-source-<name>.sh`; a name with no such file is refused with exit 1. `KIT_TASKS_SOURCE` overrides it per invocation. |
| `tasks.dir` | `tasks` | The tracked directory the `file` source keeps tasks in, relative to the project root. An absolute path, or one that climbs out of the project, is ignored with a warning and `tasks` is used. `KIT_TASKS_DIR` overrides it per invocation. |

Keep the directory tracked: the list is shared through git, so a gitignored directory would leave
every task a local draft.

## Effort WIP limit

`cckit effort start` refuses to start a **new** effort once too many are already in progress. The
counted set is the efforts whose `effort/<N>-<slug>` branch exists — a local head **or** a branch
origin has right now, read with `git ls-remote` rather than the cached `refs/remotes`. Set the
ceiling in the config file resolved above:

```json
{
  "effort": {
    "wipLimit": 3
  }
}
```

| Key | Default | What it does | Env override |
| --- | --- | --- | --- |
| `effort.wipLimit` | `2` | How many efforts may be in progress before `cckit effort start` refuses a *new* one. **At** the limit refuses; only strictly under it starts. `0` refuses every *ordinary* start — a forced one still runs. A value that is not a non-negative integer is ignored with a warning and the default `2` is used. | `EFFORT_WIP_LIMIT` |
| — | gate on | Start anyway, past the limit. Flag or env — either alone is enough. | `--force`, or `KIT_FORCE=1` |
| — | origin queried | Skip the `git ls-remote` origin query; count local heads + cached `refs/remotes` instead. An unreachable origin falls back to the same cached refs, warns once on stderr, and the start proceeds. | `EFFORT_WIP_REMOTE=0` |

Resolution order, first non-empty wins: `EFFORT_WIP_LIMIT` in the environment →
`KIT_EFFORT_WIP_LIMIT` (what `load_kit_config` exports from `effort.wipLimit`) → `effort.wipLimit`
read straight from the config file → the built-in default `2`.

The check runs before the base-branch fetch, the branch, the worktree and the bootstrap, so a
refusal leaves no branch, no worktree and no board change. It is not read-free: the gate queries
origin, and a `<slug>` argument was resolved before it, which can run `gh issue list`. Re-running
`cckit effort start` on an effort that is *already* in progress is never gated — it adds no WIP.
`cckit start <issue>` (a plain task worktree) has no WIP limit. Full behaviour:
[Only so many efforts at once](/efforts-and-waves/#only-so-many-efforts-at-once).

## Integrations

This section is the reference. For the list of tools and the steps to switch one on, start at
[Integrations](/integrations/).

An optional third-party tool is described by one JSON file, `integrations/<id>.json`, checked
against `integrations/integration.schema.json`. A descriptor carries a label, the config key that
turns the tool on, a detect command, install candidates tried in the order written, a verify
command, a docs link and an attribution block whose `affiliated` field is a boolean.

An optional `appliesWhen` block says where the tool can work. It holds two kinds of condition, and
every one present must hold:

| Condition | Judges | Holds when |
| --- | --- | --- |
| `anyExtension` | the repo | At least one file ends in a listed extension. Inside a git work tree the file list is git's tracked and unignored files. |
| `platform` (`os`, `arch`) | the machine | Each field present equals `uname -s` / `uname -m` verbatim, e.g. `{"os":"Darwin","arch":"arm64"}` for Apple silicon. |

Three optional fields carry what an installer needs beyond the candidate list:

| Field | What it does |
| --- | --- |
| `install[].bootstrap` (`manager`, `run`) | How to get that candidate's manager, e.g. `brew install uv`. Run only when **none** of the descriptor's managers is on `PATH`; a machine that already has any of them is never bootstrapped. |
| `detect.bin` | The binary's name when `detect.run` does not start with it (a `command -v <bin>` probe, for a tool whose own flags are slow to answer). |
| `afterInstall` | The one step left to the user after a successful install, shown once in the install report. |
| `config.default` | `true` makes the integration ON in a project whose config does not hold the key; only an explicit other value (`false`, or `"none"` for a named key) turns it off, and `cckit add <id> --set enable=no` writes that value. The doctor reports a missing default-on tool as a skip row: no install, no failure. Omitted: off until `cckit add <id>`. |
| `rules` | Rule templates (`templates/rules/<name>.md`) that `cckit add <id>` copies into the project's `.claude/rules/` when the integration is switched on. |
| `wire.kept` | Tool features left **on** although a flag could decline them, each mapped to the test behind that decision. The counterpart of `wire.declined`; it never reaches the command line. |

Four descriptors ship:

| Descriptor | Config key | Candidates, in order | Bootstrap | Applies |
| --- | --- | --- | --- | --- |
| `integrations/mempalace.json` | `memory.enabled` | `pipx install mempalace`, then `uv tool install mempalace` | `brew install pipx` | any repo, any machine |
| `integrations/mlx-lm.json` | `local.enabled` | `uv tool install mlx-lm`, then `pipx install mlx-lm` | `brew install uv` | `Darwin` + `arm64` only |
| `integrations/graft.json` | `codeGraph.provider` = `graft` | `npm install -g @nanonets/graft`, then `pnpm add -g @nanonets/graft` | none | a repo with at least one file in a language Graft indexes |
| `integrations/lavish.json` | `reviewPages.enabled`, **on by default** | `npm install -g lavish-axi`, then `brew install node` (only when neither `lavish-axi` nor `npx` is on `PATH`) | none | any repo, any machine |

The config key names a capability, never the vendor: `<capability>.provider` whose value names the
tool, or an existing `<capability>.enabled` switch. A key containing the descriptor's own id is
refused by the validator.

| Key | Default | What it does |
| --- | --- | --- |
| `codeGraph.provider` | *(unset — off)* | Which integration provides code-graph retrieval, as its descriptor's `config.value` names it. `graft` switches on `integrations/graft.json`. Unset or `none`: no code graph. |
| `memory.enabled` | `false` | `true` switches on `integrations/mempalace.json`: `cckit doctor` installs the MemPalace CLI and checks the wake-up header and session-start hook. |
| `local.enabled` | *(unset — off)* | `true` switches on `integrations/mlx-lm.json`: `cckit doctor` installs the runtime on Apple silicon and starts `mlx_lm.server` on `local.port` (default `8080`) with `local.model`. |
| `local.port` | `8080` | The port `mlx_lm.server` listens on. |
| `local.model` | `mlx-community/Qwen3-8B-4bit` | The model the server loads. The first start downloads it. |
| `reviewPages.enabled` | *(unset — on)* | `false` turns [review pages](/review-pages/) off: plans, decisions and grills print to the terminal. `integrations/lavish.json` sets `config.default: true`, so the unset key is on. |
| `reviewPages.answers` | *(unset)* | `issue` or `file`: where `cckit page answer` writes. Unset: a comment on the issue when `github.repo` is set and `--issue` is given, else a file. |
| `reviewPages.answersDir` | `docs/answers` | Directory, relative to the repo root, for answers written as files. |
| `local.dismissed` | *(unset)* | The `kitVersion` at which the "local layer down" session notice was dismissed. Written by `cckit doctor --dismiss-local`. |

`bash scripts/lib/integrations.sh --validate` checks every descriptor and prints one
`<id>: <field>: <problem>` line per problem; `--list` prints the ids; `--applies <id> [dir]` exits
0 when the tool can work on the repo at `dir`.

### Switching one on: `cckit add`

`cckit add` with no name lists every descriptor in `integrations/`, each marked `on` or `off` for
this project and flagged when it does not apply here, followed by the modules. It exits 0
when the registry is empty. `cckit add --llm` prints the same list as one JSON object:
`{"integrations":[{id,label,summary,key,enabled,applies}],"modules":[{id,label}]}`.

`cckit add <id>` asks one question, derived from the descriptor, and on `yes` sets the
descriptor's `config.key` to its `config.value` (boolean `true` when the descriptor names none).
That is the only key it changes. The file it writes is the project config: a root
`cckit.config.json`, else `.claude/kit.config.json`, found by walking up from the directory.
A descriptor that lists `rules` also gets each rule copied into `.claude/rules/` beside that
config. A rule file already there is kept, so an edited rule survives a second run and a deleted
one is restored.

| Case | What happens |
| --- | --- |
| `--set enable=no`, or answering no | Nothing is written. It does not switch off an integration that is already on. |
| The key already holds the ON value | No write; the file stays byte-identical. |
| An `appliesWhen` condition does not hold (no file with a listed extension, or the wrong machine) | Declined with the conditions named. Exit 0, nothing written. |
| No project config found | Exit 1. Run `cckit init` first; `add` does not create a config for an integration. |
| The descriptor fails the schema | Exit 1 with the `<id>: <field>: <problem>` lines. Nothing written. |
| `KIT_DRY_RUN=1` | Prints the config diff, the rule files it would write, then the install plan (each candidate in order, and whether its manager is on `PATH`) and the wire command. Nothing written, nothing run. |

`cckit add <id>` installs nothing: it records the choice, and the next `cckit doctor` run does the
install. `cckit add software` is the module form of the same verb
and writes this directory's `.claude/kit.config.json`. In Claude Code the `kit-add` skill drives
the same verb; the typed-only `/kit-add` command it replaces is gone.

### Installing one: the shared runner

`scripts/lib/integration-install.sh` is the one place an integration is installed from. It runs
only commands the descriptor names, and applies four rules in this order:

| Rule | What happens |
| --- | --- |
| The descriptor's `detect.run` exits 0 | Status `present`. Nothing runs, so a second run is a no-op. |
| `KIT_DRY_RUN=1` | Status `dry-run`. The plan is printed: each candidate in order, whether its manager is on `PATH`, whether consent is recorded, and the wire command. Nothing runs. |
| No consent recorded for this integration | Status `no-consent`, exit 0. Nothing runs. `KIT_ASSUME_YES` is not consent. |
| Otherwise | If no candidate's `manager` is on `PATH`, the candidates' `bootstrap` commands are tried in order until one puts a manager there. Then the `install` candidates are tried in the order written. One whose `manager` is not on `PATH` is skipped. The first whose command exits 0 **and** leaves the tool detectable wins (`installed <manager>`); later candidates never run. If none does: `failed`, exit 1. |

Consent is one `install:<id>` line in `.cckit/consent`, the gitignored state file shared by every
worktree of the repo. `cckit doctor` records it when you approve installs in that run — `--fix`
(alias `--yes`), or a yes at its terminal prompt. `bash scripts/lib/integration-install.sh
--consent <id>` records it without running the doctor.

`uv` and `pipx` put binaries in `~/.local/bin`, which is often not on `PATH` in the session that
ran the install. Every detect, install and wire command therefore runs with `$HOME/.local/bin`
appended to `PATH`, so a tool installed there is found without opening a new shell.

A descriptor's optional `wire` step runs in the project directory under the same dry-run and
consent rules. Each key of `wire.declined` is appended to `wire.run` as a flag; the values are
the reasons and never reach the command line. A candidate marked `"resident": false` (an `npx`
form that leaves no binary) is judged by its exit code alone.

`--plan <id> [dir]`, `--install <id> [dir]`, `--wire <id> [dir]` and `--wire-command <id>` are the
script's CLI forms.

### What `cckit doctor` does with them

For every descriptor whose config key is on, the doctor prints one row under **Integrations**. It
holds no tool's recipe: the row is the runner's status line.

| Run | Tool missing | Row | Exit code |
| --- | --- | --- | --- |
| `cckit doctor --fix`, or yes at the prompt | Consent is recorded, then the runner installs | `installed via <manager> (<path>)` | 0 |
| No terminal and no `--fix` | Nothing installs, no consent is recorded | `missing — nothing installs without your yes: cckit doctor --fix` | 1 |
| `--dry-run` or `--no-install` | Nothing installs, no consent is recorded | `missing — <first candidate>` | 1 |
| Any, on a machine or repo where `appliesWhen` does not hold | Nothing installs | a skip row naming the condition | unchanged |

With the key off or unset there is no row and the exit code is what it would be without the
descriptor. `cckit init` runs the doctor with `--yes`, so setup keeps installing.

Before this, a doctor run with no terminal and no flag installed the MemPalace CLI and mlx-lm
without asking. It now reports them missing; pass `--fix` in automation that relied on the install.

### The monthly recipe check

A descriptor hardcodes upstream facts: a package name, an installer's flags, a binary's name. The
gate (`scripts/check.sh`) never installs anything, so it cannot see one of them drift.
`.github/workflows/integrations-check.yml` does: at 06:17 UTC on the 1st of every month, and on a
manual `gh workflow run integrations-check.yml`, it runs `bash scripts/integrations-check.sh --yes`
on two clean runners, `ubuntu-latest` and `macos-15` (arm64, the one platform
`integrations/mlx-lm.json` applies to).

The script holds no recipe. Every command comes from the descriptor and runs through the shared
runner, in a scratch git repo that also holds the consent for the run.

| Step | What runs | A failure means |
| --- | --- | --- |
| `validate` | The descriptor against `integrations/integration.schema.json` | The descriptor is malformed |
| `platform` | `appliesWhen.platform` against `uname` | Nothing: a mismatch is a `skip` line, exit code unchanged |
| `install` | The runner's candidate walk | No candidate left the tool detectable |
| `detect` | `detect.run` | The tool installed under another name |
| `verify` | `verify.run` | The binary no longer loads, or its flag changed |
| `wire` | `wire.run` plus the `wire.declined` flags, when the descriptor has a wire step | A flag was renamed or the tool refuses the repo |

The first failing step ends that descriptor and prints `FAIL <id>: <step>: <detail>` followed by
the step's captured output. The script exits 1 when any descriptor failed. The workflow then opens
an issue titled `Integration recipe check failed on <runner>` carrying the last 120 log lines and
the run URL; while that issue is open, a later failing run comments on it.

Without `--yes` the script installs nothing: it validates each descriptor, prints its install
plan and exits 0. `bash scripts/integrations-check.sh --yes graft` checks one descriptor. Pass
`--yes` on a throwaway machine only, because the tools install onto the machine that runs it.

What the check does not exercise:

- Install candidates after the one that worked. The runner stops at the first.
- A `bootstrap` command, on a machine that already holds one of the managers.
- `uninstall` and `build.deep`.
- The install recipe of a tool already on the machine: the line reads
  `skip <id>: install: already on this machine`, and `detect`, `verify` and `wire` still run.
- An `appliesWhen.anyExtension` predicate. The scratch repo is seeded with one file of the first
  listed extension, because the recipe is under test and no repo is.

### Code-graph retrieval: Graft

`cckit add graft` sets `codeGraph.provider` to `graft` and writes `.claude/rules/code-retrieval.md`.
The rule routes each kind of code question to a Graft verb:

| Question | Verb |
| --- | --- |
| Where is X handled? | `graft ask "<task>"` |
| Every occurrence of a pattern | `graft grep "<regex>"` |
| The API of one file | `graft skeleton <file>` |
| What breaks if I change X? | `graft callers <symbol> -d 2` |
| Orient in an unfamiliar repo | `graft map` |
| What does my diff reach? | `graft blast --base origin/<base>` |

The rule's fallback is a hard rule: with no `graft` binary, no `graft/` directory, or a file in a
language Graft does not index, the agent searches with Grep/Glob as before and reports nothing. A
missing graph changes no exit code.

Graft has no shell grammar, so in a repo of only `.sh` files `cckit add graft` declines (exit 0,
nothing written). The extension list is `appliesWhen.anyExtension` in the descriptor, read from
`@nanonets/graft` 0.18.0.

| Step | Who runs it | Command |
| --- | --- | --- |
| Install | `cckit doctor --fix` | `npm install -g @nanonets/graft`, then `pnpm add -g @nanonets/graft` |
| Wire into the repo | you | `graft init --agents claude --no-statusline --no-global` |

No cckit verb runs the wire step yet; the doctor prints the command after it installs.
`KIT_DRY_RUN=1 cckit add graft` prints both steps without running either.

npm is first because the pnpm install does not run on darwin/arm64 with Node 22: it exits 0, and
`graft --version` then dies with `No native build was found` loaded from `tree-sitter-kotlin`.

The two declined flags and the one kept feature are recorded in the descriptor:

| Feature | Decision | Why |
| --- | --- | --- |
| Statusline (`--no-statusline`) | off | cckit ships its own, and a project-level `statusLine` hides a user-level one. |
| Out-of-repo writes (`--no-global`) | off | Without the flag `graft init` also writes `~/.claude/settings.json`, `~/.claude/helpers/graft-hooks.cjs` and `~/.claude.json`. |
| Hooks | **on** | Tested with graft 0.18.0 on a `.claude/settings.json` that already held one hook entry on each of SessionStart, UserPromptSubmit, PostToolUse and Stop: all four survived unchanged and first in their event, and a second `graft init` left the file identical. |

`GRAFT_MERGE_TEST=1 bash scripts/lib/integration-install-test.sh` re-runs that hook test against
the installed `graft`, in a throwaway repo and `HOME`.

`graft init` writes `.claude/settings.json` (hook blocks, four `permissions.allow` entries,
`footerLinksRegexes`), `.claude/helpers/graft-hooks.cjs`, `.claude/helpers/graft-statusline.cjs`,
`.claude/skills/graft/SKILL.md`, `.mcp.json`, `.gitignore`, `.ignore`, and builds `graft/`.
`graft uninstall -y --no-global` removes them.

Graft is by NanoNets / Trail (MIT); cckit is not affiliated with either. Its README reports 46%
fewer tool calls, 42% fewer tokens and 54% → 66% on SWE-bench Verified. Those are the vendor's
numbers and cckit has not reproduced them. Per the same README, Graft makes a daily npm version
check and one batched anonymous usage ping; `graft telemetry disable` or `DO_NOT_TRACK=1` turns
the ping off. `graft build --deep` is the one command that calls an LLM, and cckit never runs it.

An upgrade (`/kit-update`, which runs `scripts/init.sh --upgrade`) over a config with `codeGraph.provider` set re-adds a missing
`code-retrieval.md`, and a regenerated `CLAUDE.md` carries the line that points at it. A fresh
`cckit init` writes neither: the integration is switched on by `cckit add`, never by an init flag.

## Model endpoint for the effort judge

`cckit effort close` asks a model to grade the closed effort (a difficulty and a score written into
the local metrics record). The hosted path is an OpenAI-compatible endpoint read from three
environment variables. cckit stores none of the values; the config can only **name** the variables,
so a project that already exports its own does not have to rename them:

```json
{
  "model": {
    "urlEnv": "ACME_LLM_URL",
    "modelEnv": "ACME_LLM_NAME",
    "tokenEnv": "ACME_LLM_KEY"
  }
}
```

| Key | Default env var | What the variable holds | When it is empty |
| --- | --- | --- | --- |
| `model.urlEnv` | `CCKIT_MODEL_URL` | Base URL. The judge POSTs to `<value>/chat/completions`. | The hosted judge is skipped; the local model is tried if it is enabled. |
| `model.modelEnv` | `CCKIT_MODEL` | Model name sent in the request and recorded as the judge's model id. | The literal `default` is sent. |
| `model.tokenEnv` | `CCKIT_MODEL_TOKEN` | Bearer token. | No `Authorization` header is sent. |

Each key is independent: name one and the other two keep their defaults. A named variable replaces
the default one — with `model.urlEnv` set, `CCKIT_MODEL_URL` is not read. A value that is not a
shell identifier (letters, digits and `_`, not starting with a digit) is ignored with a warning on
stderr and the default name is used.

## Effort plan source

`cckit effort plan` reads the open efforts from GitHub: one listing call, then one `blocked_by` call
per effort. A project that already keeps a local snapshot of that data can name an executable that
prints it, and the plan calls that instead:

```json
{
  "effort": {
    "planSource": "tools/effort-rows.sh"
  }
}
```

| Key | Default | What it does | Env override |
| --- | --- | --- | --- |
| `effort.planSource` | unset — GitHub is read | Path to an executable that prints the open-effort rows. A relative path resolves against the project root (the directory holding `cckit.config.json`, or the parent of `.claude/` in the scaffolded layout). | `EFFORT_PLAN_SOURCE` |

The source is called as `<source> <owner/repo>` with the project root as its working directory, and
writes to stdout:

| Line | Meaning |
| --- | --- |
| `number<TAB>flow<TAB>ctx<TAB>title` | One open effort. An empty `flow` is shown as `—`; an empty `ctx` as `?`, which weighs the same as `M`. |
| `number<TAB>flow<TAB>ctx<TAB>title<TAB>blockers` | The same, with its blockers: a comma-separated list of issue numbers (`241,257`; a leading `#` is accepted). |
| `# age: <text>` | Optional. How old the data is, in the source's own words (`2h`, `synced 09:14`). Printed verbatim. |

Any other line starting with `#`, and any line whose first column is not a number, is ignored.

The plan falls back to GitHub, with a one-line warning on stderr, when the source is not executable,
exits non-zero, or prints no rows. A source that answers needs neither `gh` nor `jq`; the fallback
needs both.

Every plan prints a `source:` line under its header:

```text
  source: planSource tools/effort-rows.sh · age 2h
  source: GitHub (acme/shop)
  source: GitHub (acme/shop) — planSource tools/effort-rows.sh failed (exit 3), fell back
```

Resolution order, first non-empty wins: `EFFORT_PLAN_SOURCE` in the environment →
`KIT_EFFORT_PLAN_SOURCE` (what `load_kit_config` exports from `effort.planSource`) → GitHub.

## Effort close hooks

`cckit effort close` runs two optional project hooks. Both are paths to an executable; a relative
path resolves against the main checkout. cckit ships neither.

```json
{
  "effort": {
    "preCloseHook": "scripts/pre-close.sh",
    "knowledgeIngestHook": "scripts/ingest-effort.sh"
  }
}
```

| Key | Called as | When | On failure | Env override |
| --- | --- | --- | --- | --- |
| `effort.preCloseHook` | `<hook> <effort#> <sub#…>`, cwd = the effort worktree | Before the snapshot and the merge | A non-zero exit refuses the close; the hook's output is printed and nothing is written. A configured hook that is missing or not executable refuses too. | `KIT_EFFORT_PRE_CLOSE_HOOK` |
| `effort.knowledgeIngestHook` | `<hook> <effort#> <trace-dir>`, cwd = the main checkout | After the merge, the closes and the worktree cleanup | Non-fatal: the close has already landed. A missing or non-executable hook is skipped with a notice. | `KIT_EFFORT_KNOWLEDGE_HOOK` |

`KIT_FORCE=1` skips the pre-close hook — it is not run — and prints
`pre-close hook '<path>' skipped (KIT_FORCE=1)` on stderr. The same variable overrides the
no-work-trace refusal, so a forced close bypasses both gates.

The sub numbers are the effort's native sub-issues. On a wave-style close (no `effort/<N>` branch
anywhere) there is no effort worktree: the pre-close hook runs from the checkout the close was
invoked in, after every sub is verified closed with a merged PR and before the trace is written.

## Night mode

Night mode runs approved effort waves unattended. The `kit-autopilot` skill reads the owner's
**night grant** with `scripts/night-grant.sh`, then launches the Workflow script
`scripts/night-run.mjs`; the Workflow runtime enforces the grant's token budget. In a project that
installed cckit as a plugin both scripts live under `${CLAUDE_PLUGIN_ROOT}/scripts/`.

The grant is one comment on the plan parent issue:

````markdown
<!-- night-grant -->
Tonight: run the two approved waves. I accept the lockfile floor.

```json
{ "budget": "+2000k", "waves": [[12], [15]], "waivers": ["lockfile"], "stopCommand": null }
```
````

**Only the owner's grant counts.** A grant sets the budget, the waivers and a shell `stopCommand`,
and anyone can comment on a public repository. `night-grant.sh read` therefore keeps a marker
comment only when GitHub reports its `author_association` as `OWNER`, or its author is
`github.owner` or a login in `night.grantors`. The latest of those wins; a marker comment from any
other author is ignored and named on stderr. With no owner grant the read exits 1.

The optional `night` object in the config file resolved above adds to the grant:

```json
{
  "night": {
    "floors": { "auth-dep": "the auth library version" },
    "neverWaivable": ["auth-dep"],
    "gate": "pnpm typecheck && pnpm lint",
    "grantors": ["a-maintainer"],
    "refuseLabels": ["hold"]
  }
}
```

| Key | Default | What it does |
| --- | --- | --- |
| `night.floors` | none | Extra always-human floors, name → what a diff must touch to trip it. Added to the base floors `lockfile`, `auth`, `security-code`, `security-prose`, `workflows`, `cost`, `secret`. A tripped floor parks the effort unless the grant waives it by its exact name. |
| `night.neverWaivable` | none | Floor names no grant may waive, added to the base list `workflows`, `cost`, `secret`. |
| `night.gate` | the delegation brief's gate commands | The gate executors and verifiers run, and the final check on the base branch. |
| `night.grantors` | none | Logins allowed to write the grant besides `github.owner` and an `OWNER` commenter. Needed on an organization repository, where no commenter is `OWNER` and `github.owner` is the org. |
| `night.refuseLabels` | none | Labels that hold an effort out of a night run. cckit applies no such label itself. |

What the engine holds in code:

| Rule | Behaviour |
| --- | --- |
| Approval | An effort runs because the owner named its number in the grant's `waves`. No label or body section is required; preflight refuses only a closed issue, an issue without the `effort` label, or one carrying a `night.refuseLabels` label. |
| Width | `effort.wipLimit` efforts at once (default `2`), never more than 4. Every executor runs `cckit effort start`, which refuses a new effort at that limit, so a wider run would only park efforts. Executors are told never to pass `--force`. A parked effort keeps its branch and takes a slot from the rest of its wave; efforts already in progress before the night take slots too. A limit of `0` refuses the grant. |
| Wave order | Waves are dependency-ordered. A wave with any effort parked, refused or skipped ends the run `blocked`, and no later wave starts. |
| Final check | Once every wave merged, the gate runs on the base branch and decides `done` or `blocked`. A `stopCommand` is a separate check after each wave that ends the night early when it exits 0. |
| Waivers | Each waiver must equal one floor name. `"lockfile auth"` and `"*"` are refused when the grant is read. |

`night-grant.sh` finds the config the way every verb does — `$KIT_CONFIG`, else a walk up from the
current directory — so a project's floors and gate apply from any subdirectory.

## Agent profiles

A **profile** is a named agent configuration: which CLI to run, roughly what it costs, under which
permissions, and at which stages.

**cckit never names a model.** A kit that suggests an expensive model in its own config schema
pushes every user toward spending more, which is the opposite of the point. You spell your own
flags in `args`; the only cost signal cckit reads is `tier`, and the cheapest profile is what runs
when nothing else is chosen.

```json
{
  "agents": {
    "stages": ["build", "review", "design", "docs"],
    "profiles": {
      "cheap": {
        "kind": "claude",
        "tier": "low",
        "stages": ["build", "review"],
        "write": true
      },
      "deep": {
        "kind": "claude",
        "tier": "high",
        "permissions": "acceptEdits",
        "stages": ["build"],
        "write": true,
        "contextBudget": 8000,
        "args": ["--model", "<whatever your CLI calls it>"]
      }
    }
  }
}
```

| Key | Default | What it does |
| --- | --- | --- |
| `agents.default` | *the cheapest profile* | Profile used when nothing more specific resolves. **Leave it unset** — the lowest-`tier` profile then wins, so the inexpensive path is the default by construction. Naming a profile that is not declared is a validation error, not a silent fallback. |
| `agents.stages` | `build review design docs` | The stage vocabulary a profile's `stages` are checked against. Env override: `CCKIT_AGENT_STAGES`. |
| `kind` | **required** | The agent CLI to run (`claude`, `codex`, …). The Herdr runtime validates it before any worktree exists. |
| `tier` | `low` | What this profile is expected to **cost** relative to the others: `low`, `mid`, `high`. Unstated means `low` — assuming the cheap end is the safe direction to be wrong in. |
| `args` | `[]` | Extra CLI arguments as an **argv array**, never a shell string, so an argument containing spaces is not re-split. **Your model selection goes here**, spelled the way your CLI spells it. Passed through on both runtimes — Herdr receives the array after its `--`, tmux gets it quoted onto the pane's command line. |
| `permissions` | *(unset)* | Permission/sandbox policy, forwarded to the CLI that implements it and recorded in the stage receipt. |
| `stages` | *(none)* | Stages this profile may run at. **A profile with no `stages` is allowed nowhere** — an unstated permission is not a granted one. |
| `write` | `false` | Whether the profile may write to a branch. One writer owns a branch at a time; review profiles stay read-only until ownership is transferred. |
| `contextBudget` | *(unset)* | Upper bound in **bytes** on the whole prompt the worker receives. See [Bounding a worker's prompt](#bounding-a-workers-prompt). Unset, `0`, or non-numeric means unbounded. |

Validation runs **before** a worktree or pane is created, and refuses on: an undeclared profile, a
profile with no `kind`, a `stages` entry outside the vocabulary, a profile selected for a stage it
does not list, and an `agents.default` that names nothing declared. Each refusal names the profile
and prints what was declared, so the fix does not require reading the source.

### Which profile runs a given issue

Resolution walks four levels, highest first, and stops at the first that supplies a name:

| # | Level | Where it comes from |
| --- | --- | --- |
| 1 | Command override | the flag on this invocation |
| 2 | Issue label | `agent:<profile>` on the issue itself |
| 3 | Parent effort label | `agent:<profile>` on the parent effort |
| 4 | Project default | `agents.default`, or the **cheapest** profile when that is unset |

`scripts/setup-labels.sh` provisions one `agent:<profile>` label per profile the config declares, so
the family stays bounded by the config rather than growing one label per issue.

Two refusals are deliberate, because both would otherwise run an agent nobody chose:

- **Two different `agent:` labels on one issue is ambiguous** and refuses. It does not pick one.
- **The resolved name is validated against the stage before it is returned.** An explicit
  `agent:review` label on a `build` stage is refused, not honoured — so a rc-0 result is always
  launchable and a caller never re-checks.

When nothing resolves at all — no override, no label, no `agents.default` — that is its own distinct
failure, separate from "a profile was named and rejected", so the message can tell you which of the
two happened.

### Bounding a worker's prompt

A headless worker gets one prompt and no chance to ask for more. `contextBudget` caps that prompt in
**bytes**, so a large brief cannot spend the worker's window before it has read a line of code.

The prompt is assembled in four parts, and only one of them competes for the budget:

| Part | Cut? | What it is |
| --- | --- | --- |
| Headless framing | never | there is no human here; work only on this issue; do not read the board |
| Brief metadata | never | worktree, branch, seed freshness, and the gate command — where to work and what must pass |
| Brief sections | **yes** | `## Files this issue owns`, `## Helpers you already have`, `## Standing gotchas`, `## Durable prose` |
| Receipt contract | never | `outcome` · `url` · `gate` · `blocker` · `next stage` |

Sections are dropped **whole**, from the end, and the prompt then says which ones went and how to
read them:

```text
_2 section(s) omitted to fit this profile's contextBudget: Standing gotchas, Durable prose.
Read them with `cckit brief`._
```

Dropping whole sections rather than truncating mid-sentence, and naming the cut rather than making
it silently, are the same decision: **a partial brief has to read as partial.** A worker handed a
brief that looks complete acts as though it is.

The order is not arbitrary — the sections the worker cannot reconstruct come first. What the issue
owns is unrecoverable from anywhere else; the standing gotchas are a rule file the worker can open
on its own.

A budget too small to hold the four uncuttable parts **emits them anyway** and warns on stderr. A
worker that overran a number is recoverable; one with no receipt contract reports in a shape nothing
can parse, and the receipt is the only durable record of the run.

The board and prior conversations are never included, at any budget — including unbounded.

### Stage receipts

A worker's pane is not a record. It dies with the pane, it does not survive a Herdr server restart,
and nothing can query it — and pane history, which might preserve it, is off by default and can
hold secrets, so cckit must never depend on it.

So the worker records its own receipt, through a verb:

```bash
cckit receipt 321 --stage build <<'RECEIPT'
outcome:    pr-open
url:        https://github.com/jeiemgi/cckit/pull/999
gate:       pass
blocker:    none
next stage: review
RECEIPT
```

The stage is one of `build` · `review` · `design` · `docs` · `qa` · `none`. `qa` is the stage
`cckit qa verdict` writes — see [the QA lane](/qa-lane/#record-the-verdict--cckit-qa-verdict).

One JSON file per attempt, under `.cckit/receipts/`, keyed `<issue>-<stage>-<attempt>`. The
directory resolves from the repo's shared git dir, so a receipt a worker writes inside its own
isolation worktree is readable by a captain standing anywhere else.

```bash
cckit receipt list 321          # 321  build   1  blocked
                                # 321  build   2  pr-open
                                # 321  review  1  merged
cckit receipt show 321 build    # the latest attempt's JSON
```

**Every receipt is also posted as a comment on its issue.** `.cckit/` is gitignored and
per-machine, so a receipt that lived only there dies with the clone — and `effort-model.md` opens
with "GitHub is the single source of truth". The local file stays: it is what lets `receipt list`
and `receipt show` answer offline, with no network round trip per read. The comment is the second
copy, not a relocation.

The comment carries an invisible marker keyed to the same `<issue>-<stage>-<attempt>`, so a re-run
**edits that attempt's comment** rather than appending a second one — the same guarantee the local
file gives. A new attempt gets its own comment.

```bash
cckit receipt 321 --stage build --no-remote <<'RECEIPT'   # write the file, post nothing
```

The mirror is best-effort, and the local write has already succeeded before it runs: a failure
warns on stderr and the command still exits 0. `--no-remote`, or `CCKIT_RECEIPT_REMOTE=0`, skips it
outright. One case deliberately does *nothing* rather than degrade — if the comment lookup itself
fails, cckit does not post, because a blind post is exactly how a duplicate record appears.


Alongside the five reported fields, each receipt records the resolved `profile`, its `tier`, where
it was resolved from, and its `permissions` — so a run's effective agent and policy are auditable
after the fact.

**Re-running the verb with the same five values rewrites its own attempt** instead of recording a
second one, which is what makes it safe to retry after an unknown result. A re-run that says
something *different* is a real second try and takes the next number, so neither record is lost.

**A value outside its vocabulary is recorded and flagged, not refused.** Refusing would make two
states look identical:

| What happened | Refuse | Record + flag |
| --- | --- | --- |
| Agent crashed | no receipt | no receipt |
| Agent finished, wrote `outcome: shipped` | *no receipt* | `outcome: shipped` · `invalid: ["outcome"]` |

The first needs the stage re-run; the second has a PR sitting there and just used a word outside
the list. Keeping the value preserves the difference, and `receipt list` shows the flag so a wave
scan cannot miss it. The one hard refusal is a report with **no `outcome:` line at all** — that is
not an odd receipt, it is no receipt.

Nothing is verified against GitHub. The receipt says what the worker reported; the captain already
reads PR state before it merges anything, so checking here would ask GitHub the same question twice
and would break an offline run.

## Identity

cckit asks your name on first run and stores it in `.cckit/identity` (gitignored). Nothing personal is hardcoded; commits use your local git identity.
