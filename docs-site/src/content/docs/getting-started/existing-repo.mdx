A project that has been running for a while already has a layout, a history, and often a
`.claude/` folder somebody copied in by hand. The worry with any new tool is that it will rearrange
all of that. cckit does not: it adds its own config, records the cckit files that are already
there, and leaves everything else where it is.

**What you will have at the end:** the repository set up for cckit, every cckit file in it on
cckit's list of files it manages, and your own code, notes and plans untouched.

**Who does it:** one person with a terminal, or an agent. Every step is a single command, so an
agent can run the whole adoption and report back.

## Steps

Run these in order from inside the repository.

```sh
cckit scan      # 1. what the repository contains, and the state of any cckit files
cckit init      # 2. write the project config and .claude/  (only when there are none)
cckit adopt     # 3. record the cckit files the repository ALREADY has
cckit migrate   # 4. move an old cckit layout to the current one
cckit update    # 5. say whether the project is behind the installed cckit
cckit doctor    # 6. check the tools and the GitHub sign-in
```

<Steps>

1. **`scan`: see where you stand.** It reports the state of the cckit files: `configured` (cckit
   already runs here), `partial` or `claude-only` (some cckit files exist but are not recorded as
   cckit's), or `none` (a repository with no cckit files).

2. **`init`: only when there is nothing yet.** For a `none` repository it writes the config and a
   `.claude/` folder from a profile. Skip it if `scan` says `configured`.
   [Initialize a project](/getting-started/initialize/) covers the questions it asks.

3. **`adopt`: take ownership of files already there.** This is the step for a repository that got
   its cckit files by hand: a copied `.claude/`, an old init, skills a teammate pasted in. The
   files are present, but the **manifest**, cckit's record of which files it owns, does not know
   them, so an upgrade (`cckit init --upgrade`) and the uninstall script (`scripts/kit-remove.sh`)
   will not touch them. `adopt` records each at its current hash. It
   writes no content. Preview it first with `cckit adopt --dry-run`; it never claims your
   `knowledge/`, plans or app code.

4. **`migrate`: fix an old layout.** It moves an old cckit layout to the current one, and running
   it again changes nothing. `cckit migrate --dry-run` prints the moves and writes nothing.

5. **`update`: check the version.** It reports whether the project trails the installed cckit
   version. If it does, follow [Update a project](/getting-started/update/).

6. **`doctor`: confirm the basics.** It checks that the required tools and the `gh` sign-in are in
   place.

</Steps>

<Aside type="note" title="What is the manifest?">
The manifest is cckit's list of which files in your repository it owns and manages. Files outside
it (your app code, your `knowledge/`, your plans) are never touched by an upgrade or by the uninstall script, `scripts/kit-remove.sh`, which
deletes only what the manifest lists.
`adopt` is how you add cckit files that are already present to that list.
</Aside>

## Check it worked

```bash
cckit adopt --check   # lists cckit files not yet recorded; writes nothing
cckit status          # where the project stands
```

`cckit adopt --check` should list nothing. `cckit status` should run without an error; on a fresh
adoption it has little to report, because no work is in flight yet. Then look at `git status`:
the only changes are cckit's own config and files.

## Why it is safe to run

- **It adds; it does not rewrite.** `scan` only reads. `init` writes only its own files:
  the project config (`.claude/kit.config.json`; `cckit.config.json` at the root for a Codex-only project) and `.claude/`. `adopt` records the cckit files you already have, so cckit
  manages them in place and does not duplicate them. No company, framework or repository layout is
  built into cckit.
- **Every step does nothing when there is nothing to do.** The three that touch files (`init`,
  `adopt`, `migrate`) can be previewed with a dry run and never overwrite content they do not own.

## Make the adoption itself an issue

In this process every change starts as an issue. The issue says what and why before any code
exists, and the branch, the pull request and the review all hang off it, so the work can be traced,
reviewed and undone. Adoption can follow the same path: one issue, one branch, one pull request,
with `cckit start <issue>` and `cckit pr <issue> "<summary>"`, and the issue records which of the
six steps applied to this repository.

`cckit start <issue>` takes an issue number, so the branch, the worktree and the pull request each
start from one.

## Troubleshooting

**`adopt` did not pick up a file I expected.** It records only files under `.claude/skills`,
`.claude/rules`, `.claude/agents`, `.claude/commands`, `.claude/hooks`, `.claude/lib`,
`.agents/skills` and `.agents/rules`, plus `.claude/statusline.sh` and `.claude/settings.json`.
`cckit adopt --check` lists the ones not yet recorded and writes nothing.

**I already ran `init` elsewhere.** Running `init` on a repository that is already configured
leaves your existing config in place and does not overwrite it.

**The board looks empty.** That is expected on a fresh adoption: no issues are in flight yet. Start
one with [Take an issue to merged](/development/issue-to-merged-pr/).
