The process does not depend on which agent runs it. A team that works in Codex needs the same
things a Claude Code team gets: the instructions, the rules, the skills and the guards that stop a
commit on the base branch. Codex reads them from different files, so cckit has an adapter that
writes them where Codex looks.

**What you will have at the end:** a repository where Codex follows the same process.
`cckit init --adapter codex` writes `AGENTS.md`, the skills and rules under `.agents/`, and the
guard hooks under `.codex/`. After that, the commands that launch an agent take `--agent codex`.

Steps 1 to 4 are the setup. Steps 5 to 7 are three ways to work once it is in place; stop after
any of them.

## Steps

<Steps>

1. **Preview what the adapter writes.** A dry run prints the plan and writes nothing:

   ```bash frame="terminal"
   cckit init --profile software --adapter codex --dry-run
   ```

   Under `Would write:` you should see `cckit.config.json`, `AGENTS.md`, `.agents/rules/`,
   `.agents/skills/`, `.codex/hooks/`, `.codex/hooks.json` and `.codex/agents/`. A Codex-only
   install writes no `.claude/` directory.

2. **Install it.** Pick the line that matches the repo:

   ```bash frame="terminal"
   cckit init --profile software --adapter codex   # a repo with no cckit yet
   cckit init --upgrade --adapter codex            # a repo that already runs cckit with Claude Code
   cckit init --profile software --adapter both    # a new repo that will use both agents
   ```

   The upgrade form adds Codex and leaves the Claude Code files as they are.

3. **Check the CLI and the hooks.**

   ```bash frame="terminal"
   cckit doctor --agents
   ```

   You should see a `codex` row with the CLI version and a `codex hooks` row reading
   `registered in .codex/hooks.json`. The command makes no network call and exits 1 when the
   Codex CLI is not on `PATH`.

4. **Trust the hooks, then commit them.** Codex skips a project hook until you approve it. Open
   Codex in the repo, run `/hooks`, and trust the entries cckit registered. Then commit `.codex/`,
   `.agents/` and `AGENTS.md` so every worktree cut from the base branch carries them.

5. **Work one issue.** Start Codex in the repo and hand it the loop:

   <div class="cckit-prompt">

   ```text frame="terminal" title="Prompt to paste"
   Read AGENTS.md. Sync the board with cckit and show me what is unblocked. I will pick one issue;
   start it with cckit, work in the worktree it prints, and open the pull request with cckit when
   the project's gate passes. Do not merge.
   ```

   </div>

6. **Run several issues in parallel.** `cckit wave` prints the launch commands for the adapter,
   and `orchestrate` creates one worktree and one Codex session per issue:

   ```bash frame="terminal"
   cckit wave --adapter codex                                # the wave, with Codex launch commands
   cckit orchestrate --agent codex --dry-run <issues…>       # print the launch plan; create nothing
   cckit orchestrate --agent codex --detach <issues…>        # launch, at most 4 at once
   cckit orchestrate --results --wait 3600                   # how each worker ended
   ```

   The dry run prints `DRY RUN - would launch <n> flow(s)` and creates no worktree and no pane.

7. **Run one objective with no terminal.** `cckit autopilot run` starts `codex exec` one round at
   a time and stops on limits checked by cckit, from inside the issue's worktree:

   ```bash frame="terminal"
   cckit autopilot run --agent codex --agent-arg -s --agent-arg workspace-write \
     --objective "make the failing tests pass" --until "<your test command>" --dry-run
   ```

   The dry run prints the command it would start, `'codex' exec --json '-s' 'workspace-write' -`,
   and the limits. cckit adds no permission flag of its own: the sandbox mode is yours to name
   with `--agent-arg`.

</Steps>

## Check it worked

```bash frame="terminal"
cckit doctor --agents
```

It exits 0 and prints a `codex` row with the CLI version and a `codex hooks` row reading
`registered in .codex/hooks.json`. The doctor cannot read whether Codex trusts the hooks. To see
that for yourself, try a commit on the base branch from a Codex session: the guard should refuse
it.

## How it works

Both adapters render from one set of templates, so a rule or a skill says the same thing to both
agents. What differs is where the files go and how hooks are registered: Codex reads
`.codex/hooks.json`, and cckit merges its entries into that file without removing yours.

`export CCKIT_AGENT=codex` makes Codex the default for `orchestrate`, `autopilot` and
`autopilot run`, so `--agent codex` can be left off. The project's stored adapter choice sets the
default for `cckit wave`.

- File by file, what each adapter writes:
  [Install matrix](/install-matrix/#what-cckit-init-writes-claude-code-codex-or-both).
- How the hooks are registered and merged: [Hooks → Codex](/hooks/#codex).
- What is shared and what is not: [Adapters](/adapters/#claude-and-codex-support) and the
  [compatibility inventory](/agent-compatibility/).

<Aside type="caution" title="What is not verified for Codex">
The guard hooks are tested against the event JSON Codex documents, with stub binaries. No live
Codex session has fired them, so treat a Codex guard as unproven until you have seen it block a
commit on the base branch in your own repo. The memory hooks are not installed for Codex: they
read Claude Code transcripts. The full list of limits is on the
[Adapters](/adapters/#claude-and-codex-support) page.
</Aside>

## Troubleshooting

**`cckit doctor --agents` exits 1.** The Codex CLI is not on `PATH` in this shell. Install it, or
open a shell where `command -v codex` prints a path.

**The doctor warns that the Codex hooks are not registered.** `.codex/hooks.json` is missing
cckit's entries. Run `cckit init --upgrade`, the command the doctor names.

**A guard did not fire in Codex.** The hooks are registered and not yet trusted. Run `/hooks` in
Codex and approve them. The doctor can read the registration; it cannot read the trust state.

**A worktree has no `.codex/` directory.** The adapter files were never committed, so the branch
the worktree was cut from does not contain them. Commit them on the base branch.

**The repo already had an `AGENTS.md`.** A fresh init keeps an existing `AGENTS.md`. Pass
`--force` to replace it, or merge the generated content by hand.
