The process does not depend on which agent runs it. A team that works in Codex needs the same
things a Claude Code team gets: the instructions, the rules, the skills and the guards that stop a
commit on the base branch. Codex reads them from different files, so cckit has an adapter that
writes them where Codex looks.

**What you will have at the end:** a repository where Codex follows the same process.
`cckit init --adapter codex` writes `AGENTS.md`, the skills and rules under `.agents/`, and the
guard hooks under `.codex/`. After that, the commands that launch an agent take `--agent codex`.

The Bakery site, the example project of these guides, is here worked in Codex. Each step starts with
the sentence you say to your agent in the chat, then the command it runs.

Steps 1 to 4 are the setup. Steps 5 to 7 are three ways to work once it is in place; stop after
any of them.

### 2 · Install it

<Chat
  title="installing the Codex adapter in the Bakery site"
  say="That looks right. Install the Codex setup and keep the Claude Code files as they are."
  ran="cckit init --upgrade --adapter codex"
  means="The upgrade form adds Codex and leaves the Claude Code files as they are."
>
  I added the Codex adapter and left the Claude Code files untouched.
</Chat>

<Outcomes of="cckit init" title="Which install line fits which repo">

Pick the line that matches the repo:

```bash frame="terminal"
cckit init --profile software --adapter codex   # a repo with no cckit yet
cckit init --upgrade --adapter codex            # a repo that already runs cckit with Claude Code
cckit init --profile software --adapter both    # a new repo that will use both agents
```

The upgrade form adds Codex and leaves the Claude Code files as they are.

</Outcomes>

### 3 · Check the CLI and the hooks

<Chat
  title="checking the Codex CLI and hooks for the Bakery site"
  say="Is Codex installed here, and are the cckit hooks registered for it?"
  ran="cckit doctor --agents"
  means="The command makes no network call and exits 1 when the Codex CLI is not on PATH."
>
  The doctor shows a `codex` row with the CLI version and a `codex hooks` row reading
  `registered in .codex/hooks.json`.
</Chat>

### 4 · Trust the hooks, then commit them

Codex skips a project hook until you approve it. Open Codex in the repo, run `/hooks`, and trust
the entries cckit registered. That step is yours: the doctor cannot read the trust state.

<Chat
  title="committing the Codex adapter files of the Bakery site"
  say="Commit the Codex files so every worktree cut from the base branch carries them."
  ran={["git add .codex .agents AGENTS.md", 'git commit -m "chore: add the cckit Codex adapter"']}
  means="A worktree cut from a branch that lacks these files has no `.codex/` directory."
>
  I committed `.codex/`, `.agents/` and `AGENTS.md`.
</Chat>

### 5 · Work one issue

Start Codex in the repo and hand it the loop:

<Chat
  title="working one Bakery site issue in Codex"
  say="Read AGENTS.md. Sync the board with cckit and show me what is unblocked. I will pick one issue; start it with cckit, work in the worktree it prints, and open the pull request with cckit when the project's gate passes. Do not merge."
  ran={["cckit sync", "cckit start <issue>", 'cckit pr <issue> "<summary>"']}
  means="You pick the issue and Codex does not merge. Merging stays a decision for a person."
>
  I synced the board and listed what is unblocked. Once you pick one, I start it, work in its
  worktree and open the pull request when the gate passes.
</Chat>

### 6 · Run several issues in parallel

<Chat
  title="running three Bakery site issues at once in Codex"
  say="Run the issues I picked in parallel with Codex, one worktree each. Show me the plan first, then launch, and tell me how each one ended."
  ran={[
    "cckit wave --adapter codex",
    "cckit orchestrate --agent codex --dry-run <issues…>",
    "cckit orchestrate --agent codex --detach <issues…>",
    "cckit orchestrate --results --wait 3600",
  ]}
  means="`orchestrate` creates one worktree and one Codex session per issue, at most 4 at once."
>
  I printed the launch plan, launched one Codex session per issue, and waited for the results. The
  dry run prints `DRY RUN - would launch <n> flow(s)` and creates no worktree and no pane.
</Chat>

`cckit wave` prints the launch commands for the adapter, `orchestrate --dry-run` prints the plan,
`--detach` launches, and `orchestrate --results` reads how each worker ended.

### 7 · Run one objective with no terminal

<Chat
  title="running one Bakery site objective with Codex"
  say="Make the failing tests pass, unattended, with Codex. Preview the run first."
  ran={[{
    cmd: 'cckit autopilot run --agent codex --agent-arg -s --agent-arg workspace-write --objective "make the failing tests pass" --until "<your test command>" --dry-run',
    output: "'codex' exec --json '-s' 'workspace-write' -",
  }]}
  means="cckit adds no permission flag of its own: the sandbox mode is yours to name with `--agent-arg`."
>
  I ran the preview. It prints the command it would start and the limits, and starts nothing.
</Chat>

`cckit autopilot run` starts `codex exec` one round at a time and stops on limits checked by cckit,
from inside the issue's worktree.

<Chat

  say="Is the Codex setup healthy?"
  ran="cckit doctor --agents"
  means="It exits 0 when both rows are there. The doctor cannot read whether Codex trusts the hooks."
>
  The `codex` row shows the CLI version and the `codex hooks` row reads
  `registered in .codex/hooks.json`.
</Chat>

To see for yourself that the hooks are trusted, try a commit on the base branch from a Codex
session: the guard should refuse it.

## How it works

Both adapters render from one set of templates, so a rule or a skill says the same thing to both
agents. What differs is where the files go and how hooks are registered: Codex reads
`.codex/hooks.json`, and cckit merges its entries into that file without removing yours.

`export CCKIT_AGENT=codex` makes Codex the default for `orchestrate`, `autopilot` and
`autopilot run`, so `--agent codex` can be left off. The project's stored adapter choice sets the
default for `cckit wave`.

- File by file, what each adapter writes:
  [Install matrix](/install-matrix/#what-cckit-init-writes-claude-code-codex-or-both).
- How the hooks are registered and merged: [Hooks → Codex](/hooks/#codex).
- What is shared and what is not: [Adapters](/adapters/#claude-and-codex-support) and the
  [compatibility inventory](/agent-compatibility/).

<Aside type="caution" title="What is not verified for Codex">
The guard hooks are tested against the event JSON Codex documents, with stub binaries. No live
Codex session has fired them, so treat a Codex guard as unproven until you have seen it block a
commit on the base branch in your own repo. The memory hooks are not installed for Codex: they
read Claude Code transcripts. The full list of limits is on the
[Adapters](/adapters/#claude-and-codex-support) page.
</Aside>

## Troubleshooting

**`cckit doctor --agents` exits 1.** The Codex CLI is not on `PATH` in this shell. Install it, or
open a shell where `command -v codex` prints a path.

**The doctor warns that the Codex hooks are not registered.** `.codex/hooks.json` is missing
cckit's entries. Run `cckit init --upgrade`, the command the doctor names.

**A guard did not fire in Codex.** The hooks are registered and not yet trusted. Run `/hooks` in
Codex and approve them. The doctor can read the registration; it cannot read the trust state.

**A worktree has no `.codex/` directory.** The adapter files were never committed, so the branch
the worktree was cut from does not contain them. Commit them on the base branch.

**The repo already had an `AGENTS.md`.** A fresh init keeps an existing `AGENTS.md`. Pass
`--force` to replace it, or merge the generated content by hand.
