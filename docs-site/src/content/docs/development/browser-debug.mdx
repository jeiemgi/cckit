An agent that changes a web page cannot see the result. It edits the code, the tests pass, and
the button still sits under the header. Finding out normally takes a person: open the browser,
click around, read the console, report back.

`cckit debug` gives the agent its own way to look. It exposes the browser's developer tools as
commands the agent can run and read: a screenshot, an accessibility snapshot, the console log, the
network log, a [Lighthouse](https://developer.chrome.com/docs/lighthouse/overview) report. The
agent checks its own work before it asks you to.

## The tool behind it

The browser layer is [chrome-devtools-axi](https://github.com/kunchenguid/chrome-devtools-axi) by
Kun Chen, a self-contained [Chrome DevTools](https://developer.chrome.com/docs/devtools/) bridge
built for agents. cckit wraps it and detects whether it is available. It adds nothing to the
browser tooling, and the credit for that tooling belongs to its author.

Results come back in [TOON](/agents/#the-verbs-an-agent-uses-most), a compact text format, so a
result takes little room in the agent's context.

<Aside type="note" title="It is optional">
cckit itself is bash. The bridge needs Node and Chrome, so it is not a hard dependency. With
either one missing, `cckit debug` prints how to enable the capability and exits `0`. A run with
nobody watching is never failed by a missing optional tool.
</Aside>

## Use it on a page

**What you will have at the end:** an agent that can take a screenshot of a page, read its
console and act on what it finds.

<Steps>

1. **Check whether it is available.** This runs nothing in the browser:

   ```bash frame="terminal"
   cckit debug --check
   ```

   With Node, `npx` and Chrome present, it reports the capability as available and names the
   command it will use.

2. **Enable the bridge if the check says it is not available.** Install it, or rely on `npx`
   when Node is present:

   ```bash frame="terminal"
   npm i -g chrome-devtools-axi      # or: npx -y chrome-devtools-axi
   ```

3. **Ask the agent to look.** Start your app, then:

   <div class="cckit-prompt">

   ```text frame="terminal" title="Prompt to paste"
   Open the page you just changed with cckit debug. Take a screenshot and read the console.
   Tell me what you see, and fix any error before you report back.
   ```

   </div>

   The agent runs commands of this form:

   ```bash frame="terminal"
   cckit debug <axi-args...>
   ```

   Everything after `cckit debug` is passed to the bridge unchanged. cckit keeps no list of the
   bridge's subcommands; they are documented in the
   [chrome-devtools-axi repository](https://github.com/kunchenguid/chrome-devtools-axi).

</Steps>

## Check it worked

`cckit debug --check` prints `AVAILABLE` and the command it resolved. After step 3, the agent's
reply describes what is on the page and quotes the console, which it could not do before.

## How cckit finds the bridge

`cckit debug` looks for the command in this order:

1. the command named in the `CCKIT_AXI` environment variable
2. `chrome-devtools-axi` on `PATH`
3. `npx -y chrome-devtools-axi`, when Node and `npx` are present

Set `CCKIT_AXI` to use a pinned version or a wrapper script:

```bash
export CCKIT_AXI=<command>
```

## Troubleshooting

**`cckit debug --check` says the capability is not available.** Node, `npx` or Chrome is missing.
Install them and check again. cckit does not fail without them.

**The agent's context filled with output.** Results are compact, and a broad capture such as a
full network log is still large. Ask for one thing: one screenshot, or the console only.

**A subcommand is not recognized.** The subcommands belong to the bridge, not to cckit. Check the
[chrome-devtools-axi documentation](https://github.com/kunchenguid/chrome-devtools-axi).
