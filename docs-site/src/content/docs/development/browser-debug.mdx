Give an agent a token-efficient, scriptable way to debug a web page — screenshots, accessibility snapshots, console and network logs, [Lighthouse](https://developer.chrome.com/docs/lighthouse/overview).

`cckit debug` drives [chrome-devtools-axi](https://github.com/kunchenguid/chrome-devtools-axi) (Kun Chen), which runs a self-contained [Chrome DevTools](https://developer.chrome.com/docs/devtools/) bridge and emits [TOON](/agents/#the-verbs-an-agent-uses-most)-encoded output. TOON is a compact text format, so results stay small in an agent's context.

<Aside type="tip" title="Built on chrome-devtools-axi">
The browser layer is **[chrome-devtools-axi](https://github.com/kunchenguid/chrome-devtools-axi)** by Kun Chen — a self-contained Chrome bridge for agents. cckit only wraps and auto-detects it; all credit for the browser tooling goes there. If it helps you, ⭐ the repo.
</Aside>

<Aside type="note" title="New here? Why this exists">
Debugging a web page normally means a person clicking around a browser. An agent cannot do that. `cckit debug` exposes the same browser tools as plain commands an agent can run and read, so the agent can see what is on the page.
</Aside>

## Optional + auto-detected

cckit is pure bash; axi needs Node and Chrome. So this is **not a hard dependency** — cckit detects it at call time:

- **Node/npx and Chrome present** → `cckit debug` drives axi.
- **Otherwise** → it prints how to enable the capability and exits `0`. An unattended run is never hard-failed by a missing optional tool.

Check availability without running anything:

```bash
cckit debug --check
```

## Enabling it

```bash
npm i -g chrome-devtools-axi      # or rely on `npx -y chrome-devtools-axi` (Node present)
```

Override the command cckit invokes with an environment variable — useful for a pinned version or a wrapper:

```bash
export CCKIT_AXI=<command>
```

## Usage

Everything after `cckit debug` is forwarded verbatim to axi, so cckit does not track axi's subcommands:

```bash
cckit debug <axi-args...>         # passed straight through — see the axi docs for subcommands
```

## Debug a page, step by step

**What you'll set up:** debugging a web page normally means a person clicking around a browser — an
agent can't do that. `cckit debug` exposes the same browser tools (screenshots, accessibility
snapshots, console and network logs, Lighthouse) as plain commands an agent can run and read. Output
is [TOON](/agents/)-encoded, so results stay small in the agent's context.

### Steps

<Steps>

1. **Check availability first.** cckit is pure bash; the browser bridge needs Node and Chrome. Check
   without running anything:

   ```bash frame="terminal"
   cckit debug --check
   ```

   If Node/npx and Chrome are present, `cckit debug` drives the bridge. Otherwise it prints how to


3. **Let the agent drive it.** Everything after `cckit debug` is forwarded verbatim to the bridge, so
   the agent can take a screenshot, read the console, or run Lighthouse and act on the result:

   ```bash frame="terminal"
   cckit debug <axi-args...>         # passed straight through — see the axi docs
   ```

</Steps>

### How it works

`cckit debug` wraps chrome-devtools-axi (by Kun Chen), a self-contained Chrome DevTools bridge for
agents. cckit detects it and forwards to it; it keeps no list of the bridge's subcommands, so args
pass straight through. With Node or Chrome missing, `cckit debug` prints how to enable the bridge and
exits `0`.

<Aside type="tip" title="Pin or wrap the command">
Override what cckit invokes with `export CCKIT_AXI=<command>` — useful for a pinned version or a
wrapper script.
</Aside>

### Troubleshooting

**`cckit debug --check` says it's unavailable.** Node/npx or Chrome is missing. Install Node and
Chrome, then re-check; cckit won't hard-fail without them.

**The agent's context filled with output.** Results are TOON-encoded to stay compact, but a broad
capture (full network log) is still large. Ask for the specific artifact — one screenshot, the
console only — rather than everything.

**A subcommand isn't recognized.** cckit forwards args verbatim to the bridge; the subcommands
are the bridge's, not cckit's. Check the [axi docs](https://github.com/kunchenguid/chrome-devtools-axi).
