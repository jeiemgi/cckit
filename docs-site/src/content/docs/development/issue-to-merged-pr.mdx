A single fix involves more bookkeeping than code. Someone has to make a branch from a current
base, keep the change apart from other work, open a pull request that names the issue, move the
card on the board, close the issue and delete the branch afterwards. Done by hand, one of those
steps gets skipped.

In this guide an agent takes one issue the whole way, and each of those steps is one cckit
command. The agent runs them in order and does not improvise the branch or the pull request.

**What you will have at the end:** one issue closed, its change merged through a reviewed pull
request, and no leftover branch or folder on your machine.

## Steps

<Steps>

1. **Ask for the next ready issue.** You do not name a number. The agent reads the board and
   takes the first issue nothing is blocking.

   <div class="cckit-prompt">

   ```text frame="terminal" title="Prompt to paste"
   Check the board and pick the next issue that's ready. Take it all the way to a merged PR —
   work it on its own isolated branch, keep the change focused, and open the pull request.
   When it's merged, clean up and tell me the PR link.
   ```

   </div>

2. **The agent starts the issue.** It finds the issue, then creates a branch and a worktree for
   it. A worktree is a separate folder with its own copy of the code:

   ```bash frame="terminal"
   cckit next                       # the next unblocked issue and its start command
   cckit start <issue>              # worktree + branch; the board moves to In Progress
   ```

3. **The agent makes the change** in that folder, and nothing else. It runs the project's checks
   until they pass.

4. **The agent opens the pull request.**

   ```bash frame="terminal"
   cckit pr <issue> "<summary>"     # commit, push, open the PR; the board moves to In Review
   ```

   This is where you look at the work. The checks run on the pull request, and you or a reviewing
   agent read the change.

5. **Merge, close and clean up.** Once the review passes, the agent first brings the branch onto
   the current base branch, shows you what the diff deletes and runs the gate again. `cckit merge`
   does not do that for a branch that is behind and has no conflict. The commands are in
   [Land one pull request](/ship/merge-and-close/#land-one-pull-request). Then:

   ```bash frame="terminal"
   cckit merge                      # merge the PR, close its issue, remove the branch and worktree
   ```

   If the pull request was merged another way, such as the button on GitHub, finish by hand:

   ```bash frame="terminal"
   cckit close <issue> "<summary>"  # close the issue; the board moves to Done
   cckit gc --prune --yes           # remove merged branches and their worktrees
   ```

</Steps>

## Check it worked

```bash frame="terminal"
cckit sync      # the issue is no longer in the open list
cckit gc        # the report lists no branch or worktree for it
```

The pull request page on GitHub shows it merged and links the issue.

## How it works

Starting an issue creates an isolated worktree and branch, so the change cannot collide with
anything else you are running. The pull request, the board columns and the branch all carry the
same issue number, and no step wires them together by hand. The board steps apply when the
project uses a GitHub Projects board.

Whether an agent may merge on its own is your decision, not the tool's. By default the agent
stops after opening the pull request. The [Review](/review/) area covers who approves, and
[Merge, close and clean up](/ship/merge-and-close/) covers the last step in detail.

<Aside type="tip" title="One issue, one worktree">
`cckit start` makes the branch and the worktree in one step. The change lives in its own copy of
the repository until the pull request merges. See
[How one change is built](/development/).
</Aside>

## Troubleshooting

**A verb errored.** cckit prints little when a step succeeds. An error means something is off: a
missing dependency, uncommitted changes, a GitHub sign-in that expired. Read the message before
retrying.

**`cckit start` refused the issue.** Another live session already holds it. `cckit claims` shows
which one. See [Many sessions, one repository](/development/many-sessions/).

**The change touched more than the issue.** Keep the worktree to the one issue. If the scope
grew, split it into an [effort](/project-management/break-a-feature-into-an-effort/) with
sub-issues.

**`gc` did not remove the branch.** `gc --prune` removes a branch only once its pull request has
merged and its issue is closed. Finish the merge and the close first, then run cleanup.
