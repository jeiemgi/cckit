Building is the part of the process where several agents touch the same repository at the same
time. Two of them editing one folder overwrite each other's files, and git has no lock that stops
it. A change made straight on the shared branch reaches everyone before anyone has looked at it.

An agency avoids both with one habit: every piece of work gets its own copy of the code, and it
comes back as a pull request that someone reviews. cckit runs that habit for you. This area shows
how one change travels from an issue to a pull request, and how many travel at once without
colliding.

## The path of one change

<GitHubCycle client:only="react" />

Read it left to right. An **issue** says what to do. A **branch** gives the work a private place
to happen. The work becomes a **pull request**, and **review** either merges it or sends it back.

<Steps>

1. **Issue.** A short note of one thing to do. Its number follows the work the whole way through.

2. **Start.** `cckit start <issue>` makes a branch and a worktree for that issue, cut from a
   freshly fetched base branch. A worktree is a second folder on your disk holding its own copy of
   the code, so this work cannot disturb anyone else's.

3. **Work.** The agent makes the change inside that folder and runs the project's checks until
   they pass.

4. **Pull request.** `cckit pr <issue> "<summary>"` commits, pushes and opens the request. It
   links the request to the issue with a `Closes` line.

5. **Review.** Automated checks run, and a person or an agent looks at the change. If it is good
   it merges into the base branch. If not, it comes back and the work returns to step 3. How that
   decision is made is the [Review](/review/) area; merging and tidying up is
   [Ship](/ship/merge-and-close/).

</Steps>

<Aside type="tip" title="You do not type these by hand">
An agent runs each step. Read this page to know what is happening behind the commands.
</Aside>

## Why every change gets its own copy

One issue, one branch, one worktree, one pull request. The rule buys three things:

- **Nothing collides.** Each agent writes in its own folder, so several can build at once on
  one machine.
- **Nothing lands unseen.** The base branch only changes through a pull request. A hook blocks an
  agent's commit made directly on the base branch.
- **Everything is traceable.** The branch name, the pull request and the board all carry the
  issue number, so you can go from a line of merged code back to the request that asked for it.

One exception is deliberate. An [effort](/project-management/efforts-and-waves/) is a larger goal
with several sub-issues, and it ships as one branch and one pull request for all of them.

What still needs care when several sessions share one repository is on
[Many sessions, one repository](/development/many-sessions/).

## Who does the building

The agents that write code come from the profile you chose at setup. The `software` profile
installs a backend agent (API, data model, server logic), a frontend agent (everything the user
sees and touches), a devops agent (pipelines and deployment) and a tech lead (toolchain and
architecture decisions), alongside QA and security. The `minimal` and `automation` profiles
install a generalist instead.

Three other roles shape a build without writing it:

- **The designer** answers every visual question before the frontend agent writes it. See
  [Design](/design/).
- **The captain** is not an agent. It is whoever drives a batch of work to merged: the command
  `cckit watch --merge`, or a session you told to run an approved plan.
- **You** pick the work, approve the plan and decide what merges.

Every role and what it owns is on [The team](/philosophy/the-team/).

## Which tools plug in

cckit adopts tools for building and writes none of them. Each one is optional, and cckit works
without it.

| Tool | What it gives the agent | How you reach it |
| --- | --- | --- |
| chrome-devtools-axi | screenshots, console and network logs of a web page | [`cckit debug`](/development/browser-debug/) |
| Graft | an index that answers where code lives and what calls it | [`cckit add graft`](/development/code-graph/) |
| mlx-lm | a local model that shortens a long file before it is read | [`cckit digest`](/development/local-model-digest/) |
| tmux or Herdr | one terminal pane per parallel agent | [`cckit orchestrate`](/development/waves/) |

mlx-lm runs on Apple silicon only. The agent itself is Claude Code or Codex. GitHub is reached through the `gh` command. The full
list of optional tools, with who makes each one, is on [Integrations](/integrations/).

## The commands

For one change:

| Step | Command |
| ---- | ------- |
| See the board | `cckit sync` |
| Find what is next | `cckit next` |
| Start the work | `cckit start <issue>` |
| Open the request | `cckit pr <issue> "<summary>"` |
| Close an issue that needed no change | `cckit close <issue> "<reason>"` |

For many at once:

| Step | Command |
| ---- | ------- |
| Propose the next batch of unblocked issues | `cckit wave` |
| Launch one agent per issue | `cckit orchestrate <issues…>` |
| Check and merge the finished requests | `cckit watch --merge` |
| See which session holds which issue | `cckit claims` |

Every flag is in the [CLI reference](/cli-reference/).

## The pull request carries its own proof

A pull request should show that the checks passed, not claim it. cckit ships a helper,
`pr_attach_evidence` (`scripts/lib/pr-evidence.sh`), that attaches the output as a comment after
the request opens: the build log, the typecheck log, a screenshot of the working screen. A
reviewer, person or agent, can then trust the result without running everything again.

Each piece of evidence gets its own comment, named by its caption: one for `build`, one for
`typecheck`, one for a screenshot. Attach again and cckit updates that same comment in place, so
a request that took ten pushes shows one current build log and not ten stale ones.

<Aside type="caution" title="Evidence never breaks your work">
By default, a comment that fails to post prints a warning and the run continues. A caller that
needs the evidence to exist asks for the opposite with `--strict` or `PR_EVIDENCE_STRICT=1`, and
the failure stops the run. Either way the failure is printed and never reported as success.
</Aside>

Image evidence has one limit. GitHub has no supported way to upload a file to a comment from the
command line, so a screenshot is referenced by its path, with instructions. Drag it into the
comment box yourself, or host the file, set `KIT_EVIDENCE_URL_BASE`, and cckit embeds it.
