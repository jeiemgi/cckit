A plan with twelve issues does not have to take twelve turns. Some of those issues wait on
others, and the rest are ready now and touch different files. Working the ready ones one after
another wastes the time an agency saves by putting several people on a project.

The risk in doing them together is collision: two agents in one folder, or two agents pushing to
one branch. A wave is how cckit runs the ready work at the same time and keeps every agent in its
own copy of the code.

<CopilotFanout client:only="react" />

## What a wave is

An **effort** is a goal broken into many issues. Some issues block others, so they cannot all
start at once. A **wave** is the set of issues that are unblocked right now: everything ready to
be worked in parallel.

`cckit wave` looks at your open efforts, works out that set, and writes a **brief**: one task per
issue, each scoped to its own isolated worktree so the parallel work cannot collide. It runs
nothing itself. It hands the brief to the agent, and the agent does the work.

## Who does what

- **You** decide that a wave runs, and you can read the brief first.
- **The driving agent** is the session you are talking to. It reads the brief and starts the
  workers.
- **The workers** are one agent per issue. Each implements its issue in its own worktree and opens
  a pull request.
- **The captain** is `cckit watch`, a process and not an agent. It checks the pull requests the
  workers opened and merges the clean ones.

The tools underneath are the agent runtime (Claude Code or Codex) and, when cckit launches the
workers itself, a terminal multiplexer: tmux by default, or Herdr with `--runtime herdr`. cckit
builds neither.

## How the three parts fit

- **One wave → many agents.** The brief lists each unblocked issue as a self-contained task. The
  driving agent starts one worker per task — how depends on the runtime, see
  [Dispatch per runtime](#dispatch-per-runtime). They run **at the same time**, in **separate
  worktrees**, each implementing its issue and opening a pull request.
- **The captain gates and merges.** The *captain* is `cckit watch` — one long-running process that
  steers the whole wave. It checks every open pull request the subagents opened; the clean ones —
  tests passing, no conflicts — get merged; the rest are reported with what to fix.
- **Merging unblocks the next wave.** Closing this wave's issues frees the ones that depended on
  them. Re-run `cckit wave` and it proposes the next set.

## One turn of the loop

<Steps>

1. **Propose the wave** — `cckit wave` reads the board, finds the issues unblocked right now, and
   writes the brief: one worker task per issue, each in its own worktree.

   ```sh
   cckit wave
   ```

2. **Fan out** — the agent starts one worker per issue from that brief. They run in parallel, each
   implementing its issue and opening a pull request.

3. **Gate + merge** — the **captain** (`cckit watch`, the process that steers the wave) checks every
   open pull request. The clean ones are merged; the rest are reported with what to fix.

   ```sh
   cckit watch --merge
   ```

   If you have configured [a review stage](/config-and-permissions/#the-agent-review-stage), a PR
   the captain would merge goes to a reviewer first and waits for its verdict — one extra turn of
   the loop, not a separate command.

   A person can review the running app the same way: the [QA lane](/review/qa-lane/) brings one stack up
   per lane, and with `captain.mergePolicy.requireQa` set the captain holds a PR until
   `cckit qa verdict pass` is recorded against its current head.

4. **Advance** — merging unblocks the next wave. Re-run `cckit wave` and the loop repeats until
   there's nothing left to propose.

</Steps>

<Aside type="tip" title="Why 'captain'?">
The workers are a fleet, each one in its own worktree, opening its own pull request. The
**captain** is the one process watching over all of them: `cckit watch` polls every pull request,
merges the ones that are ready, and names the ones that are not.
</Aside>

<Aside type="note" title="Why a brief, not a launcher">
cckit emits the plan as instructions and the agent enacts it. In Claude Code that keeps the work
inside the agent's own tools — Task subagents, worktrees, background runs — instead of a separate
process you can't see.
</Aside>

## Dispatch per runtime

A brief has two layers. The **wave data** — which issues are in wave 0, their `ctx` size, and one
prompt per issue — is the same for every runtime; the prompt names no agent. The **dispatch
wording** — how this runtime starts the workers — is chosen per adapter.

| | Claude Code | Codex |
| --- | --- | --- |
| How a worker starts | a Task subagent with `isolation: "worktree"`, in the background | `cckit orchestrate --agent codex --detach <issues>` — one Codex session per issue |
| Who creates the worktree | Claude Code | cckit (`cckit start`, called by `orchestrate`) |
| How results come back | the subagent's one-line return | `cckit orchestrate --results` |

```sh
cckit wave                    # dispatch wording for the project's stored adapters
cckit wave --adapter codex    # or name it: claude | codex | both
cckit wave --llm              # wave data only, as TOON — identical whichever adapter you name
```

Without `--adapter`, the brief follows the `adapters` stored in the project config (`CCKIT_ADAPTER`
overrides it); a project that selected both gets both dispatch sections.

The Codex brief sends the wave through `orchestrate` because cckit has not verified an isolation
mode for Codex subagents. Fanning a wave out as subagents of one Codex session would put several
writers in one checkout, which is the corruption a worktree per writer exists to prevent.

## Collecting results

`cckit orchestrate` creates the worktree for each issue, skips an issue whose `blocked_by` is still
open, launches at most `--cap` workers, and records how each one ended. On tmux the pane runs the
agent under `scripts/wave-worker.sh`, which keeps the agent in the foreground of the pane and
writes its exit to cckit's shared state directory.

```sh
cckit orchestrate --detach --cap 2 <issues…>
cckit orchestrate --results --wait 600      # add --llm for JSON
```

```text
orchestrate: results for session 'orchestrate'
  #11     failure      rc 3    tmux/codex  task/11-parse-flags
  #12     interrupted  rc 137  tmux/codex  task/12-render-table
```

| Result | Meaning |
| --- | --- |
| `success` | the agent process exited 0 |
| `failure` | it exited 1–128 |
| `interrupted` | it died on a signal (exit above 128), the wrapper caught `HUP`/`INT`/`TERM`, or the record still says `running` and its pid is gone on the host that wrote it — a killed pane cannot write a final state, so the dead pid is the evidence |
| `launched`, `running` | not finished |
| `untracked` | Herdr started the agent, so cckit has no exit status to collect |

`--results` exits 0 when every worker succeeded, 1 when any failed or was interrupted (or the
session has no records), and 3 when none failed but some are unfinished.

Two limits. A result is how the **process** ended, not whether the work is right: an interactive
agent you quit normally exits 0 whatever it did. What the worker reports about its own work is the
[stage receipt](/config-and-permissions/#stage-receipts) — a separate record. And the three values
are produced by `scripts/orchestrate-test.sh` with a stub agent under both launch kinds; no live
Claude Code or Codex session is part of that test.

## One writer per branch

Git refuses to check one branch out in two worktrees. That says nothing about two agent processes
driving the branch cckit just handed them — a second wave launched onto a branch a live worker is still pushing, or a re-run of `orchestrate` over an issue
whose pane is already open.

So `orchestrate` takes a **lease** on every branch in the wave before it starts a single pane. A
branch already owned by a live writer refuses the launch, and every lease the wave took is released
— a half-launched wave is worse than none.

```text
orchestrate: #323 — another writer already owns effort/318-agents-run-by-profile-in-herdr;
             not launching this wave
```

The ledger lives with the rest of cckit's local state, so every worktree of the repo reads the same
one. A lease is dropped only on **positive evidence** the holder is gone: its worktree no longer
exists, or the process died on the host that recorded it. A lease written on another machine is
never reclaimed on a process check — process ids are not comparable across hosts, and stealing a
live remote worker's branch is the corruption the lease exists to prevent. It expires on age
instead, after `BO_LEASE_TTL` (default 24 hours), so a decommissioned host cannot wedge a branch
permanently either.


## The commands

| Do this | Command |
| ------- | ------- |
| Propose the wave (fan-out brief) | `cckit wave` |
| Scope to one effort | `cckit wave --effort <N>` |
| Pick the dispatch wording | `cckit wave --adapter <claude\|codex\|both>` |
| Launch a wave in cckit worktrees | `cckit orchestrate <issues…>` |
| Collect how each worker ended | `cckit orchestrate --results` |
| Gate + merge the wave | `cckit watch --merge` |
| Let the captain self-pace | `cckit watch --loop` |
| Machine-readable plan | `cckit plan --llm` |
| Read a recorded verdict | `cckit receipt show <issue> review` |
| Review a lane on a running stack | `cckit qa up` → `cckit qa open` → `cckit qa verdict <pass\|fail>` |
| See every lane's ports, listeners and verdict | `cckit qa lanes` |


Every flag of these verbs is in the [CLI reference](/cli-reference/#plan-and-drive-a-wave).
