Once a plan is split into issues, several of them are ready at the same moment. Taking them one
at a time leaves the rest of the plan waiting on a queue that did not need to exist.

In this guide every ready issue gets its own agent, in its own copy of the code. `cckit wave`
works out which issues nothing is blocking and writes the instructions for the agents. Each agent
opens a pull request. The **captain** (`cckit watch`) then checks those pull requests and merges
the ones that pass. Merging frees the issues that were waiting, and the next wave starts.

**What you will have at the end:** every issue of the wave either merged or reported with what to
fix, and the next wave proposed.

## Steps

<Steps>

1. **Ask the agent to clear the next wave.** You name no issue numbers; the board decides.

   <div class="cckit-prompt">

   ```text frame="terminal" title="Prompt to paste"
   Clear the next wave of ready work. Fan the unblocked issues out so they're worked in parallel,
   then gate the resulting PRs and merge the ones that pass. Advance to the next wave and keep going
   until the board is drained.
   ```

   </div>

2. **cckit fans out the wave and gates the PRs.**

   ```bash frame="terminal"
   cckit wave             # write the instructions for the first wave, one task per issue
   # …the agent spawns one subagent per issue, each opens a PR…
   cckit watch --merge    # gate open PRs, squash-merge the clean ones, advance the wave
   ```

3. **Let it advance.** `watch --merge` merges every PR that passes its gate and moves on to the next
   wave. It stops when there's nothing left unblocked.

</Steps>

## Check it worked

```bash frame="terminal"
cckit sync      # what is still open, and what the merges unblocked
cckit wave      # the next wave, or nothing left to propose
```

A wave is done when each of its pull requests is merged or named in the captain's output with the
reason it was held.

`cckit watch --merge` merges and does not close issues. If `cckit sync` still lists the issue of a
merged pull request, your base branch is not the repository's default branch on GitHub, so GitHub
did not close it: run `cckit close <issue> "<summary>"`.

## How it works

A **wave** is what can run in parallel right now: every issue that nothing is blocking.
Because the issues in a wave touch different files and each runs in its own worktree, their PRs merge
cleanly. `cckit watch` is the captain. It writes no code. It checks the wave's PRs against the gate, merges
only the clean ones, then advances to the wave those merges unblocked. The concept, the two
runtimes and how results are collected are on [Run work in parallel waves](/development/waves/).

<Aside type="tip" title="Waves come from the dependency graph">
You don't assign waves by hand. cckit reads the *blocked-by* links and computes them — see
[Efforts, waves & worktrees](/project-management/efforts-and-waves/).
</Aside>

## Troubleshooting

**A PR didn't merge.** The captain merges only PRs that pass the gate. Read the gate output on that
PR, fix the finding, and re-run `cckit watch --merge` — the rest of the wave isn't held up.

**Two subagents edited the same file.** Those issues shouldn't be in the same wave. Add a *blocked-by*
link so the dependent one lands in a later wave, then re-run.

**The wave brief is empty.** Nothing is unblocked. Run `cckit sync` to see what's blocking the
remaining issues, or start an [effort](/project-management/break-a-feature-into-an-effort/) to create some.
