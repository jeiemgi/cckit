Once agents are useful, you run more than one: a session fixing a bug, another building a
feature, a wave of workers in the background. They all share one repository on one machine, and
git was not designed for that. It has no lock that stops one session from changing the files
another is reading.

Two sessions can collide in three places:

1. **Both start the same issue.** cckit refuses this. `cckit start` records a
   [session claim](#session-claims) per issue and refuses a second live session.
2. **Both write the same branch.** cckit refuses this too. `cckit orchestrate` leases each branch
   of a wave to one writer.
3. **One moves the checkout the other is reading.** No command catches this. It is left to three
   habits, written down in the [`shared-checkout` rule](/rules/#shared-checkout), which every
   profile installs so every agent reads it.

The **primary checkout** is the folder you cloned the project into. Every worktree `cckit start`
creates hangs off it, and it is the one folder every session has in common.

## The three habits

**1. Never move the primary checkout by hand.** No `checkout`, `switch`, `pull`, `merge`, `rebase`,
`reset` or `stash` there. It stays parked on the base branch with a clean tree. The reason: git
has no lock, so one session switching branches there replaces the files under every other session
that is reading them. To look at the current base, fetch and read it without moving anything:

```bash
git fetch origin <base>
git log --oneline -5 origin/<base>
git -C <primary checkout> status -sb     # which branch it is parked on — check, do not assume
```

**2. Work in a worktree, always** — a one-line fix included. One session alone still does not work
in the primary checkout, because it cannot know it is alone.

**3. Call a freshly merged verb from a current worktree.** A `cckit` that is installed from a
clone you also develop in is as old as the branch that clone is parked on. This habit applies only
when
`readlink "$(command -v cckit)"` points into a clone you develop in:

```bash
<worktree on the current base>/bin/cckit <new-verb>
```

Do not pull the primary checkout to get the verb. It catches up at the next close op.

<Aside type="note" title="Where the rule came from">
Two incidents on 2026-07-03, on a repository with several sessions live and the CLI symlinked from
PATH into the primary checkout. A verb merged minutes earlier answered "unknown command", because
the checkout was parked on a branch that predated it. And `cckit update` reported "ahead of plugin
0.3.0", reading the version file of that same stale branch.
</Aside>

## When the primary checkout is already in the wrong place

Do not fix it from a session that did not put it there — another session may be mid-task.

| Situation | Do |
| --- | --- |
| It is parked on a branch that is not the base | find the session that owns that branch and tell it: `cckit msg send <branch> --steer "<text>"` reaches a live session between its tool calls ([Cookbook](/cookbook/#steer-a-parallel-session)) |
| It is on the base but behind | leave it. Read `origin/<base>`; the next close op fast-forwards it |
| You need a verb it does not have yet | habit 3 |
| No other session is live and you own the machine | then moving it is your call, by hand, once |
## Details

The rest of the page is the detail behind each mechanism, for the day something refuses to start.
The session claim is implemented in `scripts/lib/session-registry.sh`, the branch lease in
`scripts/lib/branch-owner.sh`, the shared state directory in `scripts/lib/kit-state.sh`, and the
source install's symlink in `scripts/install.sh`.

### What every session shares

The primary checkout is the first line of `git worktree list`. In the table, `HEAD` is the branch
a folder is on, the index is git's list of staged changes, and the stash stack is where
`git stash` puts work set aside.

| Shared thing | Where it lives | What goes wrong |
| --- | --- | --- |
| The primary checkout's `HEAD`, index and files | the clone directory | one session's `git checkout` or `git pull` replaces the files under every session reading them. Git has no lock for this |
| The stash stack | `refs/stash` in the common git directory | a bare `git stash pop` in one worktree pops an entry another session pushed |
| Branches and remote-tracking refs | the common git directory | harmless to read; `git fetch` from any worktree updates them for all |
| `.cckit/` state — the handoff note, the captain's gate record, branch leases | one per repository, resolved from the common git directory | nothing: it is shared on purpose, so a worktree and the checkout see the same state |
| `cckit` on PATH, **on a source install** | a symlink into a clone | the CLI is as old as the branch that clone is parked on — see the [install matrix](/install-matrix/) |

### What cckit isolates for you

| Mechanism | What it guarantees | What it does not |
| --- | --- | --- |
| `cckit start <issue>` · `cckit effort start <N>` | a worktree and branch of your own, cut from a freshly fetched base | it does not stop you from working in the primary checkout instead |
| The [session claim](#session-claims) `cckit start <issue>` writes | one live session per issue; a second `cckit start` on a claimed issue is refused before any branch or worktree exists | `cckit effort start` writes no claim; it has its own WIP limit |
| `cckit orchestrate`'s branch lease | one writer per branch in a wave; a branch a live writer owns refuses the launch | it covers branches cckit handed out, not a directory |
| The base-branch commit guard (`guard-base-branch-commit.sh`) | an agent's `git commit` is blocked while `HEAD` is on the base | a session that checked out a feature branch in the primary checkout commits freely |
| The raw-git guard (`guard-raw-git-ops.sh`) | `git checkout -b`, `git switch -c` and `git worktree add` on the base are redirected to `cckit start` | a plain `git checkout <existing-branch>` or `git pull` is not inspected |

Nothing in that table stops a session from running `git checkout` or `git pull` in the primary
checkout. That gap is what [the rule's three habits](#the-three-habits) fill.

### Session claims

Two sessions starting the same issue is the collision git does not catch. Git refuses one branch in
two worktrees, but the second `cckit start` found the worktree already there, reported "reusing
worktree", and both sessions wrote one tree. `cckit start` now records a **claim** and checks for
one first.

<Chat
  title="starting an issue that another session already holds"
  say="Start the contact form issue on the Bakery site."
  ran="cckit start <issue>"
  means="The start is refused with exit 1 while another live session holds the issue. `cckit start --force <issue>` starts anyway and takes the claim over."
>
  Another session already holds that issue, so I did not start it. No branch and no worktree were made.
  Do you want me to take the claim over, or pick another issue?
</Chat>

<Chat
  title="listing which sessions hold which Bakery site issues"
  say="Which sessions are working on which issue right now?"
  ran="cckit claims"
  output="(no live claims)"
  means="With a live session, each claim is a row: issue, session pid, start time, branch and worktree."
>
  Nothing is claimed right now, so no other session is working on an issue.
</Chat>

- **The record.** One JSON file per issue at `<git-common-dir>/kit-sessions/issue-<N>.json`:
  issue, branch, worktree, session pid, host, start time. It lives in the shared git dir, so every
  worktree of the repo reads the same set. Nothing is committed and nothing leaves the machine.
- **The check.** It runs before the issue read, the fetch and `git worktree add`. A refusal exits 1
  with the claimant's pid and worktree, and creates no branch and no worktree.
- **Your own claim never blocks you.** Re-running `cckit start <issue>` from the session that
  claimed it, or from inside the claimed worktree, is the same no-op it always was.
- **`--force`** (or `KIT_FORCE=1`) starts anyway and takes the claim over. `KIT_FORCE=1` is also how
  to relaunch `cckit orchestrate` onto an issue another session still claims — orchestrate stops at
  the first refused start.
- **Which pid.** The session, not the command: `KIT_SESSION_PID` when set, otherwise the nearest
  ancestor process that is not a throwaway shell — the agent process, or your terminal's own shell.
  Sub-agents that share one agent process share one session pid and are not told apart; give each
  its own `KIT_SESSION_PID` if they must be.
- **When a claim ends.** Nothing has to release it. A claim is dropped when its pid is dead (or
  alive with a different start time — a reused pid), or when its worktree has been gone for more
  than five minutes. A claim written on another host is never dropped on a pid check.
- **The board is a warning, not a gate.** An issue already In Progress or In Review prints a
  warning and the start proceeds: nothing resets the board when a session dies, so refusing on it
  would block every restart after a crash.
- **Scope.** `cckit start <issue>` only. `cckit effort start` has its own WIP limit and writes no
  claim.

`cckit claims` prints the live claims and writes nothing — a dead claim is hidden there and removed
by the next `cckit start` on that issue.

### The close ops do move it — and that is the reason for habit 1

`cckit merge` and `cckit effort close` check out the base in the primary checkout and pull it, as
their last step:

| Verb | What it runs in the primary checkout | Source |
| --- | --- | --- |
| `cckit merge` | `git checkout <base>` then `git pull --ff-only origin <base>` | `scripts/lib/kit-task-ops.sh:424-425` |
| `cckit effort close` | `git checkout <base>` then `git pull origin <base>` | `scripts/lib/effort-ops.sh:1025-1026` |

They are the one sanctioned mover. With the primary checkout already on the base and clean, the
checkout switches nothing and the pull is a fast-forward, so no session notices. Both lines end in
`|| true`: if a session left the checkout dirty or on another branch, the verb carries on and the
checkout stays stale without a message. The rule binds git you or an agent type; it does not ask
you to avoid the verbs.
