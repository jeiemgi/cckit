The hooks cckit installs, what fires each one, and what it does.

A **hook** is a script the agent runtime (Claude Code or Codex) runs automatically when something
happens — a session starts, a command is about to run, a session ends. cckit scaffolds a few during
`cckit init`, so the right check runs at the right moment without you remembering to run it. Both
adapters get the same scripts; [Codex](#codex) registers them in a different file.

<Aside type="tip" title="You don't do this by hand">
Hooks run on their own — the runtime fires them on an **event**, you never call one. Read this to
know what runs and when.
</Aside>

## Always set up

These are scaffolded for every project.

<div class="cckit-nowrap-2">

| Event | Hook | What it does |
| ----- | ---- | ------------ |
| `SessionStart` | `repo-hygiene.sh` | A read-only report at the start of each session: stale branches, leftover worktrees, and stashes — the same things `cckit gc` cleans up. |
| `SessionStart` | `kit_version_check.sh` | A quiet notice if this project is behind the installed cckit — the prompt to run `cckit update`. |
| `PreToolUse` (Bash) | `guard-base-branch-commit.sh` | Blocks a commit made straight to the base branch, so work always goes through a branch and a PR. |
| `PreToolUse` (Bash) | `guard-raw-git-ops.sh` | Blocks a raw `gh issue create`, `gh pr create`, `gh pr merge`, `gh issue close`, or a branch cut from the base branch, and prints the cckit verb to run instead. The verb adds the item to the board; the raw command does not. `KIT_ALLOW_RAW=1` lets one command through and records it in `<git-common-dir>/cckit/raw-bypass.log`. |
| `PostToolUse` · `UserPromptSubmit` · `SessionStart` · `Stop` | `kit-mail-check.sh` | Delivers [session mail](/cookbook/) (`cckit msg send`): unread mail is injected between tool calls, on the next prompt and at session start. `Stop` is blocked only by `--steer` mail, and a message is consumed when delivered, so it cannot block a second time. Silent when there is no mail. |

</div>

## Set up when you enable a feature

`cckit init` adds these when you turn the matching option on.

<div class="cckit-nowrap-2">

| Event | Hook | Enabled by | What it does |
| ----- | ---- | ---------- | ------------ |
| `PreToolUse` (Bash) | `prepush_gate.sh` | pre-push gate | Runs your project's check (tests, lint) before a `git push`, so a red branch never reaches the remote. |
| `SessionStart` | `kit-local-status.sh` | local model layer | Announces the local model (`mlx_lm.server`) when it's enabled and alive. |
| `SessionStart` | `mempal_session_start.sh` | memory (MemPalace) | Loads this project's saved context (`wake-up --wing`) at the start of a session. The body is wing-scoped; for a wing-scoped identity header, drop in `.claude/mempal-identity.<wing>.txt`. |
| `Stop` | `mempal_save.sh` | memory (MemPalace) | Files the finished session into MemPalace. |
| `PreCompact` | `mempal_precompact.sh` | memory (MemPalace) | A safety-net sweep to memory before the conversation is compressed. |
| `SessionEnd` | `mempal_followup.sh` | memory (MemPalace) | Captures any unsynced work if a session closes abruptly. |

</div>

## `KIT_PR_BASE` in a git pre-push hook

`prepush_gate.sh` is a Claude Code `PreToolUse` hook: it sees a `git push` the agent types, not one a
cckit verb runs. A push made by `cckit pr` or `cckit hotfix` reaches only a real git hook
(`.git/hooks/pre-push`, or whatever `core.hooksPath` names), and both verbs export the branch the PR
targets to it as `KIT_PR_BASE`:

| Verb | `KIT_PR_BASE` |
| --- | --- |
| `cckit pr <issue> "<summary>"` | the integration branch (`.github.baseBranch`) |
| `cckit pr <issue> "<summary>" --base main` | `main` |
| `cckit hotfix <pr\|sha> [--base B]` | `B`, `main` by default |

A gate that diffs the branch against a base should read it, and fall back to its own default when
the push did not come from cckit:

```sh
base="${KIT_PR_BASE:-develop}"
git diff --quiet "origin/$base...HEAD" -- src/ || run_checks
```

A gate that hard-codes the integration branch fails a branch cut from `main`, because it compares
that branch against `develop`.

## Where they live

Hooks are plain scripts under `.claude/hooks/` in your project, registered in
`.claude/settings.local.json`. The raw-git guard and the mail hook are the exceptions: they are
registered in the checked-in `.claude/settings.json`, so they also run in every worktree. They are yours to read and edit — every one is a safe no-op when its
tool isn't installed, so nothing breaks if a dependency is missing.

`cckit init --upgrade` refreshes a hook you never edited: one whose content matches an earlier
version of its template, or the hash recorded in `.claude/kit.manifest.json`. A hook you customized
is kept and listed as **Drifted** in the upgrade summary, for you to compare with the template.
A registration that is already in `.claude/settings.json` is left in the block and position it is
in; the file is rewritten only when a registration had to be added, and the summary then lists it
as modified. The whole path is in [Update a project](/getting-started/update/).

## Codex

`cckit init --adapter codex` (or `both`) renders the same hook templates into `.codex/hooks/` and
registers them in `.codex/hooks.json`. One script serves both runtimes: Codex sends the fields the
scripts read (`hook_event_name`, `cwd`, `tool_input.command`) and documents the same answers — exit
`2` with the reason on stderr blocks a tool, `decision: block` continues a `Stop`, and
`additionalContext` injects text.

| | Claude Code | Codex |
| --- | --- | --- |
| Scripts | `.claude/hooks/` | `.codex/hooks/` |
| Registration | `.claude/settings.local.json` (per checkout) and `.claude/settings.json` (tracked) | `.codex/hooks.json` (tracked) |
| Command path | absolute in the local file, `$CLAUDE_PROJECT_DIR` in the tracked one | `$(git rev-parse --show-toplevel)/.codex/hooks/<name>.sh` — no absolute path |
| Installed | every hook on this page | the "Always set up" hooks, plus `prepush_gate.sh` and `kit-local-status.sh` when enabled |
| Not installed | — | the four memory hooks |

- **Your `hooks.json` is merged, never replaced.** A handler is added only when the event does not
  already run the same command; your own handlers, their order and any other key stay. A merge that
  changes nothing does not rewrite the file. A `hooks.json` that is not valid JSON is left untouched
  and reported; fix it and run `cckit init --upgrade`, which runs at the same version when the
  Codex hooks are unregistered.
- **A hook script you already keep wins.** A fresh init does not overwrite an existing file under
  `.codex/hooks/` unless you pass `--force`. `.codex/config.toml` is never touched.
- **Trust.** Codex skips a project hook until you review and trust it (`/hooks` in Codex), and
  skips it again after it changes. cckit cannot read or grant that trust: `cckit doctor` reports
  whether the hooks are registered, not whether they run. Commit `.codex/` so worktrees have the
  scripts the registration points at.
- **Memory.** `mempal_save.sh` and `mempal_precompact.sh` mine `~/.claude/projects/`, the Claude
  Code transcript store. No Codex transcript format has been validated against `mempalace mine`, so
  the memory hooks are not installed for Codex. See [How cckit uses memory](/memory/how-cckit-uses-it/#under-codex).
- **`cckit remove`** deletes the hook scripts it installed and a `hooks.json` it created and you
  never edited. Entries merged into a `hooks.json` of your own stay; delete those by hand.

What is tested: `scripts/hook-adapter-test.sh` feeds each installed hook the event JSON each
runtime documents and asserts the same result on both — a base-branch commit blocked with a reason,
a worktree commit passing, `--steer` mail blocking `Stop` once, ordinary mail never blocking it, and
each message delivered once in a combined install. What is not: no live Codex session has fired
these hooks. Whether `codex-cli 0.154.0` honours a blocking `PreToolUse` hook, and whether
`codex exec` runs project hooks without an interactive trust step, are unverified — see
[Agent compatibility](/agent-compatibility/).

| Do this | Command |
| ------- | ------- |
| Scaffold the hooks | `cckit init` |
| Check setup is healthy | `cckit doctor` |
| Check the repo health a hook reports | `cckit gc` |
| Act on the update notice | `cckit update` |
