title: Codified review gates
description: Three ratchets that keep an AI reviewer's mechanical findings, a skill listing's context cost, and the instruction files every session loads, from coming back.
---

import { Aside } from '@astrojs/starlight/components';

An AI reviewer finds the same classes of defect over and over, and its findings live in pull-request
threads and die there. `scripts/review-lint.sh` is where the mechanical slice of that stream goes to
stay fixed; `scripts/skill-frontmatter-lint.sh` does the same job for a cost that no reviewer sees at
all — the bytes a skill listing occupies in every session. `scripts/instruction-budget-lint.sh` is the
same idea one level up: `CLAUDE.md` and the rules themselves. `scripts/check.sh` runs all three, and
`cckit init` scaffolds all three into your project. A fourth gate, `scripts/agent-skills-lint.sh`, resolves
every `skills:` entry in the kit's agent templates; it is described [below](#agent-skills-lint--every-agent-skill-resolves).

All three are **ratchets, not caps**: today's offenders are recorded in a baseline and allowed to stay,
but nothing may grow past its recorded size and nothing new may land dirty. Adding a rule therefore
never forces a repo-wide fix.

## review-lint — findings that became a gate

```bash
scripts/review-lint.sh                 # the gate: fails on new or grown hits
scripts/review-lint.sh --report        # every rule's current hit count; never fails
scripts/review-lint.sh --rule <ID>     # every hit for one rule, with context
scripts/review-lint.sh --update        # re-baseline from current hits
```

Rules live in `scripts/review-rules.conf`, one block per rule, each carrying the PR it was earned
from. A rule is either a per-line `pattern` (regex) or a stateful `awk` program for findings that
need to see more than one line — fence parity, for instance, where an unlabelled fence is a defect
only when it *opens* a block.

<Aside type="caution" title="Only the mechanical slice belongs here">
A finding maps to a rule when it is wrong every time it appears, regardless of intent. Doc-vs-code
drift, architectural contracts, and "is this the right abstraction" stay with the reviewer. A noisy
gate is worse than no gate.
</Aside>

### The baseline is TAB-separated

```text
# <RULE>\t<path>\t<count>   (TAB-separated: a path may contain a space)
fence-missing-language	docs/my file.md	1
```

A space-separated baseline written by an earlier version is still read, so upgrading does not turn
the gate red.

## skill-frontmatter-lint — the context budget

Claude Code concatenates a skill's `description` and `when_to_use` into the always-loaded skill
listing. Both sit in every session's context whether or not the skill is ever invoked — only the
`SKILL.md` *body* is lazy. Unbudgeted, those fields grow into second bodies: rent paid on every turn,
and past the harness cap the tail is silently truncated, so an over-long field costs tokens while
delivering nothing.

```bash
scripts/skill-frontmatter-lint.sh              # the gate
scripts/skill-frontmatter-lint.sh --report     # every skill's cost, sorted; never fails
scripts/skill-frontmatter-lint.sh --update     # re-baseline from current sizes
```

The default budget is **500 bytes** per skill (`KIT_SKILL_LISTING_BUDGET`). Both `skills/` and
`.claude/skills/` are measured, so the lint works in the kit's own layout and in the one `cckit init`
scaffolds.

<Aside type="note" title="Bytes, not characters — the locale is pinned">
`${#s}` counts characters under a UTF-8 locale and bytes under `C`/`POSIX`, and skill descriptions
are full of em-dashes and `·`. A baseline generated under one and checked under the other makes the
ratchet fire on skills nobody touched — this repo's UTF-8 baseline reported 15 false "grown" skills
under `LC_ALL=C`, and CI only looked green because `ubuntu-latest` happens to export `LANG=C.UTF-8`.

The lint therefore pins `LC_ALL=C` and measures bytes. Every environment can produce a byte count,
and no locale has to be installed to reproduce a number. An em-dash costs the three bytes it occupies.
</Aside>

## agent-skills-lint — every agent skill resolves

A `skills:` entry that names nothing fails silently: the agent loads, answers, and has fewer skills
than its frontmatter lists. A rename is how it happens — `templates/agents/pm.md` kept listing
`task-sync`, `task-new` and `task-close` after the kit shipped them as `kit-task-*`, so all three of
the PM agent's lifecycle skills were dead.

```bash
scripts/agent-skills-lint.sh           # the gate: fails on any unresolved entry
```

It reads the frontmatter `skills:` key of every `templates/agents/*.md` (block list or inline
`[a, b]`) and accepts an entry that is one of:

| Form | Resolves against |
| --- | --- |
| a skill the kit ships | `skills/<name>/SKILL.md` |
| a skill the kit scaffolds | `templates/skills/<name>/SKILL.md` |
| another plugin's skill | the `plugin:skill` form, e.g. `agent-skills:context7` |
| a third-party bare name | a line in `scripts/agent-skills-external.txt` |

Anything else is reported as `<file>:<line>: <entry>` and fails `scripts/check.sh`.

`scripts/agent-skills-external.txt` is the list of **optional** skills: names an agent template
lists that come from a third-party skill pack or from the harness (`deep-research`, `impeccable`,
the `gsap-*` and `n8n-*` sets). An agent scaffolded into a project without one of them runs without
that skill. A name that is both in that file and shipped by the kit fails the lint, so the list
cannot keep describing a kit skill as third-party.

Unlike the two ratchets above, this lint has no baseline — every entry resolves or the gate is red —
and it is **not** scaffolded by `cckit init`: it checks the kit's own agent templates. A
`plugin:skill` entry is accepted on its form alone; the lint cannot see another plugin's skills.

## instruction-budget-lint — what every session loads

Claude Code loads every `CLAUDE.md`, and every `.claude/rules/*.md` that has no `paths:`
frontmatter, into every session whatever the task. It warns at startup once those files pass a
combined 150k characters; over the limit they still load, and its docs say adherence drops. A
project adds rules one decision at a time, so the resident set grows with no single commit to blame.

A rule that covers one kind of file opts out of the resident set by declaring when it loads:

```markdown
---
paths:
  - "src/components/**/*.tsx"
---
```

```bash
scripts/instruction-budget-lint.sh              # the gate
scripts/instruction-budget-lint.sh --report     # every file's bytes and lines, resident and path-scoped; never fails
scripts/instruction-budget-lint.sh --summary    # one line: the resident total and the three largest files
scripts/instruction-budget-lint.sh --update     # re-baseline from current sizes
```

The gate holds two limits, both in the baseline when exceeded:

| Limit | Default | Override | Baseline row |
| --- | --- | --- | --- |
| Resident total — `CLAUDE.md`, `CLAUDE.local.md`, `.claude/CLAUDE.md`, and every rule without `paths:` | 150000 bytes | `KIT_INSTRUCTION_BUDGET` | `@resident <bytes>` |
| Any one instruction file, resident or path-scoped | 200 lines | `KIT_INSTRUCTION_MAX_LINES` | `<path> <lines>` |

`--report` prints the path-scoped rules as their own block with a byte total: what those rules would
add to every session if their `paths:` were removed. `cckit status` and `cckit doctor` print the
`--summary` line, so the number is seen before the startup warning is.

Two ways to bring the resident total down, and they pair:

- **Scope it.** Give a rule about one surface a `paths:` list. Globs resolve from the directory that
  holds the rule's `.claude/`, so a session started in the main checkout that edits inside
  `.claude/worktrees/<wt>/` needs the `.claude/worktrees/*/apps/**` form next to `apps/**`.
- **Split it.** Keep a short rule resident and move the reference material to a `knowledge/` doc the
  rule points at.

Do not scope a behavioural routing rule ("send every design question to the designer agent"): it
would not load until a matching file had already been read. The rules `cckit init` scaffolds from a
profile are cross-cutting and stay unscoped; `react-annotate.md`, written by `/kit-annotate`, ships
scoped to `**/*.tsx` and `**/*.jsx`.

<Aside type="caution" title="What the number leaves out">
The lint measures bytes with `LC_ALL=C`, for the reason in the note above; bytes are never fewer
than characters, so it reaches the limit no later than Claude Code does. It does not follow `@path`
imports inside a `CLAUDE.md`, and it does not count `CLAUDE.md` files in subdirectories or in
`~/.claude`. `paths:` is detected as a top-level frontmatter key on line 1's block; the globs are
not evaluated.
</Aside>

## Baselines are seeded once

`cckit init` seeds each baseline the first time it scaffolds the lint, so a fresh project starts green
and only *new* defects fail. It never regenerates an existing baseline — that would silently
re-grandfather whatever drifted since the last upgrade.

Seeding sets `KIT_LINT_WALK=1`, which forces the filesystem walk instead of `git ls-files`.
Scaffolding usually lands in a repo that already has commits, so the kit's freshly written files are
untracked and invisible to the index; without the walk the baseline comes out empty and the gate goes
red on your first commit of the scaffold.

Each lint reports its own baseline path, which is how `init.sh` finds it:

```bash
scripts/review-lint.sh --baseline-path             # scripts/review-lint-baseline.txt
scripts/skill-frontmatter-lint.sh --baseline-path  # scripts/skill-frontmatter-baseline.txt
scripts/instruction-budget-lint.sh --baseline-path # scripts/instruction-budget-baseline.txt
```

A freshly scaffolded project's instruction-budget baseline already lists two rules: the shipped
`effort-model.md` (205 lines) and `naming-and-ids.md` (202) are over the 200-line limit, so they are
grandfathered and may shrink but not grow.

## All three self-disable

`review-lint` exits 0 when there is no rule table; `skill-frontmatter-lint` exits 0 when there is no
`skills/` or `.claude/skills/` directory; `instruction-budget-lint` exits 0 when there is no
`CLAUDE.md` and no `.claude/rules/`. Shipping them to every project is safe.
