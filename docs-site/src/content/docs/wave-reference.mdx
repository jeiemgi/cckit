[Run work in parallel waves](/development/waves/) is the loop. This page is the detail behind
three parts of it.

## Dispatch per runtime

A brief has two layers. The **wave data** — which issues are in wave 0, their `ctx` size, and one
prompt per issue — is the same for every runtime; the prompt names no agent. The **dispatch
wording** — how this runtime starts the workers — is chosen per adapter.

| | Claude Code | Codex |
| --- | --- | --- |
| How a worker starts | a Task subagent with `isolation: "worktree"`, in the background | `cckit orchestrate --agent codex --detach <issues>` — one Codex session per issue |
| Who creates the worktree | Claude Code | cckit (`cckit start`, called by `orchestrate`) |
| How results come back | the subagent's one-line return | `cckit orchestrate --results` |

```sh
cckit wave                    # dispatch wording for the project's stored adapters
cckit wave --adapter codex    # or name it: claude | codex | both
cckit wave --llm              # wave data only, as TOON — identical whichever adapter you name
```

Without `--adapter`, the brief follows the `adapters` stored in the project config (`CCKIT_ADAPTER`
overrides it); a project that selected both gets both dispatch sections.

The Codex brief sends the wave through `orchestrate` because cckit has not verified an isolation
mode for Codex subagents. Fanning a wave out as subagents of one Codex session would put several
writers in one checkout, which is the corruption a worktree per writer exists to prevent.

## Collecting results

`cckit orchestrate` creates the worktree for each issue, skips an issue whose `blocked_by` is still
open, launches at most `--cap` workers, and records how each one ended. On tmux the pane runs the
agent under `scripts/wave-worker.sh`, which keeps the agent in the foreground of the pane and
writes its exit to cckit's shared state directory.

```sh
cckit orchestrate --detach --cap 2 <issues…>
cckit orchestrate --results --wait 600      # add --llm for JSON
```

```text
orchestrate: results for session 'orchestrate'
  #11     failure      rc 3    tmux/codex  task/11-parse-flags
  #12     interrupted  rc 137  tmux/codex  task/12-render-table
```

| Result | Meaning |
| --- | --- |
| `success` | the agent process exited 0 |
| `failure` | it exited 1–128 |
| `interrupted` | it died on a signal (exit above 128), the wrapper caught `HUP`/`INT`/`TERM`, or the record still says `running` and its pid is gone on the host that wrote it — a killed pane cannot write a final state, so the dead pid is the evidence |
| `launched`, `running` | not finished |
| `untracked` | Herdr started the agent, so cckit has no exit status to collect |

`--results` exits 0 when every worker succeeded, 1 when any failed or was interrupted (or the
session has no records), and 3 when none failed but some are unfinished.

Two limits. A result is how the **process** ended, not whether the work is right: an interactive
agent you quit normally exits 0 whatever it did. What the worker reports about its own work is the
[stage receipt](/config-and-permissions/#stage-receipts) — a separate record. And the three values
are produced by `scripts/orchestrate-test.sh` with a stub agent under both launch kinds; no live
Claude Code or Codex session is part of that test.

## One writer per branch

Git refuses to check one branch out in two worktrees. That says nothing about two agent processes
driving the branch cckit just handed them — a second wave launched onto a branch a live worker is still pushing, or a re-run of `orchestrate` over an issue
whose pane is already open.

So `orchestrate` takes a **lease** on every branch in the wave before it starts a single pane. A
branch already owned by a live writer refuses the launch, and every lease the wave took is released
— a half-launched wave is worse than none.

```text
orchestrate: #323 — another writer already owns effort/318-agents-run-by-profile-in-herdr;
             not launching this wave
```

The ledger lives with the rest of cckit's local state, so every worktree of the repo reads the same
one. A lease is dropped only on **positive evidence** the holder is gone: its worktree no longer
exists, or the process died on the host that recorded it. A lease written on another machine is
never reclaimed on a process check — process ids are not comparable across hosts, and stealing a
live remote worker's branch is the corruption the lease exists to prevent. It expires on age
instead, after `BO_LEASE_TTL` (default 24 hours), so a decommissioned host cannot wedge a branch
permanently either.
