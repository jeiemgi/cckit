**What you'll understand:** cckit asks before it changes anything in a repo it hasn't worked in
before. This tutorial walks the permission gate — what is asked each time, what is recorded, what always runs
regardless, and what needs a separate confirmation — so you know what an agent driving cckit
can and can't do on your behalf.

## Steps

<Steps>

1. **Start read-only.** Point cckit at the project and inspect state without granting anything:

   ```bash frame="terminal"
   cckit scan --llm    # detect repo root, stack hints, and kit state — reads only
   ```

2. **A config file is proposed before it is written.** `cckit add <module>` and `cckit migrate` show
   what they would change and ask before writing. Preview a run first:

   ```bash frame="terminal"
   KIT_DRY_RUN=1 cckit add software       # prints the proposed config, writes nothing
   cckit init --profile software --dry-run    # prints the scaffold plan, writes nothing
   ```

   That yes is not stored: the next run asks again. `KIT_ASSUME_YES=1` skips the question, and
   still keeps a file you edited.

3. **An install is the one yes cckit records.** A third-party tool (an
   [integration](/integrations/)) installs only after your yes to `cckit doctor` — its prompt, or
   `--fix`. That yes is written as one `install:<id>` line in `.cckit/consent` (gitignored), so it
   is explicit, local and never committed.

   ```bash frame="terminal"
   cckit doctor          # asks before installing anything missing
   cat .cckit/consent    # install:mempalace
   ```

4. **Destructive operations still ask every time.** Force-push, repo creation, and history rewrites
   always require a separate, explicit confirmation — recorded install consent does not cover them.

</Steps>

## How it works

cckit resolves its config by walking up from where you invoke it (nearest wins: `$KIT_CONFIG`, then
`cckit.config.json`, then `.claude/kit.config.json`, then its own fallback) — no org, repo, or path is
hardcoded. Everything it writes about *you* — install consent, identity, your privacy denylist — lands in
`.cckit/`, which is gitignored, so it never leaves your machine. Two things are **not** negotiable:
the secret and privacy guard always runs before anything is committed, and consent never bypasses it.

<Aside type="note" title="Install consent is per-repo, per-tool and local">
An `install:<id>` line in `.cckit/consent` covers that one tool in that one repo, across all of the
repo's worktrees, and stays on your machine. It permits nothing else cckit does. Delete the line to
withdraw it. In a new repo nothing is recorded, so nothing installs until you say yes there.
</Aside>

## Troubleshooting

**`cckit doctor` reports a tool missing and installs nothing.** No consent is recorded for it, and the
run had no terminal to ask in. Run `cckit doctor --fix`, or answer yes at its prompt; the yes is
stored as `install:<id>` in `.cckit/consent`.

**A destructive op keeps asking.** By design — force-push, repo create, and history rewrite always
require explicit confirmation, whatever is recorded in `.cckit/consent`.

**The guard blocked a commit even though I consented.** Consent doesn't bypass the secret/privacy
guard — that always runs. See [stop Claude committing secrets](/tutorials/stop-claude-committing-secrets/).
