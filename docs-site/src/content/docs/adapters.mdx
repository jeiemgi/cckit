cckit is split in two: an agnostic core that does every operation, and per-agent adapters that route a specific agent to it — so any agent can drive cckit while Claude Code gets a native feel.

<Aside type="tip" title="You don't do this by hand">
This is how cckit is built, not something you set up. Read it to understand how any agent can drive
cckit — there's nothing here for you to run.
</Aside>

## The two layers

<div class="cckit-nowrap-2">

| Layer | What it is | Depends on an agent? |
| --- | --- | --- |
| **Core** | Pure bash that owns every operation | No |
| **Adapter** | The thin layer a specific agent uses to discover and call the core | Yes — one per agent |

</div>

Understanding this split is the key to extending cckit to a new agent.

## The agnostic core

The core is pure bash plus the standard toolchain (`git`, `gh`, `jq`, `tmux`). It owns every operation — the GitHub work lifecycle, efforts, worktrees, orchestration, garbage collection — and nothing in it is specific to any agent.

| Path | Role |
| --- | --- |
| `bin/cckit` | The CLI dispatcher — one entrypoint for every verb |
| `scripts/lib/*.sh` | The operations (start/pr/close, effort, worktree, gc, orchestrate, ...) |
| `scripts/*.sh` | The runnable ops (publish, migrate, doctor, digest, ...) |
| `cckit.config.json` | The only source of repo / owner / base-branch — nothing is hardcoded |

The contract the core exposes to agents lives in [`AGENTS.md`](https://github.com/jeiemgi/cckit/blob/main/AGENTS.md): every verb, its arguments, and its `--llm` output. An agent that can run a shell and parse the output can drive the whole lifecycle through this contract alone.

## Adapter one — Claude Code

The Claude adapter is the native layer that makes cckit feel built-in inside Claude Code. It is a thin shell over the core — it adds discovery and ergonomics, never a second copy of an operation.

| Path | Role |
| --- | --- |
| `.claude-plugin/plugin.json` | The Claude Code plugin manifest (install entrypoint) |
| `commands/*.md` | Slash commands (`/kit-*`) that front the core verbs |
| `skills/*` | Skills that teach Claude how and when to run each operation |
| `templates/{agents,hooks,rules,skills,settings}` | What `cckit init` scaffolds into a project's `.claude/` |

Every command and skill ultimately calls a core verb or a `scripts/lib` function. There is one implementation of each operation (in the core); the adapter only routes Claude to it. This is why a fix in the core is a fix for every agent at once.

## Claude and Codex support

[Effort #257](https://github.com/jeiemgi/cckit/issues/257) establishes shared behavior and
release checks for Claude Code and Codex. The [compatibility inventory](/agent-compatibility/)
records current gaps and the acceptance scenarios each adapter must pass. Native Codex support
is being implemented; shell access alone does not establish behavioral parity.

### Choosing adapters at install

`cckit init --adapter <claude|codex|both>` selects what is installed. The default is `claude`.

| | `claude` | `codex` |
| --- | --- | --- |
| Instruction file | `CLAUDE.md` | `AGENTS.md` |
| Skills | `.claude/skills/<name>/SKILL.md` | `.agents/skills/<name>/SKILL.md` |
| Rules | `.claude/rules/*.md` | `.agents/rules/*.md`, listed by path in `AGENTS.md` |
| Specialist agents | `.claude/agents/` | not installed |
| Hooks, guards, statusline, settings | `.claude/hooks/`, `.claude/settings*.json` | not installed |
| Config (when it is the only adapter) | `.claude/kit.config.json` | `cckit.config.json` |
| Ownership manifest (when it is the only adapter) | `.claude/kit.manifest.json` | `.cckit/kit.manifest.json` |

- **One source.** Both instruction files render from `templates/instructions.md.tmpl`, and both
  skill and rule trees from `templates/skills/` and `templates/rules/`. The adapter decides the
  destination directory and which `<!-- IF:ADAPTER_CLAUDE -->` / `<!-- IF:ADAPTER_CODEX -->` blocks
  survive. There is no second copy of an instruction to keep in step.
- **Stored selection.** The config's `adapters` array records the choice. `cckit init --upgrade`
  reads it and never drops an adapter; `--upgrade --adapter codex` adds one, and the adapter already
  installed keeps its files byte for byte. Config and manifest stay where the first install put them.
- **Ownership.** Every adapter file init writes is recorded in the manifest with its hash. An edited
  file reads as modified and is preserved by an upgrade and kept by `cckit remove`.
- **Portable Codex output.** A Codex-only config carries no absolute path, and no generated file
  under `.agents/` or `AGENTS.md` references `CLAUDE_PLUGIN_ROOT`. `scripts/init-upgrade-test.sh`
  asserts both on the `minimal` profile.
- **Doctor.** `cckit doctor` reports the CLI of each selected adapter present or absent;
  `cckit doctor --agents` prints only that, offline, and exits 1 when one is absent.

Limits of the Codex adapter today:

- No hook, guard or specialist agent is installed, so nothing blocks a commit to the base branch in
  a Codex session. `AGENTS.md` says so. Hooks are [#262](https://github.com/jeiemgi/cckit/issues/262),
  specialists [#263](https://github.com/jeiemgi/cckit/issues/263).
- `.agents/rules/` is a cckit location, not one Codex loads on its own. `AGENTS.md` lists each rule
  file so the agent reads the one that applies.
- Shared rules still describe Claude-only mechanics in prose — `mempalace.md` names the hooks in
  `.claude/settings.local.json`, `branch-naming.md` the SessionStart hygiene hook, `design-routing.md`
  the Designer agent. Those passages describe things a Codex-only project does not have.
- Whether a fresh Codex session discovers the installed skills is not verified here; that is the live
  run in [#261](https://github.com/jeiemgi/cckit/issues/261). `.agents/skills` is the directory name
  present in the `codex-cli 0.154.0` binary.
- A fresh init keeps a pre-existing `AGENTS.md` unless `--force` is passed.

## Other adapters

Any other agent (Copilot, Antigravity, a custom model) is a future adapter over the same core. An adapter is whatever that agent needs to discover and call the verbs — at minimum, the agent reads `AGENTS.md` and shells out with `--llm`.

No adapter re-implements an operation; they all target the one core contract. Deeper per-agent adapters (native command palettes, richer prompts) are follow-ups. The agnostic CLI contract is the floor every agent already stands on.

## Why the split

- **One source of truth.** An operation lives once, in the core. No drift between "the Claude way" and "the CLI way".
- **Portable.** The core has no agent dependency, so cckit runs in CI, a cron job, or a bare terminal — not only inside an agent.
- **Open to any agent.** Adding an agent is writing an adapter, not forking the kit.
