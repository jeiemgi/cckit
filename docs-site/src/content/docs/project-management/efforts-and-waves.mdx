Some goals do not fit in one issue. A feature with a schema change, an API and a screen is three or
four changes, and if four agents start on them with no plan, two things go wrong: they edit the
same files, and the one that needs the schema starts before the schema exists.

A team handles this by splitting the goal into steps, writing down which step waits for which, and
running at the same time only the steps that are independent. cckit's units for that are the
**effort** and the **wave**, defined in [How work is written down](/project-management/). This page
is the commands, in the order you use them.

commands as a step-by-step guide with a prompt to paste.

## The six commands, in order

The Bakery site's launch is one goal with four steps: the landing page, the menu page, the opening
hours and a contact form that sends mail. Each window below is one command of the effort.

## 1. Write the plan down

<Chat
  title="writing the Bakery site launch down as an effort"
  say="Launching the site is bigger than one issue. Make it an effort: landing page, menu page, opening hours and a contact form."
  ran='cckit effort new "Launch the bakery site" "Landing page :: hero, three products with prices" "Menu page :: the full list of bakes" "Opening hours :: hours and holidays" "Contact form :: sends mail to the bakery"'
  means="It checks every title before it creates anything, so a refused name creates nothing."
>
  The parent issue holds the goal, the scope, notes for agents and how the work will be verified.
  Each of the four steps is a sub-issue linked to it.
</Chat>

## 2. Declare the order

<Chat
  title="saying the contact form comes after the landing page"
  say="The contact form lives on the landing page, so it has to wait for it."
  ran="cckit effort chain <landing-page-issue> <contact-form-issue>"
  means="GitHub records the blocked-by link, and the issue body gets a matching Depends on line. Skip this when the steps are independent."
>
  The contact form now waits for the landing page.
</Chat>

## 3. See what can run now

<Chat
  title="asking what can run now on the Bakery site"
  say="What can run now, and how many efforts fit in one session?"
  ran={["cckit effort plan", "cckit plan"]}
  means="effort plan packs the open efforts into session-sized batches. plan shows the waves of issues."
>
  Here are the batches and the waves.
</Chat>

## 4. Start the effort

<Chat
  title="starting the Bakery site launch effort"
  say="Start the launch effort."
  ran="cckit effort start <slug|N>"
  means="The effort can be named by its issue number or by its short name, the slug."
>
  The effort has its own branch and its own working folder, set up like any other: env files
  copied, a port of its own, dependencies installed.
</Chat>

## 5. Open the one pull request

<Chat
  title="opening the pull request for the Bakery site launch"
  say="The steps are built. Open the pull request for the whole effort."
  ran="cckit effort pr"
  means="The title carries the effort's number, and the command refuses a title without it."
>
  One pull request is open for the whole effort.
</Chat>

## 6. Close the effort

<Chat
  title="closing the Bakery site launch effort"
  say="The review is done. Close the effort."
  ran="cckit effort close <slug|N>"
  means="cckit merge refuses an effort pull request for the reason below and names this command."
>
  The pull request is merged, the parent and every sub-issue are closed, and the branch and folder
  are removed.
</Chat>

<Outcomes title="What cckit effort close does, in order">

- It saves each step's diff before it merges, so the record of what each sub-issue changed
  survives the merge.
- It merges the pull request, closes the parent and every sub-issue, and removes the branch and
  folder.
- `cckit merge` refuses an effort pull request because its squash skips that snapshot, and names
  this command.

</Outcomes>

A plan page before step 4 is recommended and not required: the `/kit-effort-new` skill shows the
plan as a [page you answer](/project-management/plan-pages/) and records the approval on the parent
issue.

Every flag, the slug rules, the metrics record and the close hooks are in the
[Effort verbs reference](/effort-reference/).

## Only so many efforts at once

A team that starts everything finishes nothing. `cckit effort start` refuses a **new** effort once
`effort.wipLimit` are already in progress. The default is 2. An effort is in progress while its
`effort/<N>-<slug>` branch exists, on your machine or on GitHub: `start` creates the branch and
`close` deletes it.

<Chat
  title="starting a third effort while two are open"
  say="Start the newsletter effort too."
  ran="cckit effort start <slug|N>"
  means="Close one open effort, or pass --force to start anyway."
>
  I could not start it. Two efforts are already in progress and the limit is 2, so I started
  nothing. Do you want me to close one, or start anyway?
</Chat>

A refusal creates nothing and names the efforts that are open. Close one, or pass `--force` to
start anyway. Starting a single issue with `cckit start <issue>` has no such limit. The exact
rules, the offline behaviour and the config key are under
[The WIP limit](/effort-reference/#the-wip-limit).

## Waves

A wave is the set of issues that can run at the same time because none of them waits for another.
`cckit plan` shows the waves, with the most urgent work (`priority:p0`) first inside each one. A
"blocked by" link always wins over priority.
[How work is written down](/project-management/#the-three-units) defines the unit, and
[Run work in parallel waves](/development/waves/) runs one.

### The weekly cadence

Priority, chains and the WIP limit decide the order. The cadence is when you read it:

| When | Run | What it gives you |
| --- | --- | --- |
| Monday | `cckit plan` | The week's order: the waves, and inside each wave p0 → p3. |
| Daily | `cckit next` | The unblocked set, and the one command that starts the top issue. |
| Friday | `cckit gc` | The branches and worktrees that can be pruned. It is a report and deletes nothing; `cckit cleanup` acts on it. |

You do not have to remember the table. `cckit next` and `cckit status` both end their output with
the same line, printed by one shared function:

```text
Weekly cadence — Monday: `cckit plan` orders the week · daily: `cckit next` picks up one issue · Friday: `cckit gc` reports what can be pruned.
```

<Aside type="note" title="Each piece of work has its own folder">
Parallel work stays apart because every issue and every effort gets its own branch and its own
copy of the project on disk, called a worktree. `cckit start <issue>` and `cckit effort start`
create it. [How one change is built](/development/) explains it.
</Aside>
