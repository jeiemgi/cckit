Open this page when you know which verb you want and need its exact flags, or when you want to
see everything cckit can do in one place. It lists every cckit verb, with one line on what it does.
To learn when and why to use a verb, start from its area: each area page in the
[Software track](/software/) names its verbs and links here for the flags.

cckit is a thin bash dispatcher over a git-mechanics bundle. Every verb reads from `cckit.config.json` — no org or repo is hardcoded. Append `--json` to any verb for machine-readable output an agent can parse.

<Aside type="tip" title="How to read this page">
The tables are grouped by job: setup, the daily lifecycle, planning a wave, running flows in parallel, and housekeeping. Copy any command straight from the table. `cckit <verb> --help` (or `cckit help <verb>`) prints one verb's usage, the question it answers, a prompt to paste and what it needs. The dispatcher answers it from the verb table before the verb runs, so it works for every verb and changes nothing; a verb with more to say adds its own text under **Details**.
</Aside>

## Every verb, by the question it answers

Each verb answers one question, and the tables below list them grouped the way `cckit help` prints
them, git mechanics first. **Paste** is a prompt to give an agent; **Needs** says whether the verb
runs on git alone or also uses the forge (GitHub) when one is configured; **Skill** names the skill
that drives the verb in Claude Code, and a dash means the verb is CLI-only. The block is generated
from `lib/core/verbs.tsv`, the one source for every verb, and `lib/core/verbs-test.sh` fails when
it drifts.

### Renaming a verb

The top level only shrinks. `bash lib/core/check.sh` fails when `lib/core/verbs.tsv` holds more
top-level verbs than `lib/core/verbs.baseline` (38 today), and fails when it holds fewer until the
baseline is lowered to match. A renamed verb keeps its old name as an `alias` row: the old name still
works and prints one line on stderr, for example
`cckit: 'plan' is an old name for 'effort plan --issues'; it still works. Use 'cckit effort plan --issues'.` An alias does not
count toward the baseline and is not removed before 1.0. An alias may name a verb and its first
words: `cckit sync` runs `cckit status --board`, and `cckit lib` runs `cckit agent lib`; the words you
typed follow them.

## Ask cckit about its own verbs

Four questions a reader has about the verbs themselves. Each one lists the prompt to paste, the
command the agent runs, and what comes back. None of them changes a file or calls the forge.

### What can cckit do?

- **Paste:** "List the cckit verbs by the question each one answers."
- **The agent runs:** `cckit help` (or `cckit --help`).
- **You see:** every verb under the question its group answers, git mechanics first, then the old
names that still work:

```text
cckit — every verb answers a question.
  cckit <verb> --help    one verb: its usage, its question and a prompt to paste
  cckit commands --json  every verb as data: question, prompt to paste, usage, needs

How do I take one change from a branch to merged?
  start           How do I start work on an issue without touching my main checkout?
  pr              How do I open the pull request for this issue?
  merge           Can this pull request land, and what does landing clean up?
  …
```

### What does this one verb do?

- **Paste:** "What does `cckit start` do, and what should I ask you to run it?"
- **The agent runs:** `cckit start --help` (the same as `cckit help start`).
- **You see:** the usage, the question, a prompt to paste and what the verb needs. The verb itself
does not run:

```text
cckit start [--force] <issue|E<n>|E<n>.<step>> [slug]

  Answers: How do I start work on an issue without touching my main checkout?
  Paste:   "Start the issue I pick in its own worktree."
  Needs:   git; reads or writes the forge (GitHub) when one is configured
  Skill:   kit-task-start
```

A verb with its own longer help, such as `cckit orchestrate` or `cckit doctor`, prints it after
this block under **Details:**.

### Which verbs exist, as data?

- **Paste:** "Read the cckit verb catalog and tell me which verbs work without GitHub."
- **The agent runs:** `cckit commands --json`.
- **You see:** an answer built from a JSON array with one object per name (50 today: 38 verbs, the
bare `cckit`, eleven old names). One object:

```json
{"name":"merge","kind":"verb","target":null,"group":"git","needs":"forge","skill":"kit-task-pr-merge",
 "question":"Can this pull request land, and what does landing clean up?",
 "prompt":"Merge this branch's pull request once its gate is green, and clean up the branch.",
 "usage":["cckit merge [<pr>] [--squash|--merge|--rebase]"]}
```

### I typed an old name. Does it still work?

- **Paste:** nothing; this is what happens when you, or a script, use a verb's old name.
- **The agent runs:** for example `cckit plan`.
- **You see:** one line on stderr, then the new verb's normal output:

```text
cckit: 'plan' is an old name for 'effort plan --issues'; it still works. Use 'cckit effort plan --issues'.
```

Each step prints `done`, `skipped` or `failed`; a re-run skips finished steps. `--no-github` scaffolds only. `--dry-run` prints every step and writes nothing. Exit 0 · 1 a step failed · 2 refused before any write. A home or system folder is never scaffolded into. |

Each profile role is installed for both from one source: `.claude/agents/<role>/AGENT.md` and `.codex/agents/<role>.toml`. See [Adapters](/adapters/#choosing-adapters-at-install) and [Hooks](/hooks/#codex). |

## The daily lifecycle

One issue becomes one branch, one worktree, one PR. These verbs walk that path.

| Verb | Purpose |
| --- | --- |
| `cckit next [--effort N]` | The unblocked set + how to start the top issue. In a project whose `tasks.default` is `light`, a bare `cckit next` prints what `cckit task next` prints (with `--json`, one JSON object or `null`); with `--effort N` it asks about issues as before. Human output ends with the weekly cadence line: Monday `cckit effort plan --issues`, daily `cckit next`, Friday `cckit gc`. `--json` rows stay `{number,ctx,title}`. |
| `cckit start <issue> [slug]` | Create an isolated worktree + branch for an issue, [bootstrapped](/config-and-permissions/#worktree-bootstrap) — env files copied, dev port assigned, deps installed at the selected targets (`worktree.installPaths` if set — those dirs regardless of their manifests — else a root that declares dependencies or is a workspace root with members, else nothing). [Claim-checked](#session-claims): refused when another live session already holds the issue, unless `--force` / `KIT_FORCE=1`. Without a [forge](/config-and-permissions/#the-forge) the issue is not read: the branch is `task/<N>-<slug>` with the slug given, else `issue-<N>`, and one line says so. |
| `cckit claims` | List the live [session claims](#session-claims) — issue, session pid, start time, branch, worktree. Read-only. `--json` returns a JSON array. |
| `cckit pr <issue> <summary> [--base <branch>]` | Commit, push, and open the PR. `--base <branch>` opens it against a branch other than the configured base — a release PR from `develop` to `main`, or a hotfix to the release branch — with the same labels, milestone and board steps. The push exports the target as `KIT_PR_BASE`, so a git pre-push hook can compare against the branch the PR targets. Without a forge it commits and pushes, prints the GitHub compare page when origin is on GitHub, and says in one line that the pull request was not opened. |
| `cckit hotfix <pr\|sha> [--base <branch>]` | Cherry-pick one merged PR or commit onto the release branch (`main` by default): a worktree from `origin/<base>`, `git cherry-pick -x`, push, and a PR titled after the source with `Cherry-pick of #N` in its body. Without a forge the source must be a commit sha (a PR number cannot be read), the branch is pushed and the compare page printed, and no PR is opened. See [Hotfix to the release branch](/ship/releasing/#hotfix-to-the-release-branch). |
| `cckit close <issue> <summary> [--reason R] [--duplicate-of N] [--superseded-by N]` | Close the issue with a summary comment and a reason (`completed`, `not-planned`, `duplicate`; superseded closes as not planned with a "Superseded by #N" comment), and mark it done on the board. |
| `cckit new --role R "<title>"` | File one issue: labels, board add, Role and Status fields. Milestone optional. A label the repo does not have is left off with a warning that names it; the issue is still created, and the verb exits non-zero only when the issue itself is not. `R` matches any option of the board's Role field by name, ignoring case and treating spaces and hyphens alike (`backend`, `Tech Lead`, `tech-lead`); a role the board has no option for leaves Role unset and prints a warning on stderr naming the missing `ROLE_OPT_<NAME>`. |
| `cckit merge [<pr>] [--merge\|--rebase]` | Merge the PR (squash by default), close its linked issues, clean the branch and worktree, and update the PR's base, which may be an `effort/<N>` branch. Refuses a PR whose **head** is `effort/*` and names `cckit effort close <N>`; `KIT_FORCE=1` merges anyway, with a warning. Without a forge, run from the branch's worktree with no PR number: the branch lands on the base through git (a squash commit titled after its last commit; `--merge` keeps the commits under a merge commit; `--rebase` replays them first), the base is pushed, the branch and worktree are cleaned up, and one line says no pull request was merged and no issue closed. |
| `cckit status --board` | Board state: issues by role with Project Status, a merge-ordered open-PR queue, and blocked / not-on-board / stale (>14d) flags. |
| `cckit status --board --json \| --write \| --cached [TTL] \| --watch [SECS] \| --plan` | The same board as one cached JSON document for a TUI or statusline — see [Board cache and watch mode](#board-cache-and-watch-mode). |
| `cckit status --board --no-snapshot` | Skip the local board snapshot `.cckit/board.md` — see [Local board snapshot](#local-board-snapshot). |
| `cckit status` | "Where are we?" in three buckets — local undone work, open PRs waiting on a human, cleanup available (local + remote) — plus the board, the light tasks when the project has any (counts by state and the tasks somebody has to act on), the next effort that can start in each flow, and the resume handoff, and one line with the resident instruction-file total. Read-only. |
| `cckit handoff "<note>"` | Save a resume-here note for the next session. |


### Session claims

`cckit start <issue>` records one claim per issue and refuses the start while another live session
holds it; `cckit claims` lists the live ones. The record, the refusal, `--force`, and when a claim
ends are on [Multi-session safety](/development/many-sessions/#session-claims).

### Where are we?

`cckit status` answers the question a session opens with, which is not what `git status` answers. Plain `git` output describes refs; it cannot see which PRs are waiting on a person, or which branches are safe to delete. The three buckets, in this order:

| # | Bucket | What it reports |
| --- | --- | --- |
| 1 | **Local undone work** | Worktrees with uncommitted changes; branches holding commits reachable from **no** remote ref; effort subs not yet merged into their effort branch. Plus the worktree inventory, because a clean worktree on an issue branch is still work in progress. A detached worktree that `cckit gc` rates LANDED (clean, HEAD on the base branch or `main`) is left out of the **In progress** list and counted in one line under it; `--json` `worktrees` still carries every worktree. |
| 2 | **PRs waiting on a human** | Each open PR with the one thing it needs: `conflict` · `checks` · `draft` · `wait` · `threads` · `ai-review` · `review` · `ready`. |
| 3 | **Cleanup available** | What can go, local **and** remote, plus what is deliberately kept (orphan work, open-issue branches) and how many branches could not be classified because a GitHub read failed (`cleanup.unknown` in the JSON). `cckit gc` shows the same classification in full; acting on it is the `/kit-cleanup` skill. |

The report ends with one **Instruction files** line — the bytes `CLAUDE.md` and every rule without a `paths:` frontmatter load into every session, against Claude Code's 150k limit, and the three largest files. `cckit doctor` prints the same line and warns over the limit; `--json` carries it as `instruction_budget` (`null` when the project has no instruction files). The gate behind it is [`instruction-budget-lint`](/review/gates/#instruction-budget-lint--what-every-session-loads).

How two of the verdicts are computed:

- **"Unpushed" means on no remote at all**, not "ahead of its own upstream". An effort sub whose commits were merged into a pushed effort branch has no upstream of its own, yet its work is safely on the remote — reporting it as undone would send you to re-push work that is already there.
- **A superseded check run never counts.** Re-running a check, or retitling a PR and re-firing a title gate, leaves the old run in GitHub's rollup. Counting every context there reports a PR as failing a check that has since passed, so only the latest run per check name is read.

In Claude Code the same report is `/kit-status`, and it answers the question in whatever wording it arrives in — "where are we", "what's the status", "how are we doing", "catch me up", "what needs my attention", or the same question in the project's own language. It deliberately does **not** fire on a question with a specific subject ("what's the status of PR 41"), which wants a direct answer rather than the whole picture.

The `ai-review` verdict only appears when the repo evidently uses an AI reviewer — a reviewer config file, or an AI review already present on another open PR. In a repo with none, it never fires.

```bash
cckit status          # the board, the light tasks, the next effort per flow, the three buckets
cckit status --json    # the same verdicts as JSON: local_undone, worktrees, prs, cleanup, next_efforts, light_tasks
```

### Light tasks

In a project that has [light tasks](/project-management/light-tasks/), `cckit status` prints a **Light tasks** section
after the board. A project with none gets no section.

```text
## Light tasks

review: 3   doing: 0   todo: 2   draft: 1   shared: 0   done: 0

| task | state | title | what it needs |
| --- | --- | --- | --- |
| `ta01` | **review** | Spring newsletter | waiting for review: its pull request is open from light/ta01-spring-newsletter |
| `tc01` | **draft** | Launch posts | only in this checkout; start it (cckit task start tc01) or share the list (cckit task share) |
```

The first line counts every task by state. The table lists the tasks somebody has to act on, in
this order: `review`, `doing`, `draft`, `shared`. A `todo` task is counted and not listed. The
states are the ones `cckit task list` prints, read from local git: this section makes no GitHub call
and does not fetch, so a teammate's change shows after the next `git fetch` or `cckit task list`.

`cckit status --json` carries the same data as `light_tasks`:
`{counts: {draft, todo, shared, doing, review, done, dropped}, attention: [{id, state, title, needs}]}`,
or `null` when the project has no light task.

### Next effort per flow

Between the board and the three buckets, `cckit status` prints one row per flow that has an open effort: the effort that can start now. It reads the open issues carrying the `effort` label (the label `cckit effort new` applies), groups them by their `flow:` label, and in each flow picks:

1. only efforts with **no open blocker** — any open `blocked_by` issue blocks, whether it is an effort in the same flow, an effort in another flow, or a plain issue. A closed blocker does not.
2. among those, the most urgent `priority:pN` (p0 → p3, unlabelled last), then the lowest issue number.

The last column counts the flow's efforts still waiting on an open blocker. A flow where every effort is blocked keeps its row and says none can start. The section also states its own emptiness: when no open issue carries the `effort` label it says so, and when the efforts could not be read (no forge or jq, unauthenticated, offline) it says that instead — the two never look alike. The read costs one issue list plus one REST call per open effort.

In `--json` output the same rows are the `next_efforts` array:

```json
{ "flow": "core", "number": 241, "ctx": "L", "title": "steady progress order and cadence", "waiting": 1 }
```

`number`, `ctx` and `title` are `null` for a flow where nothing can start. `next_efforts` itself is `null` — not `[]` — when the efforts could not be read. That alone does not change the exit status, which still follows `prs_read`.

Below the table both `cckit status` and `cckit next` print the same weekly cadence line: Monday `cckit effort plan --issues` orders the week, `cckit next` daily picks up one issue, Friday `cckit gc` reports what can be pruned.

## Plan and drive a wave

A **wave** is a set of issues with no blockers between them, so they can run at once. These verbs plan a wave and drive the agents through it.

| Verb | Purpose |
| --- | --- |
| `cckit effort plan --issues [--effort N]` | Wave plan: deps-ordered, file-disjoint, session-fit (`ctx:` weights S=1 M=2 L=4 XL=8; an issue with no `ctx:` label shows `?` and weighs 2, and a value outside the scale weighs 2 with a warning on stderr). Inside a wave, issues are ordered by their `priority:pN` label — p0 → p1 → p2 → p3, unlabeled last — with ties keeping the dependency-derived order. Dependencies always win: a blocker sits in an earlier wave than what it blocks, so priority never pulls a dependent ahead of its blocker. |
| `cckit effort plan --next` | Forward plan: inventory the kit's own skills/verbs/rules/docs, propose what to build next. |
| `cckit effort plan --wave [--effort N] [--adapter <claude\|codex\|both>]` | Read open efforts, propose incoming waves: worker fan-out + captain drive. The wave data is the same for every runtime; `--adapter` picks the dispatch wording (default: the project's stored `adapters`). `--json` emits the wave data only. |
| `cckit watch [--merge] [--loop]` | Captain: gate open PRs, squash-merge clean ones, advance. Policy floors (default on) hold PRs touching CI workflows, lockfiles, or security paths — and any `hold`-labelled or draft PR — for human review. |
| `cckit effort <new\|chain\|start\|pr\|close\|plan>` | The effort lifecycle (a parent issue + sub-issues). `new` takes `--slug` and `--kind` (one of `feat fix task chore security scaffold ci adr spike plan`, default `task`, or a content kind `post campaign brand research`; sets the `kind:` label on the parent and every sub. | `cckit effort start [--force] <slug\|N> [slug]` | Create the effort's `effort/<N>-<slug>` branch + bootstrapped worktree. **WIP-limited:** refuses a *new* effort once `effort.wipLimit` (default 2) are already in progress — in progress meaning an `effort/<N>-<slug>` branch exists as a local head **or** on origin, read with `git ls-remote` rather than the cached `refs/remotes`. At the limit refuses; only strictly under it starts. Re-starting an effort that is already in progress is never gated. The check runs before anything is written, so a refusal makes no branch, no worktree and no board change. `--force` (or `KIT_FORCE=1`) starts anyway; `0` refuses every ordinary start but not a forced one. `EFFORT_WIP_REMOTE=0`, or an unreachable origin, counts the cached refs instead and the start still proceeds. | `cckit effort plan` | Session-fit plan over the open efforts: grouped by flow, ordered by `blocked_by`, packed into sessions under `KIT_SESSION_BUDGET` (default 4). A `source:` line under the header names the source used, its age when reported, and any fallback. |
| `cckit effort review <N> [--branch B]` | Check each sub of an effort against its own `## Spec`: one line per sub with its state, whether its Spec is checkable, whether a commit on the effort branch (`effort/<N>-*`, local or origin, or `--branch`) names it, and a verdict — `done`, `open`, `landed, still open`, `closed, not on the branch`, or `no spec`. Ends with `review #N: D of M done`. A read: exits 0 when every sub is done and 1 otherwise, so a script can gate on it. |
| `cckit effort sprint <name\|bounds\|open\|list\|close>` | One week, Monday to Monday, as a forge milestone named after its ISO week (`2026-W48`). `name [YYYY-MM-DD]` and `bounds [YYYY-MM-DD]` print the sprint a day falls in and its two Mondays, on git alone. `open [--goal G] [--date D]` creates the milestone with the goal as its description and the closing Monday as its due date; an existing one is kept, and `--goal` updates its goal. `list [--all]` prints the sprint milestones with their open and closed counts. `close [<YYYY-Www>] [--review T\|--review-file F] [--retro T\|--retro-file F] [--out F] [--dry-run]` writes the sprint review and the retrospective to a page (default `.cckit/reports/<date>-sprint-<name>.md`: the goal, the issues done, the issues carried over), then closes the milestone with a one-line review in its description; `--dry-run` prints the page and writes nothing. `cckit effort new --sprint[=YYYY-MM-DD]` files an effort into a sprint: a `## Sprint` section in the body and the sprint's milestone on the parent and its subs. |
| `cckit effort chain <a> <b> [<c> …]` | Declare a linear order over 2+ issues: `b` `blocked_by` `a`, `c` `blocked_by` `b`, plus a `- Depends on #<predecessor>` line in each successor's `## Relations` section. These are the edges `cckit effort plan --issues` layers into waves. Idempotent, and additive — an issue already blocked by something else keeps that blocker. Refuses (and writes nothing) on fewer than two numbers, a non-numeric argument, an issue that does not exist, a repeated number, or an edge that would close a cycle. |

that is how an effort's sub-issue starts from `effort/<N>-<slug>` — and the launch plan says so.

### Tmux and Herdr

Tmux is the default runtime and preserves the existing tiled session. `--runtime herdr` creates one
Herdr workspace, then one tab and named agent for every cckit worktree. cckit still owns issue
selection, dependencies, branches, worktrees, pull requests, and cleanup; Herdr owns terminal
persistence and live agent state.

```bash
cckit orchestrate --dry-run --runtime herdr --agent codex <issues…>
cckit orchestrate --runtime herdr --agent codex <issues…>
cckit autopilot --runtime herdr --agent codex --cap 3

# or run a declared profile instead of naming a CLI:
cckit orchestrate --runtime herdr --profile cheap <issues…>
cckit orchestrate --profile cheap <issues…>              # tmux is the default runtime
cckit autopilot --profile cheap --cap 3
```

`--profile <name>` takes the agent `kind` and the extra CLI `args` from a declared
[agent profile](/config-and-permissions/#agent-profiles). With no `--profile` and no `--agent`, the
cheapest-tier profile runs. `--agent` overrides both and skips profiles entirely, and a project
that declares no profiles behaves exactly as before. The profile's `args` reach the agent on **both**
runtimes, so the same profile selects the same model whether it runs under tmux or Herdr.

The kinds Herdr accepts are read from the installed binary (`herdr agent start --help`), not from a
list kept inside cckit — a hand-written copy drifts against the runtime, and a kind that cckit
accepts but Herdr rejects would fail *after* the worktree was created.

Herdr accepts canonical agent kinds rather than arbitrary shell commands. cckit validates the kind
before creating worktrees. It also starts each worker with the issue's generated `cckit brief`, so
the worker does not need to read the board, and asks for a final receipt containing only the PR or
issue URL, gate result, and blocker.

`ctx:S|M|L|XL` sizes session work and `role:*` records responsibility — neither picks a model, and
neither does cckit. An **agent profile** declares a spend `tier`, a permission policy and the CLI
arguments to run; any model selection is spelled by you in `args`. See
[Agent profiles](/config-and-permissions/#agent-profiles) for the fields and the resolution order.
`--agent` still names a CLI program directly, and that path uses the program's own configured model.
A test greps the shipped `scripts/lib` and `bin` for any vendor model id and requires zero hits.

A detached ZOMBIE is compared to its own HEAD's tree: with no staged delta its metadata is pruned; with one there is no branch to recover onto, so `--yes` locks that entry (git's `locked` file) and the prune leaves it for recovery by hand. |

### Finding a helper before you write one

`cckit commands` answers "which verbs exist?". `cckit agent lib` answers the question underneath it — "which helper already does this?" — so an agent asked to, say, attach gate evidence to a PR finds `pr-evidence.sh` instead of writing that from scratch.

Each row carries the four facts you need before sourcing a file:

| Column | What it is |
| --- | --- |
| `file` | The basename to `source`. The footer prints the resolved absolute path. |
| `errors` | The file's declared failure contract — `pure`, `strict`, `best-effort`, or `mixed` — read from its `# errors:` header (see [CONTRIBUTING](https://github.com/jeiemgi/cckit/blob/main/CONTRIBUTING.md)). A caller that composes a `strict` helper with a `best-effort` one silently inherits the weaker behaviour, so check this first. `mixed` rows also show their reason, because that is the only thing saying which half propagates; `--reasons` shows every file's reason. `unknown` means the file has no header yet — reported, never fatal. |
| `public functions` | The functions meant for callers. `_`-prefixed names are private by convention and excluded, as are functions defined inside another function. Never elided. |
| `purpose` | The first sentence of the file's own header comment — derived, never invented. |

`*-test.sh` runners are excluded by default (they are test entry points, not a library); the footer always states how many, and `--all` includes them.

Run from a project cckit is installed in, it catalogs that project's own `scripts/lib` when it has one and otherwise the cckit install itself — which is the library `cckit` on your PATH can source. `--root <dir>` points it somewhere else.

```bash
cckit agent lib                 # the markdown table
cckit agent lib --json           # TOON rows {file,errors,functions,purpose}
cckit agent lib --all           # include the *-test.sh runners
cckit agent lib --reasons       # every failure reason, not only the mixed ones
```

### Briefing an agent without retyping the repo

A hand-written delegation brief drops whatever its author forgot, and what gets forgotten is what the delegated agent then rediscovers by hand. `cckit brief <issue>` reads it out of the repo instead:

| Section | Where it comes from |
| --- | --- |
| worktree + branch | `git worktree list`, matched to the issue by the same branch-name rule `gc` uses to decide what is protected — so the brief and `gc` cannot disagree about which worktree an issue owns. No worktree yet reads as an instruction to run `cckit start <issue>`, never as silence. |
| seed freshness | Whether `origin/<base>` is already an ancestor of the branch. A **STALE** seed means a green check on that branch proves nothing until it is rebased — the omission that quietly costs a whole session. |
| files this issue owns | The paths named in the issue's `## For agents` section, falling back to the whole issue when that section carries build order rather than paths (it says which). A bare basename lifted from prose is resolved against the tracked files, so `captain-test.sh` reports as `lib/verbs/captain-test.sh` and not as a new file. |
| helpers you already have | `cckit agent lib` rows for the helpers the issue **owns**, then the ones its files actually `source`, capped at ten with the overflow counted (`KIT_BRIEF_MAX_HELPERS` raises the cap). |
| standing gotchas | The `## Standing gotchas` block of the project's own `.claude/rules/delegation-brief.md`, falling back to the kit's template. Lifted, never retyped, so it cannot go stale against the rule. |
| durable prose | The `## Durable prose` block of the same rule: the instruction that an agent about to write an issue body, a PR body, a commit message, a rule, an ADR or a knowledge doc runs the `concrete` pass on it first, with the constraints that make the pass reproducible (cut only by named offense, evidence untouchable, `O13`/`O14` fixed at the gap and not reworded). A sub-agent applies a skill only when it is told to, so a mandate that lives only in `communication-style.md` never reaches it. |

Every section that cannot be filled says so on its own line. A brief that silently omits a section is the failure this verb exists to remove, so an empty file list reads "the issue names no paths — ask before starting" rather than nothing at all.

```bash
cckit brief <issue>                                          # the brief for that issue
cckit brief <issue> --skills kit-ship --verbs 'effort start,brief'   # plus the worker's toolset
```

`--skills` and `--verbs` add a `## Your toolset` section listing exactly the names given, in that
order. Each name is checked first: a skill must have a `SKILL.md` in the project or the kit, a verb
must be a row of the verb table (an `effort` sub-verb must be one the dispatcher routes). An
unknown name exits 2 before the issue is read, so a worker is never handed a tool that is not there.

Reading the issue is the verb's one hard dependency: a failed GitHub read propagates rather than yielding a brief with an empty issue in it.

## Local board snapshot

Every board read also writes `.cckit/board.md`, so an agent can grep the board instead of asking GitHub again. It is the primary checkout's `.cckit/`, shared by every worktree; `cckit status --board` prints the absolute path on stderr. `.cckit/` is gitignored, so a bare `rg` skips the file: give it the path.

```bash
cckit status --board --json                      # reads the board, writes the snapshot
rg '#575' /path/to/repo/.cckit/board.md
rg -F 'E546.' /path/to/repo/.cckit/board.md   # every sub-issue of effort 546
```

One tab-separated line per open issue, grouped under `## Efforts`, `## Sub-issues` and `## Standalone`:

```text
#575	open	sub	E546.9	priority:p1,role:tech-lead,kind:feat	[Effort 546] 9 · Local board snapshot
```

| Column | Value |
| --- | --- |
| status | The Projects v2 Status when the board is on and was read (the human board, `--json`, `--write`); otherwise the issue state, `open`. |
| kind | `effort`, `sub` or `issue`, from the title prefix (`[E<n>]`, `[E<n>.<s>]`, legacy `[Effort] N · ` and `[Effort N] M · `) or the `effort` label. |
| token | `E<n>` for an effort, `E<n>.<s>` for a sub, `-` for a standalone issue. |

The header records the time, the repository, the command and how to read the file. The write goes to a temp file renamed over the snapshot, and a failed read leaves the previous snapshot as it was. `--raw-json` and a `--cached` hit write nothing; neither does a project with no forge, which says so on stderr. `--no-snapshot` skips the write; `CCKIT_BOARD_SNAPSHOT=<path>` writes it elsewhere.

## Board cache and watch mode

A dashboard that polls the board — a TUI, a statusline — reads one JSON document instead of running its own GitHub queries:

```bash
cckit status --board --json          # print the document (one JSON object)
cckit status --board --write         # fetch, then write it to <git-common-dir>/kit-sync-cache.json
cckit status --board --cached 60     # print the cache if it is under 60s old (no GitHub call), else refresh it
cckit status --board --watch 30      # refresh the cache every 30s until interrupted
cckit status --board --plan          # the human board plus an inline `effort plan`
```

| Flag | Behavior |
| --- | --- |
| `--json` | One JSON object on stdout. On `status --board` the older spellings `--llm` and `--output=json` are unchanged: they still return the issue list as TOON. |
| `--write` | Writes the document to `<git-common-dir>/kit-sync-cache.json` — one file shared by every worktree. The write goes to a temp file that is validated and then renamed, so a reader sees the old document or the new one. A failed or partial fetch (issues, the PR list, or the Projects v2 board when it is on) exits `1` and leaves the file untouched. Prints nothing on stdout unless `--json` is also given. |
| `--cached [TTL]` | Prints the cache with no GitHub call when it is younger than `TTL` seconds (default `60`); otherwise refreshes, writes and prints it. A failed refresh exits `1` and leaves the cache as it was. |
| `--watch [SECS]` | Refreshes and writes every `SECS` seconds (default `30`). A failed refresh logs `kept the last good cache` on stderr and the loop continues. `KIT_SYNC_WATCH_MAX=<n>` stops after `n` refreshes, exiting `1` if the last one failed. With `--json` each refreshed document is also printed, one per line. |
| `--plan` | Adds `effort plan` output: an `### Effort plan` section on the human board, a `plan` string in the document. |

`--write`, `--cached` and `--watch` refuse `--role` / `--milestone` (exit `2`): the cache is one file every reader shares, so it only ever holds the whole board.

The document:

```json
{
  "schema": 1,
  "repo": "owner/repo",
  "generatedAt": "2026-11-11T10:00:00Z",
  "generatedEpoch": 1794391200,
  "open": 3,
  "roles": [
    { "role": "Tech Lead", "slug": "tech-lead",
      "issues": [ { "number": 1, "title": "…", "status": "—", "priority": "p1", "milestone": "v1", "blocked": false } ] }
  ],
  "unassigned": [],
  "blocked": [2],
  "notOnBoard": null,
  "stale": { "days": 14, "issues": [ { "number": 2, "days": 20 } ] },
  "mergeQueue": [
    { "number": 14, "title": "…", "risk": "low", "size": "S", "state": "ready",
      "blocked": false, "draft": false, "agent": false, "conflict": false, "approved": true }
  ]
}
```

- `roles` follows the config's role order; `unassigned` holds open issues with none of those `role:` labels.
- `notOnBoard` is `null` when no Projects v2 board is configured, otherwise the issue numbers missing from it.
- `mergeQueue` is in merge order — ready, then draft, then blocked; within a tier `risk:low` first, then smaller size. `state` is `ready`, `needs-review`, `conflict`, `draft` or `blocked`. It is the same ordering the human table prints.
- Every fetch appends `op.start` and `op.done` (op `sync`, `payload.ok` true or false) to `<git-common-dir>/kit-events.jsonl`. A `--cached` hit makes no fetch and emits nothing.

## Structured output for agents

Append `--json` (older spellings: `--llm`, `--output=json`) to any verb for parseable output, so an agent reasons over the result instead of scraping human text:

```bash
cckit status --board --json
cckit effort plan --issues --json
cckit effort plan --next --json   # the forward plan as TOON rows {rank,area,proposal,next}
cckit agent lib --json         # the helper catalog as TOON rows {file,errors,functions,purpose}
cckit effort plan --json
```

Human (pretty) output is the default; agents should prefer `--json`. See [Driving cckit from agents](/agents/) for the full contract.
