Every cckit verb, grouped by job, with the one-liner version of what it does.

cckit is a thin bash dispatcher over a git-mechanics bundle. Every verb reads from `cckit.config.json` — no org or repo is hardcoded. Append `--llm` to any verb for machine-readable output an agent can parse.

<Aside type="tip" title="How to read this page">
The tables are grouped by job: setup, the daily lifecycle, planning a wave, running flows in parallel, and housekeeping. Copy any command straight from the table. Run `cckit <verb> --help` for the details of one verb.
</Aside>

## Set up and install

| Verb | Purpose |
| --- | --- |
| `cckit install [bin-dir]` | Symlink `cckit` onto your PATH. |
| `cckit init --profile <p>` | Scaffold `cckit.config.json` + `.claude/` for this repo. |
| `cckit scan` | Detect this repo's stack + kit state (JSON). |
| `cckit doctor` | Onboarding preflight: deps present, `gh` authenticated, and (when enabled) the MemPalace CLI + per-wing wake-up header. Asks before installing; `--fix` installs and seeds without the prompt. |
| `cckit adopt` | Record kit-shaped files a repo already has. |
| `cckit migrate` | Reshuffle an old kit layout to the current one. |

## The daily lifecycle

One issue becomes one branch, one worktree, one PR. These verbs walk that path.

| Verb | Purpose |
| --- | --- |
| `cckit next [--effort N]` | The unblocked set + how to start the top issue. |
| `cckit start <issue> [slug]` | Create an isolated worktree + branch for an issue. |
| `cckit pr <issue> <summary>` | Commit, push, and open the PR. |
| `cckit close <issue> <summary>` | Close the issue and mark it done. |
| `cckit sync` | Board state: issues by role with Project Status, a merge-ordered open-PR queue, and blocked / not-on-board / stale (>14d) flags. |
| `cckit status` | "Where are we?" in three buckets — local undone work, open PRs waiting on a human, cleanup available (local + remote) — plus the board and the resume handoff. Read-only. |
| `cckit handoff "<note>"` | Save a resume-here note for the next session. |


### Where are we?

`cckit status` answers the question a session actually opens with, which is not what `git status` answers. Plain `git` output describes refs; it cannot see which PRs are waiting on a person, or which branches are safe to delete. The three buckets, in this order:

| # | Bucket | What it reports |
| --- | --- | --- |
| 1 | **Local undone work** | Worktrees with uncommitted changes; branches holding commits reachable from **no** remote ref; effort subs not yet merged into their effort branch. Plus the worktree inventory, because a clean worktree on an issue branch is still work in progress. |
| 2 | **PRs waiting on a human** | Each open PR with the one thing it needs: `conflict` · `checks` · `draft` · `wait` · `threads` · `ai-review` · `review` · `ready`. |
| 3 | **Cleanup available** | What can go, local **and** remote, plus what is deliberately kept (orphan work, open-issue branches). Acting on it is [`cckit cleanup`](#housekeeping-and-output). |

Two details worth knowing, because both are places a naive reading gets it wrong:

- **"Unpushed" means on no remote at all**, not "ahead of its own upstream". An effort sub whose commits were merged into a pushed effort branch has no upstream of its own, yet its work is safely on the remote — reporting it as undone would send you to re-push work that is already there.
- **A superseded check run never counts.** Re-running a check, or retitling a PR and re-firing a title gate, leaves the old run in GitHub's rollup. Counting every context there reports a PR as failing a check that has since passed, so only the latest run per check name is read.

In Claude Code the same report is `/kit-status`, and it answers the question in whatever wording it arrives in — "where are we", "what's the status", "how are we doing", "catch me up", "what needs my attention", or the same question in the project's own language. It deliberately does **not** fire on a question with a specific subject ("what's the status of PR 41"), which wants a direct answer rather than the whole picture.

The `ai-review` verdict only appears when the repo evidently uses an AI reviewer — a reviewer config file, or an AI review already present on another open PR. In a repo with none, it never fires.

```bash
cckit status          # the three buckets
cckit status --llm    # the same verdicts as JSON: local_undone, worktrees, prs, cleanup
```

## Verb ↔ skill map

Every verb below is drivable from the CLI. The ones with a skill are also reachable as a slash command in Claude Code; the ones without are CLI-only, which means an agent that only reads the skills list cannot see them. Kept here so that gap stays visible rather than being rediscovered.

| Verb | Skill | |
| --- | --- | --- |
| `status` | `kit-status` | |
| `sync` | `kit-task-sync` | |
| `next` | `kit-next` | |
| `plan-next` | `kit-plan-next` | |
| `start` · `pr` · `close` | `kit-task-start` · `kit-task-pr` · `kit-task-close` | |
| `gc` | `kit-gc` | (`kit-cleanup` acts on its report) |
| `autopilot` | `kit-autopilot` | |
| `contribute` | `kit-contribute` | |
| `digest` | `kit-digest` | |
| `doctor` · `init` · `update` | `kit-doctor` · `kit-init` · `kit-update` | plugin commands |
| `effort` | `kit-effort-new` · `-start` · `-pr` · `-close` | one skill per phase |
| `brief` | — | CLI-only |
| `plan` · `wave` · `watch` · `orchestrate` | — | CLI-only |
| `msg` · `handoff` | — | CLI-only |
| `adopt` · `migrate` · `scan` | — | CLI-only |
| `lib` · `commands` · `version` · `render` · `encode-context` · `bench` · `release` · `install` · `completions` · `debug` | — | plumbing; no skill intended |

## Plan and drive a wave

A **wave** is a set of issues with no blockers between them, so they can run at once. These verbs plan a wave and drive the agents through it.

| Verb | Purpose |
| --- | --- |
| `cckit plan [--effort N]` | Wave plan: deps-ordered, file-disjoint, session-fit. |
| `cckit plan-next` | Forward plan: inventory the kit's own skills/verbs/rules/docs, propose what to build next. |
| `cckit wave [--effort N]` | Read open efforts, propose incoming waves: subagent fan-out + captain drive. |
| `cckit watch [--merge] [--loop]` | Captain: gate open PRs, squash-merge clean ones, advance. Policy floors (default on) hold PRs touching CI workflows, lockfiles, or security paths — and any `hold`-labelled or draft PR — for human review. |
| `cckit effort <new\|start\|pr\|close\|plan>` | The effort lifecycle (a parent issue + sub-issues). `new` takes `--slug`; `start`/`pr`/`close` accept a `<slug>` or the effort `<N>`. |


## Run flows in parallel

| Verb | Purpose |
| --- | --- |
| `cckit orchestrate <a> <b> …` | Run N flows in parallel worktrees (`--dry-run` / `--cap` / `--agent`). |
| `cckit autopilot [<a> …]` | Unattended multi-flow: drive (or auto-pick) issues under a cap. |

Both are launch verbs with no JSON result — use `--dry-run` to inspect the plan before anything starts.

## Housekeeping and output

| Verb | Purpose |
| --- | --- |
| `cckit gc [--prune [--yes]]` | Report (default) or prune merged branches + worktrees. Never touches a branch/worktree whose issue is still open — including an effort sub (`sub/<N><letter>-…`) of an open effort — and aborts rather than classify anything if that protection helper cannot load. |
| `cckit render` | stdin markdown → rich output (glow on a TTY, verbatim when piped). |
| `cckit encode-context` | stdin JSON → compact TOON (token-saving for subagents). |
| `cckit digest <path\|url>` | Summarize a file or URL with the local model. |
| `cckit bench [run\|report\|…]` | [Documentation benchmark](/benchmark/): score how well this project finds + uses its own canonical docs. |
| `cckit version` | The installed cckit version. |
| `cckit commands` | List every verb (the command catalog). |
| `cckit update` | Report whether this project is behind the installed cckit. |
| `cckit release <ver> [--publish]` | Cut a release (dry-run by default). |

## Structured output for agents

Append `--llm` (or `--output=json`) to any verb for parseable output, so an agent reasons over the result instead of scraping human text:

```bash
cckit sync --llm
cckit plan --llm
cckit plan-next --llm   # the forward plan as TOON rows {rank,area,proposal,next}
cckit effort plan --llm
```

Human (pretty) output is the default; agents should prefer `--llm`. See [Driving cckit from agents](/agents/) for the full contract.
