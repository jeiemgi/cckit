Cut a release with no "what number is this" step — your commit messages decide the version. Ongoing merges **don't** ship anything; you release deliberately, by merging one pull request when a batch of work is ready.

cckit follows [Semantic Versioning](https://semver.org/) driven by [Conventional Commits](https://www.conventionalcommits.org/). The version *number* is automatic — the commit messages since the last tag pick it — and the release is cut by [release-please](https://github.com/googleapis/release-please), which keeps a single **Release PR** open and up to date. Merging that PR is the release.

<Aside type="note" title="New here? The two terms">
**Semantic Versioning** is the `MAJOR.MINOR.PATCH` number on a release (like `1.4.2`). **Conventional Commits** is a small rule for writing commit messages so a tool can read them — each subject starts with a `type:` such as `feat:` or `fix:`. Together they let cckit pick the next version from the commits alone.
</Aside>

## How the version is decided

release-please reads every Conventional Commit since the last tag and picks the highest bump (the local `cckit release` fallback applies the same rules via `scripts/lib/version-bump.sh`):

| Commit | Bump | Example |
| --- | --- | --- |
| `feat!:` / `type!:` / a `BREAKING CHANGE:` footer | **major** | `1.4.2 → 2.0.0` |
| `feat:` | **minor** | `1.4.2 → 1.5.0` |
| `fix:` / `perf:` / `refactor:` / `revert:` / anything else | **patch** | `1.4.2 → 1.4.3` |
| no commits since the tag | **none** | no release |

Check what the next version would be at any time:

```bash
cckit release --next        # or: scripts/lib/version-bump.sh --next
```

## Cutting a release (merge the Release PR)

`.github/workflows/release-please.yml` runs on every push to `main`. It doesn't ship anything on its own — it keeps a single **Release PR** open (titled `chore(main): release X.Y.Z`) and rewrites it as more work lands. So you can merge, merge, merge, then release once by merging that PR when the batch is ready.

<Steps>

1. **Work reaches `main`.** Feature branches merge into `develop`; when you're ready, `develop` merges into `main` via PR. (`main` is protected — releases only.)

2. **release-please opens/updates the Release PR** — it computes the bump from the commits since the last tag, bumps all four version surfaces (`package.json`, `docs-site/package.json`, `.claude-plugin/plugin.json`, `cckit.config.json`) plus `Formula/cckit.rb`, and regenerates `CHANGELOG.md`. Review it whenever; nothing ships yet.

3. **Merge the Release PR.** That merge is the release: release-please tags `vX.Y.Z` and cuts the GitHub Release, then the `publish` job pushes to npm and bumps the Homebrew tap automatically.

</Steps>

A batch with only `chore`/`docs` noise produces no Release PR (`bump=none` → nothing to release). Because the release is a single PR merge, two feature PRs merging at once can no longer race each other into a corrupted tag.

<Aside type="caution" title="Workflow edits are human-reviewed">
Changes to the release workflow are always reviewed by a person — the CI token has a wide blast radius. This repo ships the workflow; a maintainer merges the PR that adds or edits it.
</Aside>

## Publishing to npm + Homebrew

Publishing is automatic once the Release PR is merged — the `publish` job in `release-please.yml` runs `npm publish` and bumps the [jeiemgi/homebrew-cckit](https://github.com/jeiemgi/homebrew-cckit) tap (recomputing the formula `sha256`).

**npm uses OIDC trusted publishing** — no long-lived `NPM_TOKEN`. GitHub Actions mints a short-lived OIDC token per run (`id-token: write`) that npm exchanges for publish rights, and the tarball is signed with [provenance](https://docs.npmjs.com/generating-provenance-statements) automatically. Nothing to rotate or leak. It needs a **one-time setup** on npmjs.com (below) and npm ≥ 11.5.1 (the job upgrades npm before publishing).

The **Homebrew** channel is still gated on a repo secret and simply skipped if it's absent — either of:
  - **GitHub App (preferred)** — `HOMEBREW_APP_ID` + `HOMEBREW_APP_PRIVATE_KEY` for an app with **Contents: write** installed on `homebrew-cckit`. The workflow mints a short-lived, tap-scoped token per run — nothing to expire or rotate by hand.
  - `HOMEBREW_TAP_TOKEN` — legacy fallback: a PAT with push access to the tap repo (`contents:write`). Used only when the app secrets are absent.

<Aside type="tip" title="One-time setup checklist">
- **npm trusted publishing** — on npmjs.com, open the `@jeiemgi/cckit` package → **Settings → Trusted Publishing** and add a GitHub Actions publisher for this repo with workflow `.github/workflows/release-please.yml`. No secret to store.
- The Homebrew tap auth (the GitHub App, or the PAT) set under **Settings → Secrets and variables → Actions**.
- `develop` is the default branch; `main` is protected (PR required, no force-push or deletion) so it only advances through a merged PR.
- On the **first** Release PR, reconcile the hand-written `## [Unreleased]` block in `CHANGELOG.md` — release-please owns changelog entries from then on.
</Aside>

<Aside type="note" title="Configuring npm trusted publishing">
1. Publish `@jeiemgi/cckit` **once** the classic way if it doesn't exist yet (trusted publishing links to an existing package), e.g. `cckit release X.Y.Z --publish` from a logged-in machine.
2. On npmjs.com go to the package → **Settings → Trusted Publishing → Add publisher** → **GitHub Actions**.
3. Fill in owner `jeiemgi`, repository `cckit`, workflow filename `release-please.yml`. Leave the environment blank (the job runs without a named environment).
4. Save. The next merged Release PR publishes with zero secrets and full provenance.
</Aside>

<Aside type="note" title="Setting up the Homebrew tap GitHub App">
1. **Settings → Developer settings → GitHub Apps → New GitHub App.** Give it repo **Contents: Read and write**; no webhook, no other permissions.
2. **Generate a private key** (downloads a `.pem`) and note the **App ID**.
3. **Install** the app on `homebrew-cckit` only.
4. Add repo secrets `HOMEBREW_APP_ID` (the App ID) and `HOMEBREW_APP_PRIVATE_KEY` (the full `.pem` contents). The workflow prefers these over `HOMEBREW_TAP_TOKEN` automatically.
</Aside>

### Local fallback

`scripts/publish.sh` (aliased as `cckit release`) still cuts a release from your machine if you ever need to bypass CI. It is dry-run by default — nothing changes until you add `--publish`.

```bash
cckit release X.Y.Z              # DRY RUN — prints the full plan, changes nothing
cckit release X.Y.Z --publish    # tag + GitHub release + Homebrew formula + npm (needs tokens)
```

## Commit message rules (the contract)

- **Every PR title** uses a Conventional Commit subject: `type(scope): summary`. PRs are **squash-merged**, so the PR title becomes the single commit on the base branch — the exact line release-please reads to pick the next version.
- **Breaking changes** use `!` after the type/scope **or** a `BREAKING CHANGE:` footer — never a silent major.
- **One logical change per PR** so the generated release notes read cleanly.

### The gate (enforced in CI)

`.github/workflows/commitlint.yml` runs on every pull request and **fails the check until the PR title is a Conventional Commit subject** — so a non-conventional title can never merge and under-bump the release. The rule lives in `scripts/lib/commitlint.sh` (the single source of truth), which also runs locally through `scripts/check.sh`, so you can validate a subject before you open the PR:

```bash
scripts/lib/commitlint.sh "feat(orchestrate): headless launch"   # exit 0 = valid
```

Accepted types are the [config-conventional](https://www.conventionalcommits.org/) set — `feat`, `fix`, `perf`, `refactor`, `revert`, `docs`, `chore`, `style`, `test`, `ci`, `build` — a superset of the types that trigger a version bump (see the table above); the rest are valid but release-neutral. Re-titling a PR re-runs the check automatically (the workflow listens for `edited`).
