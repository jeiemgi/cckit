# lib/verbs/ — the verbs, for an agent that runs or changes one

Read when a verb is the task; AGENTS.md points here instead of loading it in every session. The
machine-readable list is `lib/core/verbs.tsv`; the reference for people is
`docs-site/src/content/docs/cli-reference.mdx`.

## Core verbs

Every verb, the question it answers, one prompt to paste, its usage and whether it uses the forge
live in one table, `lib/core/verbs.tsv`. `cckit help` prints it grouped by question, git
mechanics first; `cckit commands --json` returns it as data, one object per verb. The table below
carries the flags and behaviour of each verb.

| Verb | Purpose | LLM mode |
| --- | --- | --- |
| `cckit init [<folder>] [--adapter <claude\|codex\|both>]` | guided project setup, then the scaffold. Before anything is written init classifies the folder: a repository with a remote, a repository without one, a project without git, files with no project marker, an empty or missing folder, or a home/system folder (`$HOME`, `~/Desktop`, `~/Documents`, `~/Downloads`, `/`), which is never scaffolded into. Questions (is this a new project, where it lives, recipe, database, profile) are answered from `--answers FILE` (a JSON object `{"<key>":"<value>"}`: `new_project`, `folder_use`, `project_name`, `location`, `recipe`, `database_needed`, `database`, `profile`), else on a terminal; a key the file omits takes the recommended option. With neither a terminal nor an answers file init runs from flags alone, and a home folder exits 2. `--recipe <id>` starts a NEW project from `kit/recipes/<id>.json` (shipped: `nextjs-shadcn`), and the recipe's `config` object is merged into the project config (`nextjs-shadcn` sets `tasks.check` to `pnpm build && pnpm lint` and `tasks.design` to `true`, which makes every task of the project a page task and installs the `page-design` skill); `--database <id>` applies `kit/databases/<id>.json` (shipped: `supabase`: packages, `lib/supabase/{client,server}.ts`, variable names with placeholders in the gitignored `.env.local`, and a guide page; values are typed by the user and never printed). Then the git + GitHub steps, listed first and run after one confirmation (a terminal prompt, or `--yes`; with no terminal and no `--yes` they do not run and the last lines say so, naming what is left undone and the command for it: `Not done: the cckit files are not committed.` and, when the config's base branch is in neither the repository nor origin, `Not done: the branch '<base>' … does not exist`; the base branch written without the setup is the repository's GitHub default, else `main` when it exists or there is no commit, else the checked-out branch): `git init` + first commit, on a repository that already had commits ONE commit `chore: add the cckit project files` on the base branch holding the files init wrote (no env file, nothing git ignores, no script of the project's own, nothing the project had staged; skipped once the project config is tracked; `failed` when the folder is on another branch than an existing base), `gh repo create` (private; `--public` for public) or the existing remote, base branch `develop` created and pushed (when GitHub already has the base branch, the kit files commit is pushed to it), labels + milestones (missing ones only), delete-head-branches, base-branch protection (a plan that refuses it is `skipped` with the reason), Projects v2 ids when the board is on, the doctor report. Each step prints `done` / `skipped` / `failed`; a failed step does not stop the later ones and the run exits 1; a re-run skips finished steps. `--no-github` is the scaffold alone. Every scaffold adds `.cckit/` and `.claude/worktrees/` to `.gitignore`. The rendered instruction file names the project's base branch in its PR section and, with `tasks.default: "light"`, names the task files as the source of truth; the closing next steps of such a project name `cckit task new` / `cckit task start`, not the label and milestone scripts. `--dry-run` prints the recipe commands and every step and writes nothing, the folder included. Exit 0 done · 1 a step failed · 2 refused before any write (home folder, unknown recipe or answer, a recipe on a non-empty folder). `--upgrade` never enters this flow. The scaffold: config + the selected adapter(s), default `claude`. `claude` writes `CLAUDE.md` + `.claude/`; `codex` writes `AGENTS.md` + `.agents/{skills,rules}` and, when it is the only adapter, keeps the config at the root `cckit.config.json` and the ownership manifest at `.cckit/kit.manifest.json` — no `.claude/` tree. `--plain-language <on\|off>` installs the `plain-language` rule and sets `plainLanguage.enabled` (default: the profile's). `--profile <name>` picks one of `kit/profiles/*.json` (`software`, `content`, `marketing`, `research`, `automation`, `minimal`); `marketing` is `content` plus `tasks.default: "light"`, plain language on, and the `brand-voice`, `campaign` and `page-design` skills. `page-design` is also installed by any recipe or project config that sets `tasks.design: true` (on `--upgrade` too, when the project is behind the installed version; a project already at it is refused before anything is added, and gets the skill from `cckit add page-design`). It coordinates three third-party design skills that init never installs: the closing next steps offer them as `cckit add impeccable`, `cckit add emil-design-eng`, `cckit add web-design-guidelines`, then `cckit doctor --fix`. The selection is stored as `adapters` in the config; `--upgrade` keeps it, and `--upgrade --adapter <name>` adds an adapter without rewriting the other's files. Both adapters get the same hook scripts — base-branch commit guard, raw-git guard, session mail, session-start checks: Claude in `.claude/hooks/` (mail wired in the tracked `.claude/settings.json`), Codex in `.codex/hooks/`, registered in `.codex/hooks.json` by a merge that keeps the entries already there and uses no absolute path. Codex runs a project hook only after it is trusted (`/hooks`). Specialist agents come from one role source (`kit/templates/agents/<role>.md`): Claude gets `.claude/agents/<role>/AGENT.md`, Codex gets `.codex/agents/<role>.toml` (`name`, `description`, `developer_instructions`); a Claude tool allowlist and model alias do not translate and are written into the TOML as comments | — |
| `cckit status --board` | board state / what's unblocked. Every read (not `--raw-json`, not a `--cached` hit) also writes `.cckit/board.md` atomically: one tab-separated line per open issue (`#N`, status, kind, effort token `E546` / `E546.3` / `-`, labels, title), grouped Efforts / Sub-issues / Standalone, for `rg '#572' <path>` (`.cckit/` is gitignored, so give the path; sync prints it). `--no-snapshot` skips it, `CCKIT_BOARD_SNAPSHOT=<path>` moves it; no forge, no file | `--llm` → TOON |
| `cckit status --board --json` | the board as ONE JSON object for a dashboard: per-role issues, `unassigned`, `blocked`, `stale`, `mergeQueue` (merge order). `--write` saves it atomically to `<git-common-dir>/kit-sync-cache.json` and never overwrites it with a failed or partial fetch; `--cached [TTL]` prints that cache with no `gh` call while it is younger than TTL seconds (default 60), else refreshes it; `--watch [SECS]` refreshes every SECS (default 30) and keeps the last good cache when a fetch fails; `--plan` inlines `effort plan`. Each fetch emits `op.start` / `op.done` (op `sync`) to `kit-events.jsonl`. `--write` / `--cached` / `--watch` refuse `--role` / `--milestone` (exit 2) | `--json` → JSON (`--llm` / `--output=json` stay TOON) |
| `cckit next` | the next unblocked issue + how to start it. With `tasks.default: "light"` in the config, a bare `cckit next` prints what `cckit task next` prints and makes no `gh` call (with `--json`, that verb's one JSON object or `null`, not TOON rows); any argument takes the issue path. Human output ends with the weekly cadence line (Monday `cckit effort plan --issues` · daily `cckit next` · Friday `cckit gc`); the TOON rows stay `{number,ctx,title}` | `--json` → TOON |
| `cckit effort plan --issues` | wave plan: deps-ordered, priority-sorted within a wave, file-disjoint, session-fit | `--json` → TOON |
| `cckit effort plan --next` | forward plan: inventory current skills/verbs/rules/docs → propose what to build next | `--json` → TOON |
| `cckit status` | where are we: the next effort that can start in each flow (no open blocker; p0 → p3, then lowest number), the light tasks when the project has any (counts by state, then the tasks somebody has to act on: `review`, `doing`, `draft`, `shared`; read from local git, no `gh` call and no fetch), local undone work, open PRs waiting on a human, cleanup available (local + remote), then one line with the resident instruction-file bytes (`CLAUDE.md` + rules without `paths:`) against the 150k limit and the three largest files | `--json` → JSON (`next_efforts` is one row per flow; `null` when the efforts could not be read) (`instruction_budget`, `null` when nothing was measured) (`light_tasks`: `{counts, attention}`, `null` when the project has no light task) |
| `cckit brief <issue>` | the delegation brief for an issue, from real state: worktree, seed freshness, owned files, the helpers they sit on, standing gotchas | — |
| `cckit effort plan --wave [--adapter <claude\|codex\|both>]` | read open efforts, propose incoming waves: fan-out brief + captain drive. The wave data (issues, ctx, one runtime-neutral prompt per issue) is the same for every runtime; the dispatch wording is per adapter — Claude Code spawns Task subagents with worktree isolation, Codex is told to launch `cckit orchestrate --agent codex`, because cckit creates the worktrees there. Default: the project's stored `adapters` (`CCKIT_ADAPTER` overrides) | `--json` → TOON (wave data only, identical for both adapters) |
| `cckit watch [--merge] [--loop]` | captain: gate open PRs, squash-merge CLEAN, advance the wave | — |
| `cckit agent receipt <issue> --stage <s> [--no-remote]` · `cckit agent receipt <issue> --report <file> [--dry-run]` | `--stage` records one stage receipt from stdin, locally and as a comment on the issue. `--report` posts a step report's short trail comment on the issue: the `## Status` head, the report's URLs, the `## Waiting for a yes` items and the report's file name (never an absolute path), capped at 1500 characters. It refuses, posting nothing, when the comment would carry a leak-list word or a home path; `--dry-run` prints it; with no forge it says the comment was not posted and prints it | — |
| `cckit qa <up\|ready\|open\|stop\|verdict\|lanes> [--lane N]` | the QA lane, one review stack per lane (a lane is an issue number: the current branch's, or `--lane`). `up` launches the command declared under `qa` with the project's port env vars set to this lane's block and exits 0 only once every `qa.readiness` probe answers 2xx/3xx (`ready` waits on a launched lane; rc 1 names the failing probes and the launch log, rc 2 refuses a config problem, or a lane port another process already listens on, before launching). `open` prints and opens the changed screen — the PR body's `QA route: /path` line, else `qa.route` — and refuses a lane that is not usable. `stop` exits 0 only when nothing listens on the lane's ports; a listener the lane did not launch is left running (rc 1) unless `--force`. `verdict <pass\|fail>` writes a `qa` receipt bound to the reviewed commit, upserts one PR comment and mails a fail's notes to the builder; with no `pass\|fail` it reads back `pass` · `fail` · `stale` · `none`, exit 0 only for a pass on the current head. `captain.mergePolicy.requireQa` makes `cckit watch` hold a PR without that pass (`QA_MISSING`); a fail on the current head always blocks (`QA_FAILING`). `lanes` takes no argument and prints one row per lane that has a port slot, a launch record or a verdict: branch, ports, `up` · `partial` · `down` · `unknown` by who listens on those ports, the verdict (`pass` · `fail` · `stale` · `none`, or `unknown` when a verdict exists and no local branch does) and the worktree. It is read-only — no launch, no stop, no write, no `gh` or `curl` call — and exits 0 with or without lanes | `--json` → JSON (`lanes` → a JSON array of `{lane, branch, worktree, ports, up, verdict}`, `[]` with no lane) |
| `cckit start <issue\|E<n>\|E<n>.<step>> [slug]` | isolated worktree + branch, bootstrapped: env files copied, per-worktree dev PORT, deps installed at the selected targets. Precedence: **`worktree.installPaths` if set** (those dirs only, installed whether or not each declares dependencies — `[]` installs nothing, and the root/workspace checks are skipped entirely), **else** the root *only when* its manifest declares dependencies or it is a workspace root **with at least one member** (a non-empty `packages:` list, or a non-empty `workspaces` / `workspaces.packages` array), **else nothing** — so a dependency-free root never gets a stray empty `pnpm-lock.yaml`. `installPaths` entries that escape the worktree are refused. `KIT_WT_INSTALL=0` skips the install. **Claim-checked:** `cckit start [--force] <issue>` refuses (rc 1) when another live session already holds the issue's claim in `<git-common-dir>/kit-sessions/` — before the issue read, the fetch and `git worktree add`, so a refusal makes no branch and no worktree. `--force` / `KIT_FORCE=1` starts anyway and takes the claim; a claim whose session pid is dead is reaped; re-running from the same session or from inside the claimed worktree is the usual no-op. A board Status of In Progress or In Review only warns | `--json` |
| `cckit pr <issue> <summary> [--base <branch>]` | commit + push + open PR. The commit takes every change the local gate saw: tracked edits and new files that are not ignored (`git add -A`); new files are named on stderr. A gitignored file (the copied `.env.local`) never enters the commit; a new file that must stay out of a PR belongs in `.gitignore`. `--base` targets a branch other than the configured base (`.github.baseBranch`) — a release PR `develop` → `main`, or a hotfix to the release branch; labels, milestone, board and `Closes #N` are unchanged. The body's checklist follows `pr.bodyStyle`: `code` (default) is `## Verification`, naming the diff; `content` is `## Review`, for a draft. The push exports the target as `KIT_PR_BASE` (set with or without `--base`), so a git pre-push hook can compare against the branch the PR targets. `--base` with no value exits 2 before the commit and the push | `--json` |
| `cckit hotfix <pr\|sha> [--base <branch>]` | carry ONE merged change to the release branch (`main` unless `--base` or `KIT_HOTFIX_BASE`): worktree `fix/<N>-hotfix-<base>` from `origin/<base>`, `git cherry-pick -x` (`-m 1` for a merge commit; every commit of a rebase-merged PR, oldest first), push with `KIT_PR_BASE=<base>`, PR titled after the source with `Cherry-pick of #N` in the body and no `Closes`. A digits-only source is a PR number and must be MERGED; anything else is a commit, whose PR number is read from a `(#N)` suffix or `Merge pull request #N`. Re-runnable: a picked commit is not picked twice and an open PR is reported, not re-created. A conflict stops before the push — resolve, `git cherry-pick --continue`, re-run | `--json` → JSON (`ok`, `url`, `worktree`, `detail`; a refusal is `ok:false` with the reason in `detail`) |
| `cckit close <issue> <summary>` | close issue + mark done | `--json` |
| `cckit task new "<title>"` · `task list [--all]` · `task next` | light tasks: work tracked in the project, with no GitHub issue. `new` writes `tasks/<id>.md` in the current checkout (flags `--priority p0..p3`, `--kind`, `--body`/`--body-file`) and commits nothing. `list` prints each open task's state, derived from git: `draft` (only this checkout) · `todo` (on the base branch) · `shared` (in a `task share` PR that has not merged) · `doing` (a `light/<id>-…` branch exists) · `review` (that branch's copy says done) · `done` / `dropped` (the base branch's copy says so; shown with `--all`). With `plainLanguage.enabled`, `list` adds one line under the table saying what `draft` means there. `next` is the first `todo`/`draft` by priority, then creation date. Records are read through the task source (`tasks.source`, default `file`; `tasks.dir`, default `tasks`). `cckit task default` prints `light` or `issues`: the project's default list (`tasks.default`, `issues` when unset) | `--json` → `new` one JSON object, `list` a JSON array, `next` one object or `null` |
| `cckit task start [--force] [--no-push] <id>` (alias `take`) | worktree `.claude/worktrees/light+<id>-<slug>` on branch `light/<id>-<slug>` from `origin/<base>`, bootstrapped like `cckit start`. A draft is committed on the branch and removed from the checkout it was created in; the branch is pushed unless `--no-push`. Re-running reuses the worktree. Refuses a done task, a `shared` task, and a task whose branch is on origin but not local unless `--force`. With no base branch here or on origin it stops and names the fix (`cckit init --yes`, or a `github.baseBranch` that exists). No session claim. `cckit gc` reports the branch `PROTECTED: light task <id> still OPEN` until the task is done on the base branch | `--json` → JSON (`ok`, `id`, `worktree`, `branch`) |
| `cckit task finish [<id>] "<summary>" [--all]` (alias `done`) | set `status: done` in the task's file on its branch, commit tracked changes (`--all` adds new files), push, open the PR against the base branch: title a Conventional Commit subject ending in `[<id>]`, no `Closes` line. With `pr.bodyStyle: content` the body carries the content review checklist. An open PR is reported, not re-created. The task is done when the PR merges; the verb never merges. Do not run `cckit pr` in a light worktree | `--json` → JSON (`ok`, `url`, `detail`) |
| `cckit task run <id> [--check "<cmd>"] [--max-iters N] [--max-seconds N] [--agent <cmd>] [--no-finish]` | delegate ONE task end to end: `task start` (the worktree is reused when it exists), one `cckit autopilot run` objective built from the task's title and notes, then `task finish --all` with a generated summary, and the review link on stdout. The gate is `--check`, else `tasks.check` in the project config, else none; it runs after the round, and a failing gate opens no PR. The run has no `--until`, so it is one round; `--max-seconds` also bounds that round; `--agent-arg <arg>` (repeatable) is passed to the agent CLI, and cckit adds no permission flag. A stopped earlier run on the task's branch is discarded, never resumed: the task record is the objective. A task already in `review` starts no agent: its open PR is reported, or opening it is retried. `--no-finish` stops after the run and prints `<worktree>\|<branch>\|<id>`. A **page task** is a task whose kind is `page` (`cckit task new --kind page "<title>"`) or any task in a project whose config sets `tasks.design: true`; nothing is inferred from the title or the notes. For one, the objective tells the agent to load the `page-design` skill and to write the design brief and self-review to `docs/design/<id>.md`, the agent is started so its CLI prints events (`claude -p --output-format stream-json --verbose`; Codex prints them already), and the PR body gains a `## Design` section plus the checklist item `Open the page in a browser and compare it with the design brief`. The section lists the skills the run loaded, read from those events and never from the agent's own text: `Design skills loaded in this run: …`, the design skills not loaded, other skills loaded, or `No design skill was loaded in this run.`; a Claude skill call counts only when its result is not an error, so a skill that is not installed is not listed. With no event in a round's output, or no run on record (`task finish` by hand), it says the list is not known. Exit 0 done · 1 the task could not be started · 2 usage, or the run was refused · 3 agent failed · 4 limit · 5 the round changed nothing · 6 gate failed · 7 the PR could not be opened · 130 interrupted; every non-zero exit opens no PR and its last stderr line names the reason. Never merges | `--json` → JSON (`ok`, `id`, `url`, `detail`) |
| `cckit task share ["<summary>"]` | one PR from `light/share-<timestamp>` that adds every draft in the current checkout to the base branch; the tasks list as `shared` until it merges. With no new drafts it retries an earlier share of this repository whose push or PR failed (exit 1 on a failed step), and reports an open PR instead of creating one | `--json` → JSON (`ok`, `url`, `detail`) |
| `cckit claims` | list the live session claims `cckit start` wrote: issue, session pid, start time, branch, worktree. Read-only — a dead session's claim is hidden here and reaped by the next `cckit start` on that issue | `--json` → JSON array |
| `cckit effort new --spec T "<name>" ["sub :: desc" …]` | parent (5-section body + ctx/kind/priority/role/flow labels) + linted native sub-issues — identical to `/kit-effort-new` (one shared core); `start`/`pr`/`close` take `<slug\|N>`; `close` deletes the effort branch and every `sub/<N><letter>-*` branch on origin after the squash (one line each; a failed delete warns, never fails the close). The body's `## Spec` (what done means, a list) is required: `--spec` or `--spec-file`, plain lines made `- ` bullets; a missing, empty or TODO/TBD-only Spec is refused before any write. `cckit effort close` re-reads it and refuses the same way; `--no-spec-check` skips that check and says so in one line | flags: `--spec/--spec-file` (required), `--flow/--role/--kind/--priority/--goal/--scope/--for-agents/--verification/--depends-on/--milestone`, `--slug`. `--kind` is one of `feat fix task chore security scaffold ci adr spike plan` (default `task`) or a content kind `post campaign brand research`; any other value is refused before anything is created. A content kind is a label only: `cckit start` cuts its branch on `task/` (post, brand), `plan/` (campaign) or `spike/` (research), and `cckit pr` titles it `docs:` |
| `cckit effort chain <a> <b> [<c> …]` | wire 2+ issues into a linear order: `b` `blocked_by` `a`, `c` `blocked_by` `b`, plus a `- Depends on #<predecessor>` line in each successor's `## Relations` section. These are the edges `cckit effort plan --issues` layers into waves. Idempotent (an edge or line already there is skipped); pre-existing blockers are kept, never replaced. Validates everything first — fewer than two numbers, a non-numeric arg, an issue that does not exist, a repeated number, or an edge that would close a cycle refuses the whole chain and writes nothing | — |
| `cckit effort start [--force] <slug\|N> [slug]` | effort branch + bootstrapped worktree, **WIP-limited**: refuses a NEW effort once `effort.wipLimit` (default 2) are already in progress. In progress = an `effort/<N>-<slug>` branch exists as a local head **or** on origin, read with `git ls-remote` rather than the cached `refs/remotes` (which is wrong both ways: it misses a branch pushed since the last fetch and keeps one deleted on origin until a prune). At the limit refuses; only strictly under it starts. Re-starting an effort that is already in progress is never gated. The check runs before the fetch/branch/worktree/bootstrap, so a refusal makes no branch, no worktree and no board change — it is not read-free (it queries origin, and a `<slug>` arg was resolved first, which can run `gh issue list`). `0` refuses every ordinary start; `--force` still starts. A non-integer value is ignored with a warning and the default 2 is used; `EFFORT_WIP_LIMIT` overrides the config per invocation. `EFFORT_WIP_REMOTE=0` — or an unreachable origin, which warns and proceeds — counts the cached refs instead. With no `[slug]`, a failed read of the issue title warns on stderr and the start continues with the effort's existing branch slug, or `effort`. Does **not** gate `cckit start <issue>`. Creating the branch writes the start time to `<git-common-dir>/effort-metrics/<N>.start`, which `cckit effort close` reads for `build_seconds`; a re-start keeps the stamp already there | `--force`, or `KIT_FORCE=1` |
| `cckit effort pr [<slug\|N>]` | the ONE effort PR, titled as a Conventional Commit subject carrying the effort token: `type(scope): name [E<n>]` (scope = the `flow:` label, else a legacy title's `[Flow]` tag; type = `--type`, else the `kind:` label, default `feat`). Refuses before the commit, the push or any forge call when the title fails `naming_title_lint pr` (`lib/core/naming.sh`: `commitlint_check` + a trailing `[E<n>]`, `[E<n>.<step>]` or `[#<n>]`). `pr.titleStyle: issue-title` gives `[Role] [#N] name` with no lint | flags: `--summary[-file]`, `--for-agents[-file]`, `--title`, `--type` |

| `cckit effort plan` | session-fit effort plan. Rows come from GitHub (one listing + one `blocked_by` call per effort), or from the executable named by `effort.planSource` (`EFFORT_PLAN_SOURCE` overrides), called as `<source> <owner/repo>` from the project root and printing `number<TAB>flow<TAB>ctx<TAB>title[<TAB>blockers]` rows plus an optional `# age: <text>` line. A source that is not executable, exits non-zero or prints no rows falls back to GitHub. The `source:` line under the header names the source used, its age when reported, and any fallback | `--json` → JSON |
| `cckit orchestrate <a> <b> …` | run N flows in parallel worktrees, in tmux or Herdr. cckit owns the worktree per issue, the `blocked_by` gate, the `--cap` and the result: on tmux each pane runs the agent under `lib/verbs/wave-worker.sh`, which records how the process ended | — (use `--dry-run`) |
| `cckit orchestrate --results [--session=<s>] [--wait <secs>]` | read the wave's collected results: `success` (exit 0), `failure` (exit 1–128), `interrupted` (signal exit, or a `running` record whose pid is gone on the host that wrote it); not finished: `launched`, `running`; `untracked` on Herdr, which owns the agent process. rc 0 all success · 1 any failure/interrupted or no records · 3 none failed, some unfinished. Same for every `--agent` kind | `--json` → JSON |
| `cckit autopilot [<a> …]` | select work, then call `orchestrate --detach` under a cap | — (use `--dry-run`) |
| `cckit autopilot run [<issue>] --objective "<text>"` | ONE headless objective on the current branch: `claude -p` or `codex exec`, one round at a time. Code stops it on `--max-iters` (default 5), `--max-seconds` (3600), `--round-seconds` (900), a passing `--until "<cmd>"`, a failing `--check "<cmd>"` gate, or a round that changed neither HEAD nor the tree. An `--until` that already passes before round 1 ends the run with exit 0 and no round, and stderr says that nothing was changed and that `--check` is the flag for a gate. `--max-tokens` is checked between rounds from the runtime's own usage output; a round that prints none stops the run. `--publish --summary "<s>"` opens the PR through `cckit pr` unless the branch already has one. `--record-skills` starts Claude with `--output-format stream-json --verbose` and writes the skills each round loaded to `.skills` in the state file (`loaded`, `complete`, `source`), read from the CLI's events; `complete` is false when a round printed none. `--resume` continues with counters carried over; a round cut short by a signal or a killed runner counts as usage `unknown`, not zero, and a start is refused (exit 2) while the agent an earlier run recorded in `.cckit/autopilot/<branch>.agent.pid` is still alive. Exit 0 done · 2 refused · 3 agent failed · 4 limit · 5 no progress · 6 gate failed · 7 publish failed · 130 interrupted. Refuses the base branch, `--notify`, and an agent other than claude/codex. Never merges | state file `.cckit/autopilot/<branch>.json` (use `--dry-run`) |
| `cckit gc` | report prunable branches + worktrees — SAFE (own PR merged) and LANDED (no PR of its own, work already on base: effort subs, `worktree-agent-*` isolation worktrees) — never one whose issue is still open; aborts if the protection helper is missing. A branch whose PR or issue state could not be read (a failed `gh` call) is reported UNKNOWN ("could not determine") and kept, never "no PR". A worktree with a detached HEAD gets its own row: LANDED when it is clean and its HEAD is on the base branch or `main`, ORPHAN otherwise | `--json` → JSON counts (`safe`, `landed`, `protected`, `orphan`, `unknown`) |
| `cckit cleanup [--yes]` | the guided destructive sweep over that report: plan first, delete only the SAFE + LANDED rows and prune the listed ZOMBIE metadata (staged work recovered to its branch first); ORPHAN / PROTECTED / UNKNOWN / stashes are never deletable. A LANDED detached worktree is removed; an ORPHAN one, and a detached zombie still holding staged work, are kept | `--json` → JSON counts + `applied` |
| `cckit page <mode\|open\|poll\|reply\|end\|answer>` | review pages, on by default (`reviewPages.enabled`; off with `cckit add lavish --set enable=no`, or `CCKIT_PAGES=terminal` for one command). `mode` prints `page`, or `terminal: <reason>` when the session has no browser: `CI`, `CCKIT_HEADLESS` (exported by `cckit autopilot run` and the tmux wave worker), a headless Claude Code session (`CLAUDE_CODE_SESSION_ATTENDED=0` or an `sdk*` entrypoint), SSH, no `DISPLAY`/`WAYLAND_DISPLAY` off macOS, no agent session and no TTY, or no `lavish-axi`/`npx` on PATH. `CCKIT_PAGES=page` skips the session checks, never the config switch. `open <html-file> [--fallback <md-file>]` runs `lavish-axi <file>` (`npx -y lavish-axi` without the binary); in terminal mode, or when the tool exits non-zero, it prints the fallback file and exits 0; flags after `--` go to the tool. `poll` / `reply` / `end <html-file> [args…]` pass through to the tool and are no-ops in terminal mode. `answer --kind <plan\|decision\|grill> --title "<t>" [--issue <n>] [--body-file <file\|->]` writes ONE comment on the issue when `github.repo` is set and `--issue` is given, else the file `docs/answers/<date>-<kind>-<slug>.md` (`reviewPages.answersDir`), which the caller commits; `reviewPages.answers: issue\|file` fixes the destination. The same kind, title and body twice writes nothing. Exit 0 · 1 the answer could not be written · 2 usage error. An agent calls `mode` before writing any HTML, and calls `answer` on both paths. A page before `cckit effort start` is recommended; `effort start` checks nothing | `--json` → JSON (`mode`: `{mode, reason}`; `open`: `{mode, file}`; `answer`: `{ok, where, issue\|file, written}`) |
| `cckit agent render` | stdin markdown → rich (glow on a TTY; verbatim when piped) | — |
| `cckit version` | the installed cckit version | `--json` |

Every verb accepts a global `--json` (older spellings `--llm` and `--output=json` still work); verbs that produce a result emit a
single JSON object/array on stdout, with human text on stderr. Interactive/launch verbs
(`init`, `orchestrate`, `autopilot`) have no JSON result — use `--dry-run` to inspect their plan.
`cckit brief` has no JSON form either, and deliberately: its output IS the prompt you hand a
delegated agent, so markdown is the machine-readable form. Read the facts behind it as data with
`cckit agent lib --json` and `cckit status --json`.

> **`cckit effort plan --next` is the one exception to "feed verb output back to the model."** Its forward
> plan is for the human/orchestrator's decision only — never inject it into a monitored model's
> prompt or context (context-anxiety rule). Run it, decide, and hand only the chosen, scoped effort
> to an agent. `cckit effort plan --issues` / `cckit next` (ordering existing work) remain safe to reason over.

### Orchestration flags (`orchestrate` / `autopilot`)

| Flag | Effect |
| --- | --- |
| `--dry-run` | resolve + print the launch plan; create no worktrees, start nothing |
| `--cap <N>` | concurrency cap (default 4); flows past the cap are queued + reported |
| `--agent <cmd>` | per-pane agent command (default `claude`, or `CCKIT_AGENT=`) — drive any CLI agent |
| `--profile <name>` | run a declared agent profile (or `CCKIT_PROFILE=`): its `kind` becomes the agent and its `args` are passed to the CLI. Unset picks the cheapest-tier profile; `--agent` overrides and skips profiles entirely. A project that declares none is unaffected |
| `--runtime <tmux\|herdr>` | terminal owner (default `tmux`, or `CCKIT_RUNTIME=`); Herdr requires a supported agent kind such as `codex` or `claude` |
| `--force` | launch even if an issue is `blocked_by` an OPEN issue (the gate is on by default) |
| `--no-seed` | start the agent without an auto-prompt |

**Base branch override.** `KIT_BASE_BRANCH` in the environment wins over `github.baseBranch` in the
config for that invocation: `KIT_BASE_BRANCH=effort/<N>-<slug> cckit orchestrate <sub>` cuts the
sub's worktree from the effort branch instead of the base. `orchestrate` then prints
`base '<branch>' comes from KIT_BASE_BRANCH in the environment (the config says '<base>')`. The
branch must exist on origin (`wt_start` fetches it). Every verb that loads the config reads the same
variable — `cckit start` cuts from it and `cckit pr` targets it — so set it per command, not with a
shell-wide `export`. `orchestrate` passes an override on to each agent pane (tmux: `env KIT_BASE_BRANCH=…`
on the agent's command line; Herdr: `--env`), so `cckit pr` in the pane targets the branch the
worktree was cut from. The base cckit resolved from a config is not an override in a child process:
a `cckit` run in another project reads its own config.

### Night mode (no verb: `/kit-autopilot` + two scripts)

The `kit-autopilot` skill reads the owner's night grant with `lib/verbs/night-grant.sh read <parent>`
and launches the Workflow script `lib/verbs/night-run.mjs` with the args that prints. In a consuming
project both live under `${CLAUDE_PLUGIN_ROOT}/scripts/`.

| Rule | What the scripts enforce |
| --- | --- |
| Who may grant | a `<!-- night-grant -->` comment counts only from an author GitHub reports as `OWNER`, from `github.owner`, or from a login in `night.grantors`; any other author's is ignored |
| Approval | the grant's `waves` list; no label or body section on the effort is required |
| Width | `effort.wipLimit` efforts at once (default 2), never more than 4; executors never pass `--force` |
| Wave order | a wave that did not fully merge ends the run `blocked`; no later wave starts |
| Final check | the gate on the base branch, even when the grant sets a `stopCommand` |
| Waivers | each must equal one floor name; `workflows`, `cost`, `secret` and `night.neverWaivable` are never waivable |

Config: `night.floors`, `night.neverWaivable`, `night.gate`, `night.grantors`, `night.refuseLabels`
— see [Night mode](https://cckit.dev/config-and-permissions/#night-mode).

## Model endpoint

cckit shells out to whatever agent invokes it; it does not embed a model. The endpoint the verbs
that synthesize text read is configured by environment variable names, never values:

`cckit effort close` appends one record per effort to `<git-common-dir>/effort-metrics/records.jsonl`;
its fields, their sources and when each is `null` are in the README under *The effort metrics record*.

The effort-close judge reads an OpenAI-compatible endpoint from `CCKIT_MODEL_URL` (base URL; it
POSTs to `<value>/chat/completions`), `CCKIT_MODEL` (model name) and `CCKIT_MODEL_TOKEN` (bearer
token). A project with its own variables names them in the config instead — `model.urlEnv`,
`model.modelEnv`, `model.tokenEnv` hold env var **names**, never values. See
[Model endpoint for the effort judge](https://cckit.dev/config-and-permissions/#model-endpoint-for-the-effort-judge).

**Agent profiles** (`agents.profiles` in the config) carry a spend `tier`, a permission policy and
extra CLI argv. **cckit never names a model** — you spell your own flags in `args`, and the
cheapest-tier profile runs when `agents.default` is unset, so the inexpensive path is the default
by construction. A profile also declares the `stages` it may run at and whether it may
`write` to a branch; a profile with no `stages` is allowed nowhere, and `write` defaults to false.
Validation refuses an undeclared profile, a missing `kind`, an unknown stage, or a dangling
`agents.default` **before** a worktree or pane exists. See
[Agent profiles](https://cckit.dev/config-and-permissions/#agent-profiles).
